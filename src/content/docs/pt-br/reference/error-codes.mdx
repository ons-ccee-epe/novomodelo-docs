A carga do caso reporta erros em dois grupos: [tipos de relatório de validação](#tipos-de-relatorio-de-validacao)
(categorias de diagnóstico coletadas durante a validação do caso) e
[tipos de falha de carga](#tipos-de-falha-de-carga) (retornados quando a carga do caso falha). A página também
lista os erros de carga da política gerados pela recusa de um checkpoint e os
[erros de execução](#erros-de-execucao) de um `novomodelo run` em andamento.

## Como esses erros chegam até você

O Novo Modelo expõe erros por quatro canais voltados ao usuário:

- **Relatório legível de `novomodelo validate`** — os erros são impressos como linhas com o prefixo `error:`; os avisos (após uma validação bem-sucedida) são impressos como linhas com o prefixo `warning:`.
- **`novomodelo validate --json`** — em caso de sucesso, um objeto JSON no stdout: `{ configured, boundary_date, report }`, mais `policy_load: { mode, unused_stored_bases }` quando a execução carregaria uma política (`mode` `warm_start`, `resume` ou `simulation_only`), sem chave `error`; `configured` é `true` quando `policy.boundary` está configurado e a execução o aplica, o que só ocorre em uma execução que treina, e `false` caso contrário. Em caso de falha, essas três chaves são `null` e uma chave `error` contém `{ phase, message }`. O campo **`phase`** é o nome da [variante de `LoadError`](#tipos-de-falha-de-carga) que falhou, um dos seis [tipos da fase de preparação](#tipos-da-fase-de-preparacao) ou um tipo de carga da política (`WarmStartIncompatible`, `ResumeIncompatible`, `SimulationPolicyIncompatible` ou `IoError` para um checkpoint cuja leitura o sistema operacional recusa); ele nomeia uma variante de `LoadError`, um tipo de preparação ou um tipo de carga da política, nunca o `ErrorKind` de um diagnóstico coletado. Uma falha na carga do caso reporta [`ConstraintError`](#constrainterror) em quase todos os casos, porque toda falha de leitura, análise sintática e esquema de cada arquivo e toda regra de validação são coletadas em um único relatório; seu `message` contém uma linha `[<ErrorKind>] <file>[ (<entity>)]: <message>` por erro coletado, unidas por quebras de linha (a parte `[ (<entity>)]` aparece apenas quando o erro nomeia uma entidade). Os avisos não constam do JSON. Somente a ausência do diretório do caso não imprime objeto JSON; ela é reportada no stderr e encerra com código `2`.

  Um caso sem `policy.boundary` é validado com sucesso com:

  {/* capture: novomodelo validate --json case | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy case (novomodelo init --template 1dtoy case; unmodified; run with NO_COLOR=1, exit code 0) */}

  ```json
  {
    "configured": false,
    "boundary_date": null,
    "report": null
  }
  ```

  Um grupo de unidades geradoras que referencia um barramento inexistente falha com:

  {/* capture: novomodelo validate --json badref | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; system/hydros.json: hydro 0 unit group 0 bus_id changed from 0 to 99; run with NO_COLOR=1, exit code 1) */}

  ```json
  {
    "configured": null,
    "boundary_date": null,
    "report": null,
    "error": {
      "phase": "ConstraintError",
      "message": "[InvalidReference] system/hydros.json (Hydro 0 unit group 0): Hydro 0 unit group 0 references non-existent Bus 99 via field 'bus_id'"
    }
  }
  ```

- **`novomodelo.io.validate(...)` (Python)** — retorna `{ valid, errors: [{ kind, message }], warnings: [{ kind, message, file, entity }] }`. `errors` contém no máximo uma entrada: nenhuma quando `valid` é verdadeiro, uma em caso de falha. Seu `kind` é a mesma string do `phase` da CLI, e seu `message` é o texto completo do erro, que, em uma falha na carga do caso, começa com `constraint violation: `. Para um diretório do caso ausente, em que a CLI não imprime objeto JSON, o Python ainda retorna uma entrada `IoError`. O `kind` de cada aviso é o nome do `ErrorKind`.
- **Classes de exceção Python de `novomodelo.errors`** — a carga do caso gera `ValidationError` ou `CaseIoError`; uma recusa na carga da política gera a classe do seu erro: `PolicyIncompatibleError` para um checkpoint recusado, ausente ou que não pode ser decodificado, `CaseIoError` para uma leitura de checkpoint recusada pelo sistema operacional, e `ValidationError` para um diretório da política ausente ou uma reconciliação de fronteira recusada (veja [Erros de carga da política](#erros-de-carga-da-politica)). Veja [`novomodelo.errors`](/pt-br/reference/python-api/#novomodeloerrors) para a hierarquia completa e [Guia rápido em Python — Tratamento de erros](/pt-br/getting-started/python-quickstart/#tratamento-de-erros) para a captura dessas classes.

As falhas de carga da política usam códigos de saída e classes de exceção diferentes; veja [Como uma falha de carga da política chega até você](#como-uma-falha-de-carga-da-politica-chega-ate-voce). Para a causa e a correção das falhas mais comuns em um estudo, veja [Solução de problemas](/pt-br/running/troubleshooting/).

## Tipos de relatório de validação

Cada erro coletado na carga de um caso é impresso como uma linha de relatório, `[<Kind>] <file> (<entity>): <message>`. A
parte `(<entity>)` aparece apenas quando o erro nomeia uma entidade, e `<Kind>` é um dos valores abaixo.

`novomodelo validate` imprime cada erro como `error: ` seguido da sua linha de relatório e encerra com código `1` quando há
algum erro. `novomodelo run` imprime `error: constraint violation: ` seguido das mesmas linhas. Após uma validação
bem-sucedida, `novomodelo validate` imprime cada aviso como uma linha `warning:` no formato `<file> (<entity>): <message>`
após a linha `Valid case: ...`, sem o tipo entre colchetes, e `novomodelo.io.validate` (Python) retorna os
avisos, cada um com seu tipo, no array `warnings`.
Um aviso da carga da política que a execução aplicaria é impresso depois deles como
`warning: <output dir>/<policy.path>: <message>`, não nomeia entidade e é contabilizado na linha `Validation:`.

Os três tipos de aviso (`UnusedEntity`, `ModelQuality`,
`SemanticAmbiguity`) nunca interrompem uma execução, assim como um `BusinessRuleViolation` que `novomodelo validate` imprime como linha `warning:`; todas as demais linhas de relatório são erros que precisam ser resolvidos
para que o caso seja carregado.

`WarmStartIncompatible`, `ResumeIncompatible` e `SimulationPolicyIncompatible` não são tipos de linha de relatório:
cada um nomeia uma carga da política recusada, como valor de `phase`, e os avisos dessa carga: `WarmStartIncompatible` para uma
carga com `policy.mode = "warm_start"` em uma execução que treina, `ResumeIncompatible` para uma carga com `policy.mode = "resume"`
em uma execução que treina, e `SimulationPolicyIncompatible` para a carga de uma execução somente de simulação, qualquer que seja seu
`policy.mode`; veja as respectivas entradas abaixo.

### `FileNotFound`

**Severidade:** Erro

**Quando ocorre:** Um arquivo exigido pela estrutura do caso está ausente
do diretório do caso. Emitido durante a verificação dos arquivos obrigatórios, uma vez para
cada um que não é encontrado em disco.

**Exemplo:** Um diretório do caso sem `system/hydros.json`:

{/* capture: novomodelo validate fnf1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy fnf1; system/hydros.json deleted; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted, the error: prefix is not quoted and only the first of the two [FileNotFound] lines is quoted) */}

```text
[FileNotFound] system/hydros.json: required file 'system/hydros.json' not found in case directory
```

Um diretório do caso sem `system/buses.json` gera duas
linhas `[FileNotFound]`: a primeira reporta o arquivo obrigatório ausente, a segunda,
a falha na sua leitura:

{/* capture: novomodelo validate nobus | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nobus; system/buses.json deleted; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[FileNotFound] system/buses.json: required file 'system/buses.json' not found in case directory
[FileNotFound] system/buses.json: No such file or directory (os error 2)
```

**Solução:** Crie o arquivo ausente no subdiretório correto. Os arquivos obrigatórios são: `config.json`, `penalties.json`, `stages.json`,
`initial_conditions.json`, `system/buses.json`, `system/lines.json`,
`system/hydros.json` e `system/thermals.json`.

### `ParseError`

**Severidade:** Erro

**Quando ocorre:** Um arquivo existe e foi lido, mas não pôde ser analisado —
sintaxe JSON inválida, cabeçalho Parquet ilegível, campo obrigatório ausente ou
variante de enum desconhecida em uma união JSON com tag. Emitido quando a análise sintática
de um arquivo falha. `config.json` e
`system/hydros.json` reportam um campo ausente ou uma variante desconhecida como
[`SchemaViolation`](#schemaviolation), e
`system/hydro_production_models.json` faz o mesmo para uma variante desconhecida.
Uma entrada de `training.stopping_rules` que contenha um campo pertencente a *outro* `type` de regra — por exemplo,
`seconds` (um campo de `time_limit`) em uma regra `bound_stalling` — também é rejeitada
como `ParseError`, com uma mensagem `unknown field`.

**Formato de exibição:**

```
parse error in {path}: {message}
```

Este formato só aparece para um erro de análise gerado após a conclusão do relatório de validação (veja [Tipos de falha de carga](#tipos-de-falha-de-carga)); uma falha de análise no relatório é impressa como a linha `[ParseError]` mostrada nos exemplos abaixo.

**Campos:**

| Campo     | Descrição                                       |
| --------- | ----------------------------------------------- |
| `path`    | Caminho do arquivo cuja análise falhou          |
| `message` | Descrição legível da falha de análise           |

**Exemplo:**

{/* capture: novomodelo validate trunc | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy trunc; stages.json cut off after the opening bracket of the stages array, leaving one line that ends in a newline; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] stages.json: parse error: EOF while parsing a list at line 2 column 0
```

Um campo obrigatório ausente, aqui uma entrada de restrição sem `slack`:

{/* capture: novomodelo validate gcnoslack | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy gcnoslack; constraints/generic_constraints.json added as a single line holding a constraints array with one constraint, id 0, name cap, expression hydro_storage(0), and no slack object; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] constraints/generic_constraints.json: parse error: missing field `slack` at line 1 column 69
```

Uma regra `bound_stalling` que contém `seconds`, um campo de `time_limit`:

{/* capture: novomodelo validate secs | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy secs; config.json re-written with 2-space indentation, training.stopping_rules gains a bound_stalling rule with iterations 5, tolerance 0.01 and seconds 3; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] config.json: parse error: unknown field `seconds`, expected `iterations` or `tolerance` at line 19 column 5
```

**Solução:** Corrija o erro de sintaxe no arquivo indicado. Use um validador de JSON
ou um visualizador de Parquet para localizar a posição exata. Em arquivos JSON, as causas comuns são
vírgulas finais, aspas ausentes ou chaves desbalanceadas. Para uma mensagem
`missing field`, adicione o campo indicado. Para uma mensagem `unknown
field` dentro de uma entrada de `stopping_rules`, remova o campo que não
pertence ao `type` dessa entrada ou mova-o para uma entrada cujo `type` o declare.

**Veja também:** um objeto `anticipated_config` em `system/thermals.json` que não corresponda a nenhuma das
formas de antecedência aceitas é coletado sob este tipo — veja
[Antecedência inválida de térmica antecipada](#antecedencia-invalida-de-termica-antecipada).

#### Campo desconhecido em uma entrada de restrição genérica

**Quando ocorre:** Cada objeto de restrição genérica aceita exatamente cinco campos
(`id`, `name`, `description`, `expression`, `slack`); qualquer outra chave é rejeitada
como `ParseError`, com uma mensagem `unknown field`.

**Campos:**

| Campo     | Descrição                                                                                |
| --------- | ---------------------------------------------------------------------------------------- |
| `path`    | Sempre `constraints/generic_constraints.json`                                            |
| `message` | Uma mensagem "unknown field", que nomeia a chave indevida e os cinco nomes de campo aceitos |

**Exemplo:** Um objeto de restrição com uma chave `type` adicional:

{/* capture: novomodelo validate gcunk | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy gcunk; constraints/generic_constraints.json added, written with 2-space indentation, holding a constraints array with one constraint, id 0, name cap, expression hydro_storage(0), slack enabled false, plus the extra key type set to upper; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] constraints/generic_constraints.json: parse error: unknown field `type`, expected one of `id`, `name`, `description`, `expression`, `slack` at line 10 column 12
```

**Solução:** Remova o campo desconhecido, mantendo
apenas as cinco chaves aceitas. Veja [Restrições genéricas](/pt-br/reference/generic-constraints/) para a gramática.

### `SchemaViolation`

**Severidade:** Erro

**Quando ocorre:** Um arquivo é analisado com sucesso, mas um campo viola uma restrição
do esquema: um campo obrigatório está ausente de `config.json` ou de `system/hydros.json`, ou uma coluna Parquet obrigatória está ausente (um campo ausente em qualquer outro arquivo JSON é um [`ParseError`](#parseerror)), um valor está fora do intervalo válido
(por exemplo, capacidade negativa, custo de penalidade não positivo, reservatório cujo
`min_storage_hm3` excede `max_storage_hm3` ou estágio cujo `num_openings` é
0), um campo contém um tipo inesperado, ou um `id` de entidade aparece duas vezes em um
arquivo de cadastro como `system/buses.json`. Emitido durante a verificação dos campos de um
arquivo já analisado.

**Exemplo:**

Um custo de penalidade negativo:

{/* capture: novomodelo validate negdef | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy negdef; system/buses.json: deficit segment 0 cost changed from 7500.0 to -100.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/buses.json: field buses[0].deficit_segments[0].cost: penalty value must be > 0.0, got -100
```

Um reservatório cujo armazenamento mínimo excede o máximo:

{/* capture: novomodelo validate resv | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy resv; system/hydros.json: hydro 0 reservoir min_storage_hm3 changed from 0.0 to 800.0 and max_storage_hm3 from 1000.0 to 500.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/hydros.json: field hydros[0].reservoir: min_storage_hm3 (800) must be <= max_storage_hm3 (500)
```

Um estágio sem aberturas:

{/* capture: novomodelo validate nop | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nop; stages.json: stage 0 num_openings changed from 10 to 0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] stages.json: field stages[0].num_openings: num_openings must be > 0
```

Um `config.json` sem `training.selection`:

{/* capture: novomodelo validate nosel | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nosel; config.json re-written with 2-space indentation, training.selection removed; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] config.json: field training.selection: a forward-pass count is required via training.selection
```

Dois barramentos com o mesmo `id` em `system/buses.json`:

{/* capture: novomodelo validate dupbus | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy dupbus; system/buses.json: bus 0 duplicated as a second entry; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/buses.json: field buses[1].id: duplicate id 0 in buses array
```

**Solução:** Corrija o valor no campo indicado. Os caminhos de campo usam
notação de ponto e índices de array começando em zero. Consulte a página
[Formato do caso](/pt-br/reference/case-format/) para os intervalos válidos e os campos obrigatórios.
Para limites de armazenamento, garanta `min <= max`. Para quantidades de aberturas, garanta `num_openings >= 1`.
Em `config.json`, `training.selection` (por exemplo,
`{ "method": "sampled", "forward_passes": 192 }`) e `training.stopping_rules`
são chaves obrigatórias, sem valor padrão quando ausentes. A ausência de `training.selection` é
reportada com a mensagem `a forward-pass count is required via training.selection`; adicione a chave em `config.json`.

**Veja também:** uma inversão da faixa de vertimento ou uma rejeição de
não negatividade em `constraints/hydro_bounds.parquet` é coletada sob este tipo durante uma carga
completa do caso — veja
[Inversão da faixa de vertimento](#inversao-da-faixa-de-vertimento).
Duas das quatro falhas de
[Antecedência inválida de térmica antecipada](#antecedencia-invalida-de-termica-antecipada) imprimem linhas `[SchemaViolation]`; as
outras duas imprimem linhas `[ParseError]` e `[BusinessRuleViolation]`. A carga de um caso imprime toda falha de esquema
como uma linha `[SchemaViolation]`; a forma `schema error in <path>, field <field>: <message>` é o formato de exibição
de [`SchemaError`](#schemaerror), que só aparece para um erro de carga gerado após a conclusão do
relatório.

O objeto `slack` de uma restrição genérica também é verificado sob este tipo, no
campo `constraints[<i>].slack.penalty` ou `constraints[<i>].slack.penalty_basis`:
uma folga habilitada exige um `penalty` positivo e um `penalty_basis`, e uma
folga desabilitada não traz nenhum dos dois. A mensagem de base ausente indica a escolha:

{/* quoted from source: resolve_slack in crates/novomodelo-io/src/constraints/generic.rs at novomodelo v0.20.0 */}


#### policy.path recusado

**Quando ocorre:** `policy.path` é resolvido em relação a `--output`, e um link é verificado tanto onde está quanto para onde aponta. O caminho é recusado quando nomeia o diretório de saída ou um de seus ancestrais, ou quando nomeia, contém ou está dentro de um diretório que uma execução reescreve ou remove. [Configuração — `policy`](/pt-br/running/configuration/#policy) enuncia a regra. Em um caso que treina, o caminho também é recusado quando ele (para um link, seu destino) ou seu irmão `.staging` ou `.previous` não é um diretório ou contém uma entrada que nenhum gravador de checkpoint deixa ali; a mensagem é `refusing to write a checkpoint: …`, citada em [Gerenciamento da política — Conteúdo do diretório de checkpoint](/pt-br/running/policy-management/#conteudo-do-diretorio-de-checkpoint).

{/* quoted from source: crates/novomodelo-io/src/config/policy.rs:248-289 at novomodelo v0.20.0 */}

```text
"{value}" names the output directory or one of its ancestors, which a checkpoint write would replace; choose another directory, such as "./policy"
"{value}" {relation} {dir}, which a run removes whole before writing its outputs; choose a directory that neither contains nor lies inside it, such as "./policy"
"{value}" {relation} {dir}, which holds files a run writes and a checkpoint write would replace; choose a directory that neither names nor contains it, such as "./policy"
```

`{relation}` é `names`, `contains` ou `lies inside`, e `{dir}` é o diretório relativo à saída, como `simulation/hydros`. Para um link, `{value}` assume a forma `{path} -> {target}`. `novomodelo validate` reporta a fase `SchemaError` (código de saída `1`), ou `IoError` (código de saída `2`) quando o caminho não pode ser inspecionado; `novomodelo run` imprime `error: schema error in {path}, field policy.path: {message}` e encerra com código `1`.

#### Limite de termos na expansão de expressões nomeadas excedido

**Quando ocorre:** A expansão substitui cada referência `@name` pela
expressão referenciada e agrega o resultado em um único coeficiente por variável.
Uma declaração acíclica, mas de expansão exponencial, é detectada assim que a
expansão ultrapassaria 100.000 operações sobre coeficientes, muito acima de qualquer
expressão escrita legitimamente, abortando a explosão antes que ela
se materialize. Uma cadeia de duplicação cujos elos são multiplicados por um parâmetro
escalar, `@e_k = @a * @e_{k-1} + @e_{k-1}`, atinge o limite; uma cadeia de simples
autoadições, `@e_k = @e_{k-1} + @e_{k-1}`, reduz-se a um termo por variável
e fica abaixo dele. O limite só se aplica quando uma restrição (ou outra
expressão) de fato referencia a declaração descontrolada — declará-la
sem referenciá-la é apenas uma verificação de existência, de baixo custo, e não uma expansão.

**Campos:**

| Campo     | Descrição                                                                       |
| --------- | --------------------------------------------------------------------------------|
| `path`    | Sempre `constraints/generic_constraints.json`                                   |
| `field`   | `constraints[i].expression` (ou o próprio campo da expressão que referencia)     |
| `message` | `` `@<name>`: named-expression reference "@<name>" expands to more than 100000 coefficient operations; this indicates an exponential reference pattern (e.g. a doubling chain "@e = @prev + @prev")`` quando a expansão ocorre dentro de uma expressão nomeada referenciada, ou `` `<fragment>`: expression expands to more than 100000 coefficient operations`` quando ocorre no próprio texto da expressão que referencia, por exemplo `@e15 + @e15` |

**Exemplo:**

{/* capture: novomodelo validate nbudget | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nbudget; constraints/generic_parameters.json added, written with 2-space indentation, holding one constant scalar parameter, id 1, name a, value 0.5; constraints/generic_constraints.json added, written with 2-space indentation, holding one constraint, id 0, name c0, expression @e60, slack disabled, and 61 named expressions, e0 = hydro_storage(0) and e<k> = @a * @e<k-1> + @e<k-1> for k 1 to 60; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 0, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] constraints/generic_constraints.json: field constraints[0].expression: `@e60`: named-expression reference "@e60" expands to more than 100000 coefficient operations; this indicates an exponential reference pattern (e.g. a doubling chain "@e = @prev + @prev")
```

**Solução:** Reescreva a cadeia de expressões nomeadas para que cresça linearmente, e não
por autoadições repetidas — por exemplo, acumulando em uma única expressão corrente
em vez de duplicar uma referência a cada passo. Veja
[Restrições genéricas](/pt-br/reference/generic-constraints/) para as regras de composição
de `@name`.

#### Expressão de restrição genérica rejeitada

**Quando ocorre:** Uma expressão em `constraints/generic_constraints.json`
(`constraints[i].expression`, ou `expressions[i].expression` para a definição
de uma expressão nomeada) recusada pela gramática ou pela sua regra de linearidade.
Toda mensagem começa com o fragmento problemático entre crases, como em
`` `@zz`: unknown name … ``; um problema no final do texto termina, em vez disso, com
`(at the end of the expression)`.

| Erro                                                               | Mensagem após o fragmento citado                                                                                                               |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Um `@name` declarado nem como parâmetro escalar nem como expressão nomeada | `unknown name "@<name>": no scalar parameter or named expression with this name was declared`                                      |
| Um produto de dois termos que contêm variáveis do PL               | `product of LP variables is not linear`; quando um fator é uma expressão nomeada, seguido de `("@<name>" is the named expression at expressions[<i>], which contains LP variables)` |
| Uma divisão por um termo que contém variável do PL                 | `division by an expression containing LP variables`                                                                                             |
| Uma constante formada por números que divide por zero              | `division by zero`                                                                                                                              |
| Um literal numérico grande demais para ser representado            | `numeric literal <text> is not finite`                                                                                                          |
| Uma parte constante em uma expressão sem operador relacional       | `an expression without a relational operator cannot have a constant part; put the bound in generic_constraint_bounds.parquet or use <=, >= or ==` |
| Dois operadores relacionais                                        | `a generic constraint expression carries at most one relational operator (<=, >=, ==); an inline double-relational range is not supported — split into two constraints` |
| Um operador relacional dentro de parênteses                        | `a relational operator is only allowed at the top level`                                                                                        |
| Um `<` ou `>` isolado                                              | `bare '<' at position <n> is not a valid operator; use '<=' for a relational bound`                                                              |
| Parênteses e sinais unários aninhados em mais de 256 níveis        | `expression nests deeper than 256 levels`                                                                                                       |
| Um corpo de expressão nomeada com operador relacional              | `a named expression cannot contain a relational operator`                                                                                       |
| Um corpo de expressão nomeada que não lê nenhuma variável do PL    | `"<name>" contains no LP variable; declare it in generic_parameters.json as a kind "expression" parameter`                                       |

**Campos:**

| Campo     | Descrição                                                              |
| --------- | -----------------------------------------------------------------------|
| `path`    | Sempre `constraints/generic_constraints.json`                        |
| `field`   | `constraints[i].expression` ou `expressions[i].expression`            |
| `message` | O fragmento citado, seguido de uma das mensagens da tabela acima       |

**Exemplo:** Um produto de duas variáveis do PL:

```text
[SchemaViolation] constraints/generic_constraints.json: field constraints[0].expression: `hydro_generation(0) * thermal_generation(0)`: product of LP variables is not linear
```

**Solução:** Mantenha todos os termos lineares: multiplique uma variável do PL apenas por um
número, um parâmetro escalar ou uma expressão formada por eles, e divida apenas
por uma constante desse tipo. Verifique se cada `@name` corresponde a um parâmetro declarado em
`constraints/generic_parameters.json` ou a uma entrada do próprio array
`expressions` deste arquivo; mova um corpo que não lê nenhuma variável do PL para
`constraints/generic_parameters.json` como um parâmetro `expression`. Veja
[Restrições genéricas — Gramática das expressões](/pt-br/reference/generic-constraints/#gramatica-das-expressoes)
para a gramática completa.

**Quando ocorre:** Uma entrada de `constraints/generic_parameters.json` cujos
campos não correspondem ao seu `kind`, ou um parâmetro `expression` cuja fórmula é
recusada. As mensagens sobre a fórmula começam com o fragmento problemático entre crases,
como em uma [expressão de restrição genérica](#expressao-de-restricao-generica-rejeitada).

| Erro                                                             | Campo                             | Mensagem                                                                                                  |
| ---------------------------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Um campo de conteúdo de outro tipo, como `values` em um `constant` | `scalar_parameters[i].<field>`    | `"values" is only valid for kind "per_stage" or "seasonal", not "constant"`                                 |
| Um parâmetro `expression` sem sua fórmula                         | `scalar_parameters[i].expression` | `"expression" kind requires an "expression" field`                                                         |
| Uma variável do PL na fórmula                                     | `scalar_parameters[i].expression` | `an LP variable cannot appear in a scalar-parameter expression`                                            |
| Um `@name` que não é parâmetro escalar                            | `scalar_parameters[i].expression` | `unknown scalar parameter "@<name>"; a named expression cannot appear in a scalar-parameter expression`    |
| Um operador relacional na fórmula                                 | `scalar_parameters[i].expression` | `a scalar-parameter expression cannot contain a relational operator`                                       |
| Uma constante que divide por zero                                 | `scalar_parameters[i].expression` | `division by zero`                                                                                        |
| Um ciclo de referências entre parâmetros `expression`             | `scalar_parameters`               | `expression-parameter reference cycle detected: <a> -> <b> -> ... -> <a>`                                  |

**Campos:**

| Campo     | Descrição                                           |
| --------- | --------------------------------------------------- |
| `path`    | Sempre `constraints/generic_parameters.json`        |

| `message` | Uma das mensagens da tabela acima                   |

**Exemplo:** Um parâmetro `expression` que lê uma variável do PL:


do PL deve ficar em `constraints/generic_constraints.json`, como uma expressão
nomeada. Veja
[Restrições genéricas — parâmetros `expression`](/pt-br/reference/generic-constraints/#parametros-expression).

#### Antecedência inválida de térmica antecipada

**Quando ocorre:** O `anticipated_config` de uma térmica em `system/thermals.json`
aceita exatamente uma de duas chaves: `lead_stages` (um inteiro maior ou igual a 1) ou
`lead_time_hours` (um número finito maior que 0). Uma antecedência maior que todo o horizonte
de estudo também precisa alcançar um estágio pós-estudo declarado. Quatro falhas acrescentam, cada uma, uma
linha ao relatório de validação:

- `lead_stages` é 0.
- `lead_time_hours` é zero ou negativo.
- O objeto não corresponde a nenhuma das formas aceitas, por exemplo por ter as duas chaves, nenhuma delas ou um
  `lead_stages` negativo.
- A antecedência é maior que todo o horizonte de estudo e não alcança nenhum estágio
  pós-estudo declarado.

**Mensagens:** `novomodelo validate` imprime uma linha `error:` para cada falha. As três
primeiras falhas interrompem a leitura de `system/thermals.json` na primeira entrada problemática, de modo que um arquivo
com várias antecedências inválidas reporta apenas a primeira; a regra do horizonte reporta todas
as térmicas problemáticas. As capturas seguem a ordem da lista acima.

{/* capture: novomodelo validate <case> | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; system/thermals.json: thermal 0 given anticipated_config with lead_stages 0; run with NO_COLOR=1, exit code 1; the Validation summary line is not quoted) */}

```text
error: [SchemaViolation] system/thermals.json: field thermals[0].anticipated_config.lead_stages: lead_stages must be >= 1, got 0
```


Uma antecedência `lead_time_hours` que viola a regra do horizonte produz esta mensagem
no lugar da mensagem de `lead_stages` acima:

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/thermal.rs:126-130 at novomodelo v0.20.0 */}


`{total_horizon_hours}` é a duração de todo o horizonte de estudo em horas. Nas
linhas `SchemaViolation`, o índice em `thermals[0]` é a posição da entrada no array `thermals`, contando a partir de 0; a mensagem do horizonte nomeia, em vez disso, o `id`
da térmica, como em `thermals[id=0]`.

a 1, ou a `lead_time_hours` um número maior que 0. Para uma antecedência maior que o horizonte
de estudo, reduza a antecedência ou declare, em `post_study_stages.json`, um estágio pós-estudo que a antecedência
alcance. Veja
[Visão geral da modelagem dos elementos do sistema §4](/pt-br/math/system-elements#usinas-termeletricas-com-antecipacao-de-despacho) para o
modelo de térmica antecipada e
[`system/thermals.json`](/pt-br/reference/case-format/system/#systemthermalsjson)
para os campos do arquivo.

#### Inversão da faixa de vertimento

**Quando ocorre:** Uma faixa de vertimento invertida (`min_spillage_m3s > max_spillage_m3s`)
ou um `min_diversion_m3s`, `min_spillage_m3s` ou `max_spillage_m3s` negativo em
`constraints/hydro_bounds.parquet` é reportado aqui (com a tag `[SchemaViolation]`)
na carga completa de um caso, e aparece como um `SchemaError` isolado quando esse
arquivo é verificado separadamente.

**Campos:**

| Campo         | Descrição                                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `description` | Contém uma linha `[SchemaViolation] constraints/hydro_bounds.parquet: field hydro_bounds[<i>].<column>: <message>` — veja abaixo |

**Exemplo:**

```text
[SchemaViolation] constraints/hydro_bounds.parquet: field hydro_bounds[0].max_spillage_m3s: max_spillage_m3s (5) must be >= min_spillage_m3s (10)
```

```text
[SchemaViolation] constraints/hydro_bounds.parquet: field hydro_bounds[0].min_diversion_m3s: value must be >= 0.0, got -5
```

**Solução:** Corrija a linha problemática para que `min_spillage_m3s <=
max_spillage_m3s` e para que `min_diversion_m3s`, `min_spillage_m3s` e
`max_spillage_m3s` sejam todos não negativos. Veja
[Formato do caso](/pt-br/reference/case-format/) para a referência das colunas de
`hydro_bounds.parquet`.

#### Capacidade negativa do canal de desvio

**Quando ocorre:** O `diversion.max_flow_m3s` de uma hidrelétrica em `system/hydros.json`
é negativo. A capacidade do canal limita superiormente a vazão desviada, e a
vazão tem limite inferior `0`, de modo que uma capacidade negativa é rejeitada na carga. Um
canal sem limite de capacidade omite `max_flow_m3s` ou o define como
`null`.

**Campos:**

| Campo         | Descrição |
| ------------- | ----------- |
| `description` | Contém uma linha `[SchemaViolation] system/hydros.json: field hydros[<i>].diversion.max_flow_m3s: max_flow_m3s must be >= 0, got <value>`, em que `<i>` é a posição da hidrelétrica no arquivo, a partir de zero |

**Exemplo:**

```text
[SchemaViolation] system/hydros.json: field hydros[0].diversion.max_flow_m3s: max_flow_m3s must be >= 0, got -5
```

**Solução:** Defina `max_flow_m3s` como a capacidade do canal, `0` ou mais, ou
omita-o para um canal sem limite de capacidade. Um `max_diversion_m3s` por estágio ou por patamar
em `constraints/hydro_bounds.parquet` continua limitando a vazão.

### `InvalidReference`

**Severidade:** Erro

**Quando ocorre:** Uma referência de chave estrangeira entre entidades aponta para uma entidade
que não existe no cadastro esperado. Por exemplo, o `bus_id` de um dos grupos de unidades geradoras
de uma usina hidrelétrica referencia um barramento que não está em
`system/buses.json`. Emitido durante a resolução das referências entre entidades.

**Exemplo:**

{/* capture: novomodelo validate badref | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy badref; system/hydros.json: hydro 0 unit group 0 bus_id changed from 0 to 99; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[InvalidReference] system/hydros.json (Hydro 0 unit group 0): Hydro 0 unit group 0 references non-existent Bus 99 via field 'bus_id'
```

**Solução:** Adicione a entidade referenciada ao seu arquivo de cadastro ou
corrija o ID no arquivo que a referencia. Verifique todas as referências de ID:
`unit_groups[].bus_id`, `thermals.bus_id`, `lines.source_bus_id`,
`lines.target_bus_id`, `hydros.downstream_id`.

**Veja também:** uma linha de `constraints/ncs_bounds.parquet` com um `stage_id` não declarado é reportada sob este
tipo — veja
[`stage_id` não declarado em parquet de sobrescrita de limites](#stage_id-nao-declarado-em-parquet-de-sobrescrita-de-limites).

#### Referência de limite de restrição genérica sem linhas de ativação

**Quando ocorre:** `constraints/generic_constraint_bounds.parquet` é a
**grade de ativação** das restrições genéricas — uma restrição se aplica em
`(stage, block)` se e somente se existir uma linha para ela ali, independentemente
de a linha fornecer um extremo numérico ou de o extremo vir inteiramente
do próprio resto afim embutido na restrição (por exemplo, um `<= @demanda`
embutido). Uma restrição cujos únicos extremos vêm desse resto afim, mas
que não tem nenhuma linha no parquet de limites, é coletada como `InvalidReference`
— caso contrário, a referência não se aplicaria a nada e ficaria silenciosamente inerte.

**Campos:**

| Campo         | Descrição                                                                                              |
| ------------- | -------------------------------------------------------------------------------------------------------|
| `description` | Contém uma linha `[InvalidReference] constraints/generic_constraints.json (GenericConstraint <id>): GenericConstraint <id> declares a bound reference but has no activation rows in generic_constraint_bounds.parquet: the reference would apply to nothing` |

**Exemplo:**

```
constraint violation: [InvalidReference] constraints/generic_constraints.json (GenericConstraint 3): GenericConstraint 3 declares a bound reference but has no activation rows in generic_constraint_bounds.parquet: the reference would apply to nothing
```

**Solução:** Adicione ao menos uma linha para o `id` da restrição em
`generic_constraint_bounds.parquet` em cada `(stage, block)` em que ela deva
se aplicar — a linha pode deixar `bound_lower`/`bound_upper` ambos nulos, desde que o
próprio resto afim da restrição forneça o valor; a função da linha passa a ser
apenas ativar a célula. Veja
[Restrições genéricas — a grade de ativação](/pt-br/reference/generic-constraints/)
para o modelo completo.

### `DuplicateId`

**Severidade:** Erro

**Quando ocorre:** Um id ou chave é declarado duas vezes onde deve ser único.
Três situações emitem este tipo: um `id` de grupo de unidades geradoras declarado duas vezes na mesma usina hidrelétrica
(os ids de grupos de unidades são únicos dentro da usina, não globalmente); um `id` de nó do grafo da política (policy graph)
declarado duas vezes em `policy_graph.nodes[]` de `stages.json`; e duas linhas de um
arquivo de sobrescrita `constraints/*_bounds.parquet` que definem a mesma coluna para a
mesma entidade, estágio e patamar. Um `id` de entidade declarado duas vezes em um arquivo de cadastro,
como dois barramentos com o mesmo `id` em `system/buses.json`, é um
[`SchemaViolation`](#schemaviolation), e não um `DuplicateId`; veja o
exemplo dos dois barramentos naquela seção.

**Exemplo:**

{/* capture: novomodelo validate dupug | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy dupug; system/hydros.json: unit group 0 of hydro 0 duplicated, with max_generation_mw and max_turbined_m3s of both copies set to 25.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[DuplicateId] system/hydros.json (Hydro 0): Hydro 0: unit group id 0 is declared more than once; unit group ids must be unique within a plant
```

**Solução:** Renomeie o `id` repetido do grupo de unidades ou do nó, ou remova ou mescle
as linhas de sobrescrita de limites que definem a mesma coluna duas vezes.

### `InvalidValue`

**Severidade:** Erro

**Quando ocorre:** Um valor viola uma regra de domínio que `novomodelo validate`
verifica após a carga dos arquivos. Exemplos: as probabilidades das transições
que saem de um estágio em `stages.json` não somam 1,0, ou um estágio do estudo
tem um array `blocks` vazio. Um reservatório cujo `min_storage_hm3` excede
`max_storage_hm3` e um estágio cujo `num_openings` é 0 são reportados, em vez disso, como linhas
[`SchemaViolation`](#schemaviolation).

**Exemplo:**

{/* capture: novomodelo validate trans | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy trans; stages.json: policy_graph.transitions added as 0 to 1 with probability 0.5, 1 to 2 and 2 to 3 with probability 1.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[InvalidValue] stages.json: outgoing transition probabilities from stage 0 sum to 0.50000000 (expected 1.0 ±0.000001); probability must sum to 1.0
```

{/* capture: novomodelo validate noblk | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy noblk; stages.json: stage 1 blocks replaced by an empty array; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[InvalidValue] stages.json: stage 1 declares no blocks; every study stage must declare at least one block
```

**Solução:** Corrija o valor indicado na mensagem. Consulte
a página [Formato do caso](/pt-br/reference/case-format/) para as restrições documentadas. Para transições,
faça as probabilidades que saem de cada estágio somarem 1,0. Para estágios, declare ao menos um
patamar no array `blocks` de cada estágio do estudo.

**Veja também:** um `min_diversion_m3s` ou `max_diversion_m3s` positivo em uma hidrelétrica
sem canal de desvio declarado é reportado sob este tipo — veja
[Limite de desvio sem canal declarado](#limite-de-desvio-sem-canal-declarado).
Um armazenamento inicial fora da faixa de armazenamento da hidrelétrica, ou listado no array
errado de `initial_conditions.json`, também é reportado sob este tipo — veja
[Armazenamento inicial recusado na carga](#armazenamento-inicial-recusado-na-carga).

#### Linha de limites de restrição genérica sem nenhum extremo e sem resto afim

**Quando ocorre:** Uma linha de `generic_constraint_bounds.parquet` com
`bound_lower = null` e `bound_upper = null` só é válida quando o
próprio `bound_lower_affine`/`bound_upper_affine` da restrição fornece ao menos
um extremo (a linha então apenas ativa a célula, conforme acima). Uma linha com ambos
nulos em uma restrição **sem** resto afim em nenhum dos lados não tem
extremo algum e é coletada como `InvalidValue`.

**Campos:**

| Campo         | Descrição                                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------|
| `description` | Contém uma linha `[InvalidValue] constraints/generic_constraint_bounds.parquet (GenericConstraintBoundsRow[<i>]): GenericConstraintBoundsRow[<i>] on constraint <id> has neither bound_lower nor bound_upper: at least one endpoint is required` |

**Exemplo:**

```
constraint violation: [InvalidValue] constraints/generic_constraint_bounds.parquet (GenericConstraintBoundsRow[4]): GenericConstraintBoundsRow[4] on constraint 3 has neither bound_lower nor bound_upper: at least one endpoint is required
```

**Solução:** Forneça `bound_lower` e/ou `bound_upper` na linha,
ou adicione um operador relacional embutido (`<=`, `>=`, `==`) à
`expression` da restrição, para que um resto afim preencha o extremo ausente. Veja
[Restrições genéricas — a grade de ativação](/pt-br/reference/generic-constraints/).

#### Limite de desvio sem canal declarado

**Quando ocorre:** `constraints/hydro_bounds.parquet` pode sobrescrever o
`min_diversion_m3s` e o `max_diversion_m3s` de uma hidrelétrica por `(hydro, stage)` ou por patamar.
Quando a hidrelétrica não declara canal `diversion`, sua vazão desviada é fixada em
`[0, 0]`. Um piso positivo resultaria no intervalo inviável `[min > 0, 0]`, e
um teto positivo desviaria água que nenhuma usina recebe. A verificação de regras
de negócio rejeita ambas as sobrescritas antes que cheguem ao PL, com um apontamento por
campo.

**Campos:**

| Campo         | Descrição                                                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `description` | Contém uma linha `[InvalidValue] constraints/hydro_bounds.parquet (Hydro <id>): Hydro <id>: hydro_bounds row at stage_id=<stage>[ block_id=<block>] sets <field>=<value>, but the hydro declares no diversion channel; without a channel the diversion column is [0, 0]`, em que `<field>` é `min_diversion_m3s` ou `max_diversion_m3s` |

**Exemplo:**

{/* capture: novomodelo validate divcap | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy divcap; constraints/hydro_bounds.parquet added with compression zstd and one row: hydro_id 0, stage_id 1, max_diversion_m3s 25.0, and the 1dtoy hydro declares no diversion channel; run with NO_COLOR=1, exit code 1; the Validation summary line is not quoted and the error: prefix is not quoted) */}

```text
[InvalidValue] constraints/hydro_bounds.parquet (Hydro 0): Hydro 0: hydro_bounds row at stage_id=1 sets max_diversion_m3s=25, but the hydro declares no diversion channel; without a channel the diversion column is [0, 0]
```

**Solução:** Declare um canal `diversion` na hidrelétrica em
`system/hydros.json` (veja [Visão geral da modelagem dos elementos do sistema](/pt-br/math/system-elements)) ou remova
a sobrescrita positiva de `min_diversion_m3s` ou `max_diversion_m3s` para aquele
`(hydro, stage)` em `constraints/hydro_bounds.parquet`.

#### Armazenamento inicial recusado na carga

**Quando ocorre:** `initial_conditions.json` define o armazenamento de uma hidrelétrica fora
de sua faixa ou no array que não corresponde à sua configuração de `filling`:

- Um `storage[].value_hm3` de uma hidrelétrica sem configuração de `filling` está
  fora da faixa `[min_storage_hm3, max_storage_hm3]` da própria hidrelétrica em
  `system/hydros.json`, além de uma tolerância relativa de `1e-9` (absoluta
  abaixo de 1 hm³). Uma hidrelétrica que entra em operação após o primeiro estágio também é
  verificada. O valor é recusado, nunca truncado. Uma hidrelétrica cujo `min_storage_hm3`
  excede seu `max_storage_hm3` reporta, em vez disso, aquele [`SchemaViolation`](#schemaviolation).
- Uma hidrelétrica com configuração de `filling` está listada em `storage`, ou uma hidrelétrica
  sem essa configuração está listada em `filling_storage`.

Os `min_storage_hm3` e `max_storage_hm3` por estágio de
`constraints/hydro_bounds.parquet` limitam o final do seu estágio, e não o armazenamento
inicial; um valor inicial fora dos limites do primeiro estágio de operação da hidrelétrica gera o
aviso [`ModelQuality`](#modelquality), e não um erro.

**Campos:**

{/* quoted from source: check_initial_storage_range and check_initial_storage_array in crates/novomodelo-io/src/validation/semantic/hydro.rs at novomodelo v0.20.0 */}

| Campo         | Descrição |
| ------------- | ----------- |
| `description` | Contém uma linha `[InvalidValue] initial_conditions.json (Hydro <id>): Hydro <id>: initial storage (<value>) must lie in [min_storage_hm3, max_storage_hm3] = [<min>, <max>]` para um valor fora da faixa, ou `Hydro <id>: has a filling configuration, so its initial storage belongs in filling_storage, not storage` ou `Hydro <id>: has no filling configuration, so its initial storage belongs in storage, not filling_storage` para o array errado |

**Exemplo:**

{/* quoted from source: check_initial_storage_range in crates/novomodelo-io/src/validation/semantic/hydro.rs at novomodelo v0.20.0 — a 1dtoy case whose hydro 0 (storage range [0, 1000]) is seeded with storage 1200 */}

```text

```

**Solução:** Defina o valor dentro da faixa `[min_storage_hm3,
max_storage_hm3]` da hidrelétrica, ou mova a entrada para `filling_storage`, no caso de uma hidrelétrica com
configuração de `filling`, e para `storage`, no caso de uma sem ela. Veja
[Arquivos de condições iniciais](/pt-br/reference/case-format/initial-conditions/).

### `CycleDetected`

**Severidade:** Erro

**Quando ocorre:** Um grafo direcionado que deve ser acíclico contém um ciclo.
Dois grafos são verificados. A cascata hidráulica: as ligações `downstream_id` entre usinas
hidrelétricas devem formar uma floresta direcionada (sem ciclos), pois um ciclo significaria que a usina A
deságua na usina B, que por sua vez deságua de volta na usina A. O grafo da política: os
`policy_graph.nodes[]` de `stages.json`, ligados por `transitions[]`, devem ser
acíclicos; esta verificação só se aplica quando `nodes[]` é declarado.

**Mensagens:**

{/* capture: novomodelo validate cyc | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy cyc; system/hydros.json: hydro 1 (a copy of hydro 0 named UHE2) added, hydro 0 downstream_id set to 1 and hydro 1 downstream_id set to 0; run with NO_COLOR=1, exit code 1; the command prints nine error lines, of which only the [CycleDetected] line is quoted; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[CycleDetected] system/hydros.json: hydro cascade contains a cycle involving hydro IDs: [0, 1]
```

A mensagem dos nós do grafo da política:

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/stages.rs:476-481 at novomodelo v0.20.0 */}

```text
policy-graph nodes contain a cycle; the node graph must be acyclic
```

`novomodelo validate` a imprime como `[CycleDetected] stages.json: <message>`, em que
`<message>` é o texto acima.

**Solução:** Revise a cadeia de `downstream_id` das usinas listadas e remova
o ciclo. Toda cascata hidráulica deve ser uma árvore direcionada cujas raízes são usinas sem
usina a jusante (descarga no canal de fuga). No grafo da política, remova a
entrada de `transitions[]` que fecha o ciclo.

### `DimensionMismatch`

**Severidade:** Erro

**Quando ocorre:** Uma verificação de cobertura entre arquivos falha. Por exemplo, quando
`scenarios/inflow_seasonal_stats.parquet` está presente, cada hidrelétrica precisa de uma linha
para cada estágio do estudo em que está ativa, e cada par (hidrelétrica, estágio) ausente
é um erro que nomeia a hidrelétrica e o estágio. Uma divergência significa que um
arquivo opcional por entidade fornece dados para algumas entidades, mas não para todas as que
os exigem. Quando `system/fpha_hyperplanes.parquet` contém alguma linha, toda usina
configurada com o modelo `fpha` que tenha capacidade de turbinamento precisa de linhas
próprias, qualquer que seja seu `source`, e uma usina sem elas é reportada como
`Hydro <id> is configured with FPHA model but has no FPHA hyperplanes`.

{/* quoted from source: the fpha_hyperplanes check and collect_fpha_hydro_ids in crates/novomodelo-io/src/validation/dimensional.rs at novomodelo v0.20.0 */}

**Exemplo:**

{/* capture: novomodelo validate cyc | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy cyc; system/hydros.json: hydro 1 (a copy of hydro 0 named UHE2) added, hydro 0 downstream_id set to 1 and hydro 1 downstream_id set to 0; run with NO_COLOR=1, exit code 1; the command prints nine error lines, of which only the first [DimensionMismatch] line is quoted; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[DimensionMismatch] scenarios/inflow_seasonal_stats.parquet (Hydro 1): Hydro 1 missing inflow seasonal stats for stage 0
```

**Solução:** Adicione as linhas ausentes ao arquivo Parquet; a mensagem nomeia a
hidrelétrica e o estágio sem linha. Quando esse arquivo está presente, cada hidrelétrica precisa de uma
linha para cada estágio do estudo em que está ativa.

### `BusinessRuleViolation`

**Severidade:** Erro

**Quando ocorre:** É violada uma regra de negócio específica do domínio que não pode
ser expressa como uma simples restrição de intervalo. Exemplos: um `turbined_cost` negativo
em uma hidrelétrica cujo modelo de geração é `fpha`, um cronograma de enchimento de volume morto que não consegue
atingir o volume morto antes da entrada em operação da hidrelétrica, as regras de térmica antecipada
e de fronteira pós-estudo, uma linha de sobrescrita de limites que nomeia um
`stage_id` não declarado, uma usina elevatória em serviço em um estágio em que sua hidrelétrica de origem ou de destino não está em operação (Operating), ou uma referência por patamar de restrição genérica que os patamares do estágio
não conseguem satisfazer. Uma verificação reporta um `BusinessRuleViolation` como aviso: quando o modelo de afluências é estimado a partir de `scenarios/inflow_history.parquet` e uma hidrelétrica tem mais de uma observação em um mesmo período sazonal de um ano, `novomodelo validate` imprime uma linha `warning:` (código de saída `0`) informando que as observações são agregadas na resolução do período sazonal.

**Exemplo:**

{/* capture: novomodelo validate fpha | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy fpha; system/hydros.json: hydro 0 generation.model changed from constant_productivity to fpha, and a penalties block with turbined_cost -0.05 added to hydro 0; run with NO_COLOR=1, exit code 1; the Validation summary line is not quoted) */}


#### Coluna determinística de afluência externa sob modelo autorregressivo

**Quando ocorre:** No esquema de amostragem de afluências `external`, a média e o desvio-padrão
sazonais de uma afluência são substituídos pelos momentos amostrais de seu
arquivo de cenários externos apenas para uma hidrelétrica de ordem autorregressiva 0 sem componente
anual; uma hidrelétrica cujos arquivos declaram um coeficiente de defasagem ou um componente anual
mantém as estatísticas declaradas em seus próprios arquivos. A substituição é feita por classe: uma
classe de carga ou de fonte não despachável obtém seus momentos de seu arquivo externo
apenas quando essa própria classe é `external`.

Uma coluna constante (σ = 0) é aceita para carga, NCS e uma hidrelétrica de ordem 0
sem componente anual, mas é **rejeitada** para uma hidrelétrica cujos arquivos declaram uma
ordem autorregressiva acima de 0 ou um componente anual: um único valor determinístico
não pode substituir tal modelo, pois teria de ser igual à própria saída
PAR determinística do modelo, estágio a estágio, que o carregador não
reconstrói a partir de uma coluna constante.

**Campos:**

| Campo         | Descrição                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `description` | Contém uma linha `[BusinessRuleViolation] <external inflow file> (inflow entity <e> stage <stage_id>): <message>` |

**Exemplo:**

```
constraint violation: [BusinessRuleViolation] scenarios/external_inflow_scenarios.parquet (inflow entity 7 stage 3): inflow external library at stage 3, entity 7: every scenario value is constant (σ = 0), but this hydro's inflow follows an autoregressive model of order > 0; a deterministic value here would have to equal that model's own deterministic PAR output at every stage, which this loader does not compute upstream
```

**Solução:** Dê à coluna externa uma variação real de estágio para estágio ou
reduza o modelo autorregressivo de afluências da usina para ordem 0 (sem coeficiente de defasagem, sem
componente anual), se sua afluência for de fato determinística. Veja
[Geração de cenários §4.4](/pt-br/math/scenario-generation) para a regra de aceitação/rejeição
e [`scenario_source`](/pt-br/running/configuration/#trainingscenario_source) para a
configuração do esquema.

#### Compromisso de despacho em térmica não antecipada

**Quando ocorre:** As entradas `past_anticipated_commitments` de `initial_conditions.json`
declaram um compromisso de despacho decidido externamente para uma térmica antecipada,
identificado por `thermal_id`. A validação do caso rejeita qualquer entrada cujo `thermal_id`
não corresponda a uma térmica com `anticipated_config` — seja porque a térmica não
existe, seja porque existe mas não está configurada como antecipada.

**Campos:**

| Campo         | Descrição                                                                                                                                                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `description` | Contém uma linha `[BusinessRuleViolation] initial_conditions.json (initial_conditions.past_anticipated_commitments[thermal_id=<id>]): Thermal <id>: referenced in past_anticipated_commitments but is not an anticipated thermal (anticipated_config is None or thermal does not exist)` |

**Exemplo:**

```
constraint violation: [BusinessRuleViolation] initial_conditions.json (initial_conditions.past_anticipated_commitments[thermal_id=12]): Thermal 12: referenced in past_anticipated_commitments but is not an anticipated thermal (anticipated_config is None or thermal does not exist)
```

**Solução:** Defina `anticipated_config` na térmica `<id>` em
`system/thermals.json` ou remova/corrija o `thermal_id` na entrada
`past_anticipated_commitments` problemática. Veja
[Visão geral da modelagem dos elementos do sistema §4](/pt-br/math/system-elements#usinas-termeletricas-com-antecipacao-de-despacho) para a configuração de térmicas antecipadas e [Formato do caso](/pt-br/reference/case-format/)
para o esquema de `initial_conditions.json`.

#### Fronteira pós-estudo desancorada ou malformada

**Quando ocorre:** A verificação de regras de negócio valida `post_study_stages.json` — o
calendário da fronteira pós-horizonte — e as entregas de térmicas antecipadas que
recaem sobre ele. Várias falhas distintas são coletadas nessa única verificação.
(Uma usina cuja antecedência é maior que todo o horizonte de estudo e não alcança **nenhum**
estágio pós-estudo declarado é detectada antes, na validação de térmicas antecipadas,
com uma mensagem
`system/thermals.json … the plant can never deliver within the study horizon`
(veja
[Antecedência inválida de térmica antecipada](#antecedencia-invalida-de-termica-antecipada)); para eliminá-la,
reduza a antecedência ou declare um estágio pós-estudo que a antecedência alcance — veja
[Visão geral da modelagem dos elementos do sistema §4](/pt-br/math/system-elements#usinas-termeletricas-com-antecipacao-de-despacho).)
As falhas pós-estudo, associadas a `post_study_stages.json`:

- O primeiro estágio do calendário pós-estudo não começa exatamente no final do
  horizonte de estudo.
- Os estágios pós-estudo não são contíguos em datas (lacuna ou sobreposição entre
  estágios consecutivos).
- O `duration_hours` de um estágio pós-estudo, arredondado para dias inteiros, resulta em duração não positiva.
- **Regra 1** — a antecedência de uma usina alcança um estágio pós-estudo sem
  célula `thermal_bounds` para seu `(thermal_id, post_study_stage_index)`.
- **V2** — os compromissos de uma usina decididos antes do estudo e entregues após o
  horizonte não ladrilham os estágios pós-estudo que cobrem com cobertura `1.0`.
- **V3** — uma janela de compromisso cobre um estágio pós-estudo que o próprio estudo
  decide (`carried`), ou um estágio além do alcance de decisão da usina.
- **V5** — um compromisso fixo não nulo cobre um estágio pós-estudo fora da
  janela de entrada em operação da usina.

**Campos:**

| Campo         | Descrição                                                                                                          |
| ------------- | ---------------------------------------------------------------------------------------------------------------------|
| `description` | Contém uma linha `[BusinessRuleViolation] post_study_stages.json (...): <message>` por falha — veja as mensagens abaixo |

**Exemplo:**

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (stages[0].start_date): first post-study stage starts 2026-09-08 but the study horizon ends 2026-09-05; the post-study calendar must begin exactly at the study horizon end.
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (stages start_date=2026-10-01): post-study stages are not date-contiguous: the stage starting 2026-09-05 ends 2026-09-28 but the next stage starts 2026-10-01; each stage must end exactly where the next begins.
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (thermals[id=12].anticipated_config): Thermal 12: anticipated lead reaches post-study stage index 0, but post_study_stages.json has no thermal_bounds entry for (thermal_id 12, post_study_stage_index 0).
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (thermals[id=12].anticipated_config): Thermal 12: past_anticipated_commitments do not tile post-study stage index(es) [0] at coverage 1.0; declare the fixed commitment for each (a committed 0 MW is explicit).
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (thermals[id=12].anticipated_config): Thermal 12: past_anticipated_commitments cover post-study stage index(es) [1], which the study itself decides; a declared fixed value there contradicts the study's own decision. Remove the window, or lengthen anticipated_config's lead so the delivery becomes pre-study-decided.
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (thermals[id=12].anticipated_config): Thermal 12: past_anticipated_commitments cover post-study stage index(es) [2], which are past the plant's decision reach and cannot be represented. Remove the window, or shorten anticipated_config's lead so the delivery falls inside the reach.
```

```
constraint violation: [BusinessRuleViolation] post_study_stages.json (thermals[id=12].anticipated_config): Thermal 12: past_anticipated_commitments window [2026-10-01, 2026-11-01) value_mw = 120 covers post-study stage index 0, which is outside the plant's commissioning window [entry=Some(0), exit=Some(6)); the plant is not in service for this stage and the fixed commitment cannot be delivered. Declare a zero commitment at this stage, or widen the commissioning window.
```

**Solução:** Declare `post_study_stages.json` com o primeiro estágio começando
exatamente no final do horizonte de estudo e cada estágio contíguo em datas com o seguinte.
Adicione uma célula `thermal_bounds` para cada `(thermal_id, post_study_stage_index)` alcançado pela
antecedência decidida dentro do estudo de uma usina. Ladrilhe, com cobertura `1.0`, todo estágio pós-estudo coberto por uma
janela `past_anticipated_commitments` de um compromisso decidido antes do estudo,
sem nunca cobrir um estágio decidido pelo estudo ou além do alcance da usina,
e mantenha todo compromisso fixo não nulo dentro da janela de entrada em operação da usina.
Veja [Fronteira pós-estudo e estudos encadeados](/pt-br/math/post-study-boundary) para o modelo de fronteira e
[Formato do caso](/pt-br/reference/case-format/) para o
esquema de `post_study_stages.json`.

#### Janela `past_anticipated_commitments` descoberta ou com cobertura excessiva

**Quando ocorre:** As janelas `past_anticipated_commitments` de uma térmica antecipada
devem ladrilhar exatamente os estágios de entrega **dentro do estudo** que a usina decidiu
antes do estudo — cada um desses estágios coberto com fração `1.0` — e nunca um
estágio que o próprio estudo decide. A verificação de regras de negócio reporta uma lacuna (um
estágio inicial descoberto), um excesso de alcance (uma janela que cobre um estágio
decidido pelo estudo) e um cruzamento do horizonte (uma única janela que atravessa o final do horizonte) como
diagnósticos separados; cada um pode ocorrer de forma independente. Uma janela pode legitimamente
se estender **além** do horizonte (um compromisso decidido antes do estudo e entregue
após o horizonte; para o termo equivalente em outras ferramentas de planejamento, veja o
[Glossário](/pt-br/reference/glossary)) — essa cobertura pós-estudo é validada
separadamente, em
[Fronteira pós-estudo](#fronteira-pos-estudo-desancorada-ou-malformada), acima.

**Campos:**

| Campo         | Descrição                                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------|
| `description` | Contém uma linha `[BusinessRuleViolation] initial_conditions.json (thermals[id=<id>].anticipated_config): <message>` — veja as mensagens abaixo |

**Exemplo:**

```
constraint violation: [BusinessRuleViolation] initial_conditions.json (thermals[id=7].anticipated_config): Thermal 7: past_anticipated_commitments do not tile the leading 2 delivery stage(s) at coverage 1.0; study stage id(s) [0] are not covered exactly once. Write a commitment window (a committed 0 MW is explicit) for every leading delivery stage.
```

```
constraint violation: [BusinessRuleViolation] initial_conditions.json (thermals[id=7].anticipated_config): Thermal 7: past_anticipated_commitments cover study stage id(s) [3] beyond the leading 2 calendar-derived delivery stage(s); a commitment window may not cover a study stage the study itself decides. Shorten the plant's anticipated_config lead so its window stays within the leading 2 delivery stage(s).
```

```
constraint violation: [BusinessRuleViolation] initial_conditions.json (thermals[id=7].anticipated_config): Thermal 7: past_anticipated_commitments window [2026-08-15, 2026-09-15) straddles the study horizon end (2026-09-01); a single window may not cover both in-study and post-study delivery. Declare two windows split at the horizon instead: one ending at 2026-09-01 for the in-study coverage, one starting at 2026-09-01 for the post-study coverage.
```

**Solução:** Escreva uma janela de compromisso para cada estágio de entrega dentro do estudo que a
usina decidiu antes do estudo (um compromisso de `0` MW é uma janela legítima e explícita
— não uma omissão), sem nunca cobrir um estágio que o próprio estudo decide (encerre a janela antes ou
aumente a antecedência do `anticipated_config` da usina, se esse estágio for de fato decidido
antes do estudo), e divida no final do horizonte qualquer janela que o
atravesse. Esses são os estágios de entrega dentro do estudo cuja decisão ocorre
antes do primeiro estágio do estudo: os primeiros `lead_stages` estágios ou, para
`lead_time_hours`, todo estágio cujo instante de decisão — uma antecedência antes do
final do estágio — seja anterior ou igual ao início do estudo. Veja
[Visão geral da modelagem dos elementos do sistema §4](/pt-br/math/system-elements).

#### `stage_id` não declarado em parquet de sobrescrita de limites

**Quando ocorre:** Uma linha em `constraints/{thermal,hydro,line,pumping,contract,hydro_unit_group}_bounds.parquet`
cujo `stage_id` não é um estágio do estudo declarado (pertinência aos ids declarados em
`stages.json`, que podem ter lacunas ou começar em 1) é rejeitada em `novomodelo validate`
como [`BusinessRuleViolation`](#businessruleviolation); uma linha de `constraints/ncs_bounds.parquet`
é rejeitada como [`InvalidReference`](#invalidreference) com
`NcsBoundsRow[i] has invalid stage_id N (not a valid study stage)`. Linhas em
`constraints/generic_constraint_bounds.parquet` e
`constraints/penalty_overrides_*.parquet` com `stage_id` não declarado
**não** são rejeitadas e não têm efeito.

**Campos:**

| Campo         | Descrição                                                                                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `description` | Uma linha `[BusinessRuleViolation] constraints/{family}_bounds.parquet (...): ...` por linha rejeitada, para as seis famílias, ou uma linha `[InvalidReference] constraints/ncs_bounds.parquet: NcsBoundsRow[i] has invalid stage_id N ...` para NCS |

**Exemplo:**

```
error: [BusinessRuleViolation] constraints/hydro_bounds.parquet (hydro_id=0, stage_id=15): Hydro 0: hydro_bounds override names stage_id=15, which is not a declared study stage
```

**Solução:** Corrija o valor de `stage_id` para que corresponda a um dos IDs de estágio
declarados em `stages.json`. Em caso de erro de digitação (por exemplo, `15` em vez de `5`), corrija a linha; em caso de
sobrescrita obsoleta que referencia um estágio removido, exclua a linha ou atualize a declaração
dos estágios.

#### Referências por patamar de restrição genérica

**Quando ocorre:** Um termo de restrição genérica nomeia um patamar que seu estágio
não pode expor. A verificação só é executada para um par (restrição, estágio) que tenha uma linha
em `constraints/generic_constraint_bounds.parquet`. Uma referência de evaporação é um
termo `hydro_evaporation`; uma referência de armazenamento é um termo `hydro_storage_initial`,
`hydro_storage_final`, `hydro_useful_volume_initial` ou
`hydro_useful_volume_final`. Sendo `K` o número de patamares que o estágio
declara, a verificação rejeita quatro condições:

- Um índice de patamar igual ou maior que `K` em uma referência de evaporação ou de armazenamento, em qualquer
  estágio.
- Uma referência de evaporação a um patamar de 1 a `K - 1` em um
  [estágio paralelo](/pt-br/reference/case-format/stages/#stagesjson) com `K > 1`.
- Uma referência de evaporação sem patamar em um estágio cronológico com `K > 1`.
- Uma referência de armazenamento a uma fronteira interna entre patamares, isto é, uma fronteira entre dois
  patamares, em um estágio paralelo com `K > 1`.

As regras estão enunciadas em
[Referências a patamares de `hydro_evaporation`](/pt-br/reference/generic-constraints/#referencias-de-patamar-em-hydro_evaporation).

**Tipo, arquivo, entidade:** `BusinessRuleViolation`,
`constraints/generic_constraints.json` e a entidade `constraint[id=N]`, em que
`N` é o `id` da restrição.

**Mensagens:** `novomodelo validate` imprime uma linha `error:` por rejeição. As cinco
linhas abaixo mostram uma mensagem por modelo, nesta ordem:

1. Um patamar de evaporação igual ou maior que `K`.
2. Um patamar de evaporação de 1 a `K - 1` em um estágio paralelo.
3. Uma fronteira interna de armazenamento em um estágio paralelo.
4. Um patamar de armazenamento igual ou maior que `K`.
5. Uma referência de evaporação sem patamar em um estágio cronológico.

{/* capture: novomodelo validate case 2>&1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; stages.json: stages 0 and 1 carry two blocks PEAK and OFFPEAK with hours h // 2 and h - h // 2 of the single block's hours h, stage 0 block_mode parallel, stage 1 block_mode chronological; constraints/generic_constraints.json added with five constraints on hydro 0, slack disabled: id 0 evap_out_of_range hydro_evaporation(0, 5), id 1 evap_parallel_block hydro_evaporation(0, 1), id 2 storage_interior hydro_storage_final(0, 0), id 3 storage_out_of_range hydro_storage_initial(0, 5), id 4 evap_chronological_bare hydro_evaporation(0); constraints/generic_constraint_bounds.parquet added with compression zstd and one row per activation, constraints 0-3 at stage 0 and constraint 4 at stage 1, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1; the Validation summary line, which carries the temporary path, is not quoted) */}

```text
error: [BusinessRuleViolation] constraints/generic_constraints.json (constraint[id=0]): Constraint "evap_out_of_range": per-block evaporation reference `hydro_evaporation(0, 5)` at stage 0 references block 5 which does not exist at stage 0 (K = 2)
error: [BusinessRuleViolation] constraints/generic_constraints.json (constraint[id=1]): Constraint "evap_parallel_block": per-block evaporation reference `hydro_evaporation(0, 1)` at stage 0 names block 1, past the stage-level evaporation, which requires chronological block mode (stage 0 is parallel with 2 blocks); use block 0 or no block
error: [BusinessRuleViolation] constraints/generic_constraints.json (constraint[id=2]): Constraint "storage_interior": per-block storage reference `hydro_storage_final(0, 0)` at stage 0 resolves to an interior boundary, which requires chronological block mode (stage 0 is parallel with 2 blocks)
error: [BusinessRuleViolation] constraints/generic_constraints.json (constraint[id=3]): Constraint "storage_out_of_range": per-block storage reference `hydro_storage_initial(0, 5)` at stage 0 references block 5 which does not exist at stage 0 (K = 2)
error: [BusinessRuleViolation] constraints/generic_constraints.json (constraint[id=4]): Constraint "evap_chronological_bare": stage-level `hydro_evaporation(0)` at chronological stage 1 is ambiguous — evaporation is per-block there (K = 2); name a block, e.g. `hydro_evaporation(0, 0)`
```

Cada mensagem por patamar cita o termo completo `accessor(hydro, block)`; a mensagem de
ambiguidade no nível do estágio cita `accessor(hydro)` e sugere um termo com patamar.

**Solução:** Nomeie um patamar que exista no estágio: os índices de patamar vão de 0
a `K - 1`. Em um estágio paralelo, referencie a evaporação com o patamar 0 ou sem
patamar, e referencie o armazenamento apenas no início ou no final do estágio: patamar 0
ou nenhum patamar para uma referência inicial, o último patamar ou nenhum patamar para uma referência
final. Para referenciar grandezas por patamar, defina `block_mode` como `"chronological"`
no estágio em [`stages.json`](/pt-br/reference/case-format/stages/#stagesjson); um
estágio cronológico exige um patamar nomeado para a evaporação, como em
`hydro_evaporation(<hydro>, 0)`.

#### Usina elevatória fora das janelas de operação de suas extremidades

**Quando ocorre:** Uma usina elevatória em `system/pumping_stations.json` está em serviço em um estágio em que sua hidrelétrica de origem ou de destino não está em operação: antes do `entry_stage_id` dessa hidrelétrica, a partir de seu `exit_stage_id`, ou enquanto ela está em enchimento de volume morto (Filling). É impressa uma linha para cada extremidade problemática, nomeando o primeiro estágio nessa situação.

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/pumping.rs:63-69 at novomodelo v0.20.0 */}

```text
PumpingStation {id}: active at stage {stage_id} while its {side} hydro {hid} is not Operating there (before entry_stage_id, at or after exit_stage_id, or Filling); a pumping station may operate only inside both endpoints' Operating windows
```

`{side}` é `source` ou `destination`. A linha é impressa como `[BusinessRuleViolation] system/pumping_stations.json (PumpingStation {id}): <message>`.

**Solução:** Mantenha a usina elevatória em serviço apenas nos estágios em que ambas as hidrelétricas estejam em operação: ajuste o `entry_stage_id` e o `exit_stage_id` da usina elevatória ou os das hidrelétricas.

#### Bases armazenadas não utilizadas

Uma carga da FCF completa só usa uma base de PL armazenada quando ela se ajusta ao PL do seu estágio

{/* quoted from source: crates/novomodelo-sddp/src/policy/policy_load.rs:451-479 at novomodelo v0.20.0 */}

```text
warning: stored bases not used: {n} of {m} do not fit the current LP (first: node {node}, {reason}); a stored basis is used only when its column count equals the LP's, its row count equals the LP's template rows plus its recorded cut rows, its basic count equals its row count, and every recorded cut-row slot holds a loaded cut; the policy was trained on a different LP
```

`policy_load.unused_stored_bases`. O Python imprime `novomodelo-python: policy validation warning: {message}`. O código
de saída não é afetado.

### `NotImplemented`

**Severidade:** Erro

**Quando ocorre:** Duas ou mais hidrelétricas que declaram um
`travel_time_hours` positivo alimentam a mesma usina a jusante com valores que diferem em
mais de `1e-9`, e ao menos um estágio do estudo em `stages.json` usa
`block_mode` `"chronological"`. A
verificação rejeita o caso sempre que algum estágio do estudo é cronológico, e não apenas nos
estágios em que a temporização dos arcos seria diferente. Emitido pela verificação de regras de negócio,
com uma linha para cada usina a jusante afetada, em `system/hydros.json`.

**Exemplo:**

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/travel_time.rs:193-197 at novomodelo v0.20.0 */}

```text
Hydro {downstream_id}: chronological confluence with heterogeneous travel times is unsupported in v1 — {n} declared arcs feed this downstream plant with differing travel_time_hours ({arcs}); align the arcs' travel_time_hours or keep every study stage in Parallel mode
```

`{downstream_id}` é o id da usina a jusante, `{n}` é o número de arcos
que a alimentam e `{arcs}` lista esses arcos como itens
`hydro {id} (travel_time_hours={t})` separados por vírgula.

**Solução:** Atribua o mesmo `travel_time_hours` a todos os arcos que chegam a essa usina a jusante
em
[`system/hydros.json`](/pt-br/reference/case-format/hydros/#systemhydrosjson) ou
defina `block_mode` como `"parallel"` em todos os estágios do estudo em
[`stages.json`](/pt-br/reference/case-format/stages/#stagesjson).

### `ModelQuality`

**Severidade:** Aviso (não bloqueia a execução)

**Quando ocorre:** É detectado um problema no modelo de entrada que mantém
o caso válido. Exemplos: uma ordenação de penalidades invertida, o estado de tendência hidrológica
desabilitado em todos os estágios do estudo apesar de terem sido fornecidos coeficientes autorregressivos, um
valor negativo em `scenarios/inflow_history.parquet`, um período sazonal sem
observações nesse arquivo, um par hidrelétrica-período sazonal com pelo menos uma, mas menos de
`estimation.min_observations_per_season`, ocorrências de estágio totalmente cobertas nesse
arquivo, um alerta sobre o `travel_time_hours` declarado de uma hidrelétrica, ou um armazenamento
inicial fora dos limites de armazenamento ao final do primeiro estágio de operação
da hidrelétrica. Cada um é reportado como aviso.

**Exemplo:**

{/* capture: novomodelo validate ord | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy ord; system/hydros.json: hydro 0 gains a penalties block with generation_violation_below_cost 10000.0; run with NO_COLOR=1, exit code 0; the Valid case and Validation summary lines are not quoted) */}

```text
warning: penalties.json: Penalty ordering violation: max(deficit_segment_costs) (7500) should be > generation_violation_below_cost (10000) (both $/MWh) -- 1 hydro(s) affected, worst case: Hydro 0
```

Todo aviso de ordenação de penalidades começa com `Penalty ordering violation:`; as três
mensagens são citadas em
[Verificações de penalidades na carga](/pt-br/math/penalty-system#implementacao-no-novo-modelo).

A mensagem de tendência hidrológica:

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/stages.rs:120-125 at novomodelo v0.20.0 */}

```text
inflow lags are disabled on all study stages (state_variables.inflow_lags = false) despite a PAR(p>0) inflow model (AR order {max_order}), so the inflow-lag dimensions are omitted from the per-stage state. This is a valid configuration for external-solver interoperability; otherwise it is likely a misconfiguration
```

`{max_order}` é substituído pela ordem do modelo AR quando o aviso é emitido. Quando ele
ocorre e o que altera:
[`stages[].state_variables` — Projeção de Cortes](/pt-br/math/cut-management/#stagesstate_variables--projecao-dos-cortes).

A mensagem de contagem de observações:

{/* quoted from source: crates/novomodelo-io/src/validation/semantic/scenarios.rs:1048-1052 at novomodelo v0.20.0 */}

```text
hydro {hid} season {sid} has {n} observations (minimum recommended: {min_obs}); estimation accuracy may be insufficient with so few observations
```

`{min_obs}` é `estimation.min_observations_per_season`. `novomodelo validate` reporta
o aviso apenas quando o modelo de afluências é estimado a partir de
`scenarios/inflow_history.parquet` (isto é, quando o caso não fornece ao mesmo tempo
`scenarios/inflow_seasonal_stats.parquet` e `scenarios/inflow_ar_coefficients.parquet`)
e `stages.json` declara `season_definitions`.

As mensagens de armazenamento inicial, reportadas em `initial_conditions.json` para a hidrelétrica:

{/* quoted from source: check_initial_storage_first_stage_bounds in crates/novomodelo-io/src/validation/semantic/hydro.rs at novomodelo v0.20.0 */}

```text
Hydro {id}: initial storage ({value}) lies below the minimum storage ({min}) at the end of stage {stage_id}, its first operating stage; that stage must reach it from its own inflow
Hydro {id}: initial storage ({value}) lies above the maximum storage ({max}) at the end of stage {stage_id}, its first operating stage; that stage must release the excess
```

O primeiro estágio de operação é o primeiro estágio do estudo dentro da janela de
entrada em operação da hidrelétrica. Seus limites são a linha no nível do estágio (`block_id` nulo) de
`constraints/hydro_bounds.parquet` para essa hidrelétrica e esse estágio ou, na ausência dela, os
`min_storage_hm3` e `max_storage_hm3` da própria hidrelétrica. Uma hidrelétrica com configuração de `filling`
não é verificada. O armazenamento inicial é mantido como declarado.

**Solução:** Revise a entrada sinalizada. Para um aviso de ordenação de penalidades, veja
[Verificações de penalidades na carga](/pt-br/math/penalty-system#implementacao-no-novo-modelo); para o
aviso de tendência hidrológica, veja
[`stages[].state_variables` — Projeção de Cortes](/pt-br/math/cut-management/#stagesstate_variables--projecao-dos-cortes);
para o aviso de armazenamento inicial, verifique se o primeiro estágio de operação consegue atingir
seus limites de armazenamento ou mova o armazenamento inicial para dentro deles.
Avisos deste tipo não impedem a execução do solver.

### `SemanticAmbiguity`

**Severidade:** Aviso (não bloqueia a execução)

**Quando ocorre:** Uma construção válida cuja semântica é ambígua ou
dependente do estágio de um modo que provavelmente surpreenderá o usuário. Duas construções
o disparam, ambas emitidas pela verificação de regras de negócio em
`constraints/generic_constraints.json`:

1. **`thermal_generation(N)` em uma térmica antecipada.** Uso de
   `thermal_generation(N)` em uma restrição genérica quando a térmica `N` é uma
   térmica antecipada. `thermal_generation` refere-se à geração por patamar
   medida no estágio de _entrega_ (quando o compromisso se concretiza), e não à
   decisão de compromisso tomada no estágio corrente. Quem pretende restringir
   o próprio compromisso deve usar `anticipated_decision(N)`.

   **Exemplo:** Uma restrição genérica `thermal_generation(0)` em uma térmica antecipada:

   {/* capture: novomodelo validate sa1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sa1; system/thermals.json: thermal 0 given anticipated_config with lead_stages 1; initial_conditions.json: past_anticipated_commitments gains one window for thermal 0, 2024-01-01 to 2024-02-01, value_mw 0.0; constraints/generic_constraints.json added holding one constraint, id 0, name peak_cap, expression thermal_generation(0), slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 1, block_id and bound_lower null, bound_upper 10.0; run with NO_COLOR=1, exit code 0; the Valid case and Validation summary lines and the first warning line, which concerns the thermal's stage-cadence transition, are not quoted) */}

   ```text
   warning: constraints/generic_constraints.json (constraint[id=0]): Constraint "peak_cap": thermal_generation(0) references an anticipated thermal. thermal_generation refers to the per-block generation at the delivery stage, not the forward commitment. If you intend to constrain the commitment itself, use anticipated_decision(0) instead.
   ```

   **Solução:** Revise a expressão da restrição. Se o objetivo é limitar a
   geração despachada no estágio de entrega, `thermal_generation(N)` está correto
   e o aviso pode ser ignorado. Se o objetivo é limitar a própria decisão de
   compromisso antecipado, substitua `thermal_generation(N)` por `anticipated_decision(N)`.

2. **Tags de energia armazenada que não se cancelariam.** Uma restrição referencia
   tags calculadas — nos coeficientes da expressão, nos seus limites (um `@emax` no
   lado direito conta) ou por meio de um parâmetro `expression` que as lê
   — em uma de duas formas:
   - um teto `max_stored_energy(h)` junto a uma tag de produtibilidade da mesma
     hidrelétrica diferente de `integrated_accumulated_productivity(h)` (ou um
     teto `max_stored_energy_mwh(h)` junto a uma tag de produtibilidade em MWh diferente
     de `integrated_accumulated_productivity_mwh_per_hm3(h)`). As tags diferem
     em abrangência (uma usina ou sua cascata a jusante) ou em critério de avaliação (o ponto de
     referência da usina ou a média da faixa útil), de modo que uma comparação de energia armazenada
     construída com elas não se cancela. É emitido um aviso para cada par desse tipo.
   - tags em MWh (a família `_mwh` e `_mwh_per_hm3`) misturadas com tags brutas. As
     duas famílias diferem por um fator de $10^6/3600$; o aviso diz
     `Constraint "<name>": mixes MWh tags (<tags>) with raw productivity tags (<tags>); the two units differ by a factor of 10^6/3600. Use one family throughout.`

   O caso continua válido.

   **Exemplo:** Uma restrição que combina as duas tags para a hidrelétrica 0:

   {/* capture: novomodelo validate sa2 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sa2; constraints/generic_parameters.json added holding two computed parameters for hydro 0, id 1 name rho tag accumulated_productivity and id 2 name emax tag max_stored_energy; constraints/generic_constraints.json added holding one constraint, id 0, name sec_mismatch, expression @rho * hydro_useful_volume_final(0) >= 0.3 * @emax, slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 1, block_id, bound_lower and bound_upper null; run with NO_COLOR=1, exit code 0; the Valid case and Validation summary lines are not quoted) */}

   ```text
   warning: constraints/generic_constraints.json (sec_mismatch): Constraint "sec_mismatch": pairs max_stored_energy(0) with accumulated_productivity(0) for hydro 0; the two differ in scope or evaluator and would not cancel. The coefficient matching max_stored_energy is integrated_accumulated_productivity.
   ```

   **Solução:** Use `integrated_accumulated_productivity` como o coeficiente
   correspondente a `max_stored_energy`, ou
   `integrated_accumulated_productivity_mwh_per_hm3` com
   `max_stored_energy_mwh`, e mantenha cada restrição em uma única família; veja
   [o exemplo da curva de segurança](/pt-br/reference/generic-constraints/#exemplo-resolvido-uma-curva-de-seguranca).

O aviso é impresso por `novomodelo validate` em sua saída legível; a saída
de sucesso de `--json` não traz avisos.

## Tipos de falha de carga

O valor de `phase` de `novomodelo validate --json` e o `kind` de uma entrada do array `errors` de
`novomodelo.io.validate` (Python) nomeiam a falha que interrompeu a carga. Quase toda falha na carga do caso reporta
[`ConstraintError`](#constrainterror), porque a carga reúne seus problemas em um único relatório. Os tipos estão
listados abaixo na ordem das etapas da carga em que normalmente ocorrem: leitura de um arquivo, análise sintática,
verificação de seus campos e, por fim, validação do caso inteiro.

Durante a carga de um caso, uma falha de leitura, análise ou esquema em um arquivo é coletada
no relatório de validação, em vez de ser retornada isoladamente. Ela aparece como uma
linha de um [`ConstraintError`](#constrainterror): `[FileNotFound]` para uma falha de
leitura, `[ParseError] <file>: parse error: <message>` para uma falha de análise e
`[SchemaViolation] <file>: field <field>: <message>` para uma falha de esquema. Os
formatos de exibição abaixo só aparecem para um erro de carga gerado após a conclusão
desse relatório, como uma recusa de `policy.path` gerada depois que o caso foi carregado; veja [Códigos de saída](/pt-br/reference/cli-reference/#codigos-de-saida).

### `IoError`

**Severidade:** Erro

**Quando ocorre:** Um arquivo obrigatório consta do manifesto de arquivos, mas não pode ser
lido do disco — arquivo não encontrado, permissão negada ou outra falha de E/S
do sistema operacional. Ocorre quando um arquivo JSON ou Parquet é lido para análise e a leitura
retorna um erro. Também é retornado quando um `policy.path` não pode ser inspecionado (código de saída `2`).

**Formato de exibição:**

```
I/O error reading {path}: {source}
```

**Campos:**

| Campo    | Descrição                                   |
| -------- | ------------------------------------------- |
| `path`   | Caminho do arquivo que não pôde ser lido    |
| `source` | Erro de E/S subjacente do sistema operacional |

**Solução:** Verifique se o arquivo existe no diretório do caso. Verifique se o
processo tem permissão de leitura no diretório e no arquivo. Para uma carga completa do caso, a
raiz do caso deve conter todos os arquivos obrigatórios (veja [Formato do caso](/pt-br/reference/case-format/)).
Um problema coletado durante a carga de um caso é impresso como linha de relatório; veja [Tipos de relatório de validação](#tipos-de-relatorio-de-validacao).

---

`ParseError` — veja [`ParseError`](#parseerror); uma falha de análise coletada no relatório é impressa como uma
linha `[ParseError]`.

---

### `SchemaError`

**Severidade:** Erro

**Quando ocorre:** Um arquivo é analisado com sucesso, mas um campo viola uma restrição
do esquema: um campo obrigatório está ausente, um valor está fora do intervalo válido ou
um discriminador de enum nomeia uma variante desconhecida. Ocorre durante a verificação dos campos de um
arquivo já analisado. Também é retornado quando `training.selection`
(que traz a quantidade de simulações forward) ou `training.stopping_rules` está ausente
e a configuração é analisada ou mesclada fora de uma carga de caso (por exemplo, em sobrescritas
de configuração via Python); uma carga de caso reporta a mesma ausência como uma linha
[`SchemaViolation`](#schemaviolation). Também é retornado para um `policy.path` que a execução recusa após a carga do caso (código de saída `1`; veja
[Configuração — `policy`](/pt-br/running/configuration/#policy)).

**Formato de exibição:**

```
schema error in {path}, field {field}: {message}
```

**Campos:**

| Campo     | Descrição                                                              |
| --------- | ---------------------------------------------------------------------- |
| `path`    | Caminho do arquivo que contém a entrada inválida                       |
| `field`   | Caminho, separado por pontos, do campo problemático (por exemplo, `"hydros[3].bus_id"`) |
| `message` | Descrição legível da violação                                          |

**Solução:** O valor de `field` identifica a posição exata do problema.
Verifique se os campos obrigatórios estão presentes e se os valores estão dentro dos intervalos
documentados. Um problema coletado durante a carga de um caso é impresso como linha de relatório; veja [Tipos de relatório de validação](#tipos-de-relatorio-de-validacao).

---

### `ConstraintError`

**Severidade:** Erro

**Quando ocorre:** Categoria genérica para todos os diagnósticos de validação coletados
em qualquer etapa de validação, para rejeições na montagem do sistema e para verificações
feitas diretamente pelos carregadores após a montagem (por exemplo, uma escala de ruído
derivada do fechamento e não finita é rejeitada aqui, com indicação da hidrelétrica e do
período sazonal). O campo `description` contém
todas as mensagens de erro coletadas, unidas por quebras de linha, cada uma prefixada com seu
`[<Kind>]`, o arquivo de origem, um identificador opcional de entidade e o texto da mensagem.

**Formato de exibição:**

```
constraint violation: {description}
```

**Campos:**

| Campo         | Descrição                                       |
| ------------- | ----------------------------------------------- |
| `description` | Todas as mensagens de erro, unidas por quebras de linha |

**Exemplo:** A captura de falha em `--json` em
[Como esses erros chegam até você](#como-esses-erros-chegam-ate-voce) reporta `ConstraintError` como sua
`phase`, com a linha de relatório coletada em `message`.

**Solução:** Leia todas as linhas de `description` — cada linha é um problema
distinto. Corrija todos e execute novamente. O prefixo `[<Kind>]` identifica a
categoria de cada problema, e a seção de cada tipo traz sua solução. Um problema coletado durante a carga de um caso é impresso como linha de relatório; veja [Tipos de relatório de validação](#tipos-de-relatorio-de-validacao).

## Tipos da fase de preparação

Os seis valores de `phase` abaixo aparecem apenas nas verificações de validação de `novomodelo validate`
anteriores ao solver e **não** são tipos de `LoadError`. Eles aparecem no
campo `phase` do erro de `novomodelo validate --json` quando uma verificação da fase de preparação falha
antes da inicialização do solver.

### `ConfigValidationError`

**Severidade:** Erro

**Quando ocorre:** Uma falha de validação de `config.json` na fase de preparação
da montagem do estudo, depois que a configuração foi analisada e antes do início da montagem do
modelo estocástico. Rótulo de arquivo: `config.json`.

**Exemplo:** Uma regra de parada `gap` sem `tolerance` nem
`relative_tolerance`:

{/* capture: novomodelo validate gap | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy gap; config.json re-written with 2-space indentation, training.stopping_rules gains a gap rule with neither tolerance nor relative_tolerance; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
config.json: configuration validation error: gap stopping rule requires at least one of tolerance / relative_tolerance to be present
```

#### Recusas da configuração de seleção de cortes

`training.cut_selection` é verificado em três pontos. Um valor recusado pelo esquema imprime uma linha `[ParseError]`
na carga do caso; uma regra entre dois de seus campos reporta `ConfigValidationError`; uma combinação com outra
configuração reporta [`StudySetupError`](#studysetuperror) (ou `BoundaryReconciliationError` com `policy.boundary`
configurado). Todos encerram com código `1`. [Configuração — `training.cut_selection`](/pt-br/running/configuration/#trainingcut_selection)
enuncia as regras.

{/* capture: novomodelo validate <variant> | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: 1dtoy (novomodelo init --template 1dtoy) with training.cut_selection set per row; run with NO_COLOR=1; the Validation summary line and the error: prefix are not quoted, and the line and column suffix of a parse error is cut */}

| Configuração | Reportado como | Mensagem |
| --- | --- | --- |
| `selection` informado como array | `[ParseError]` | `config.json: parse error: invalid type: sequence, expected internally tagged enum SelectionMethod` |
| Um parâmetro de contagem definido como `0` | `[ParseError]` | `config.json: parse error: training.cut_selection.selection.check_frequency must be >= 1 (got 0)`, nomeando a chave definida como `0` |

| `tie_tolerance` sob `level1` | `[ParseError]` | ``config.json: parse error: the key `tie_tolerance` was removed: `level1` compares row values exactly; delete the key (`training.cut_selection.selection`)`` |
| `row_activity_tolerance` `null` | `[ParseError]` | `config.json: parse error: invalid type: null, expected f64` |
| Um `method` com erro de grafia | `[SchemaViolation]` | ``config.json: field dynmic: unknown variant `dynmic`, expected `level1` or `dynamic` `` |
| `lookback_iterations` menor que `check_frequency` | `ConfigValidationError` | `config.json: configuration validation error: cut_selection config error: cut_selection.lookback_iterations (2) must be >= cut_selection.check_frequency (5)` |

| `max_active_per_stage` com `dynamic` | `StudySetupError` | ``config.json: configuration validation error: training.cut_selection.max_active_per_stage is inadmissible with the dynamic cut selection method; a lazy solve takes its candidates from the active rows and dynamic runs no selection pass, so an evicted row never returns — remove the cap, or use the `level1` method`` |

O método `domination` imprime seu próprio nome na mensagem de método removido. Duas combinações com um
[`training.selection`](/pt-br/running/configuration/#trainingselection) enumerado também reportam `StudySetupError`:

{/* quoted from source: crates/novomodelo-sddp/src/setup/mod.rs:2372-2387 and 2422-2436 at novomodelo v0.20.0 */}



### `StochasticPreparationError`

**Severidade:** Erro

**Quando ocorre:** Uma falha durante a preparação do modelo estocástico — geração de
cenários, montagem do modelo de afluências ou validação de cenários externos. Rótulo de arquivo:
`scenarios/inflow_history.parquet` para um erro do modelo estocástico (após o rótulo,
sua mensagem começa com `stochastic error:`) e `scenarios/` para qualquer outra falha
desta fase, como um erro de carga (após o rótulo, sua mensagem começa com
`I/O error:`). O rótulo depende de como o erro é classificado, e não do arquivo
a que ele se refere.

**Exemplo:** Uma biblioteca histórica sem nenhuma janela completa, um
modelo de afluências ajustado não estacionário (escala de ruído não finita), um
estágio autorregressivo com desvio-padrão nulo, um estágio com mais aberturas que o
primeiro estágio do seu grupo de ruído, ou um arquivo de árvore de aberturas declarado e
ausente.
[Recusas da biblioteca histórica](#recusas-da-biblioteca-historica),
[Recusas do modelo de afluências](#recusas-do-modelo-de-afluencias),
[Número de aberturas do grupo de ruído](#numero-de-aberturas-do-grupo-de-ruido) e
[Arquivo da árvore de aberturas ausente](#arquivo-da-arvore-de-aberturas-ausente) citam as mensagens.

#### Recusas da biblioteca histórica

**Quando ocorre:** Três recusas do conjunto de janelas históricas podem ocorrer
a partir de um caso. O conjunto atende ao esquema forward `historical` e aos estágios que
usam o método de amostragem `historical_residuals` (veja
[Conjunto de Janelas Históricas](/pt-br/math/scenario-generation/#conjunto-de-janelas-historicas) e
[Aberturas por Resíduos Históricos](/pt-br/math/scenario-generation/#25-aberturas-por-residuos-historicos)).
Cada mensagem é `insufficient data: ` seguido do texto abaixo:

- Nenhum ano é admissível, de modo que o conjunto fica vazio:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/window.rs:136-141 at novomodelo v0.20.0 */}
  ```text
  no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
  ```
- Um estágio do estudo não tem período sazonal:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/historical.rs:258-271 at novomodelo v0.20.0 — reproduced with the binary of record at inflow-model order 1, so not quoted as a capture */}
  ```text
  V2.1: stage {stage_id} (index {index}) has season_id: None; all study stages must have a season_id assigned
  ```
- Um resíduo do conjunto não é finito:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/historical.rs:579-598 at novomodelo v0.20.0 */}
  ```text
  V2.3: historical library contains non-finite eta (NEG_INFINITY or NaN) at window year {year}, stage id {stage_id}, hydro id {hydro_id} — sigma=0 with non-matching historical observation or numerical failure
  ```

V2.1 nomeia o id do estágio e, em seguida, seu índice a partir de 0. Um estágio não tem período sazonal
quando não declara nenhum e o caso não tem definições de períodos sazonais ou tem um
mapa de períodos sazonais `custom` que deixa a data de início do estágio descoberta. Por exemplo,
com um modelo de afluências de ordem 1 e um mapa de períodos sazonais `custom` que cobre o primeiro
estágio e seu período sazonal de defasagem, mas deixa descoberta a data de início de um estágio posterior,
`novomodelo validate` reporta V2.1.

V2.3 nomeia o ano da janela, o id do estágio e o id da hidrelétrica.

**Exibição em `novomodelo validate`:** a fase é `StochasticPreparationError`
e o código de saída é `1`. A linha `error:` traz o rótulo do arquivo e o
prefixo `stochastic error:`. Este trecho omite a linha de resumo `Validation:`,
que traz o caminho do caso.

{/* capture: novomodelo validate case 2>&1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; stages.json: season_definitions added with cycle_type monthly and twelve seasons, season_id 0 to 3 on the four stages, sampling_method historical_residuals on every stage; scenarios/inflow_history.parquet added with compression zstd, hydro 0, three monthly windows 2020-01-01 to 2020-04-01, values 41, 42 and 43; scenarios/inflow_ar_coefficients.parquet added with compression zstd and zero rows; run with NO_COLOR=1; the Validation summary line, which carries the temporary path, is not quoted) */}

```text
error: scenarios/inflow_history.parquet: stochastic error: insufficient data: no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
```

`novomodelo run` no mesmo caso encerra com código `1`. A linha não tem rótulo de arquivo e é
seguida da dica de validação. Este trecho omite o banner, o bloco `Execution` e a
linha `Loading case:`.

{/* capture: novomodelo run case 2>&1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: the same temporary 1dtoy derivative as the novomodelo validate capture above; run with NO_COLOR=1; the banner, the Execution block and the Loading case line, which carry the hostname and the temporary path, are not quoted */}

```text
error: stochastic error: insufficient data: no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
  -> run `novomodelo validate <CASE_DIR>` for a full diagnostic report
```

`novomodelo validate` monta o estudo da mesma forma que `novomodelo run`, de modo que também reporta uma recusa
da biblioteca do esquema forward `historical`: como
[`StudySetupError`](#studysetuperror) (`scenarios/: stochastic error: …`) sem
`policy.boundary`, e como
[`BoundaryReconciliationError`](#boundaryreconciliationerror)
(`policy.boundary: …`) com ele; ambos os comandos encerram com código `1`.
Quando um estágio também usa `historical_residuals`, a recusa é reportada como mostrado acima, com ou sem
`policy.boundary`.

#### Recusas do modelo de afluências

**Quando ocorre:** O modelo de afluências, declarado pelos arquivos autorregressivos e de
estatísticas do caso ou ajustado a partir de `inflow_history.parquet`, não consegue sustentar o
estudo. Duas recusas têm mensagem fixa:

- Um estágio autorregressivo tem desvio-padrão nulo. A mensagem nomeia
  o id da hidrelétrica e o id do estágio, e `ar_order` é a ordem autorregressiva
  do estágio:
  {/* quoted from source: crates/novomodelo-stochastic/src/par/validation.rs:54-70 at novomodelo v0.20.0 */}
  ```text
  invalid PAR parameters for hydro {hydro_id} at stage {stage_id}: zero standard deviation with ar_order={ar_order}: AR model requires nonzero variance to normalize coefficients
  ```
  Este é um erro do modelo estocástico. `novomodelo validate` o imprime após o
  prefixo `scenarios/inflow_history.parquet: stochastic error: ` e encerra com código `1`.
  `novomodelo run` o imprime como `error: stochastic error: invalid PAR parameters …`
  com a dica de validação e encerra com código `1`.
- Os coeficientes ajustados a partir do histórico implicam um processo não estacionário, de modo que uma
  razão derivada de desvio-padrão dos resíduos não é finita. A mensagem nomeia o
  id da hidrelétrica e o id do período sazonal:
  {/* quoted from source: crates/novomodelo-io/src/scenarios/residual_derivation.rs:144-152, crates/novomodelo-io/src/error.rs:60 and crates/novomodelo-sddp/src/error.rs:45-46 at novomodelo v0.20.0 */}
  ```text
  I/O error: constraint violation: derived residual_std_ratio is non-finite for hydro_id={hydro_id} season={season}: the coefficients imply a non-stationary process (implied residual variance 1 - sum(psi*rho) is negative)
  ```
  Este é um [`ConstraintError`](#constrainterror) gerado durante o ajuste do
  modelo, de modo que chega ao comando como erro de carga. `novomodelo validate` o imprime
  com o rótulo de arquivo `scenarios/` e encerra com código `1`. `novomodelo run` o imprime sem
  o prefixo `I/O error: `, seguido de uma dica para executar `novomodelo validate`, e também
  encerra com código `1`.

#### Número de aberturas do grupo de ruído

**Quando ocorre:** Um estágio do estudo tem mais aberturas que o primeiro estágio do seu
grupo de ruído, a sequência de estágios adjacentes do estudo com o mesmo `season_id` cujas
datas de início caem em um mesmo ano civil
([Geração de cenários §2.3](/pt-br/math/scenario-generation/#23-arvore-de-aberturas)). As
contagens comparadas são as que a árvore de aberturas usa: `num_openings` depois dos
limites impostos por um conjunto de janelas históricas e por uma biblioteca externa de
cenários (os avisos de limitação da aba Notas de implementação de
[Geração de cenários](/pt-br/math/scenario-generation/#implementacao-no-novo-modelo)),
de modo que um limite aplicado apenas ao primeiro estágio pode provocá-la. A verificação
ocorre antes do sorteio de qualquer ruído. A mensagem nomeia os dois estágios:

{/* quoted from source: crates/novomodelo-stochastic/src/tree/generate.rs:160-187 and crates/novomodelo-stochastic/src/error.rs:28 at novomodelo v0.20.0 */}

```text
insufficient data: stage {dst_id} has {k_dst} openings but shares a noise group with stage {src_id}, which has {k_src}; a stage cannot have more openings than the first stage of its noise group: lower num_openings of stage {dst_id} in stages.json to {k_src}
```

Este é um erro do modelo estocástico. `novomodelo validate` o imprime depois do prefixo
`scenarios/inflow_history.parquet: stochastic error: ` e encerra com código `1`.
`novomodelo run` o imprime como `error: stochastic error: insufficient data: stage …`,
com a dica do validate, e encerra com código `1`.

**Resolução:** Reduza o `num_openings` do estágio indicado em `stages.json` para a
contagem que a mensagem informa. Quando um limite reduziu a contagem do primeiro estágio,
mais janelas históricas ou mais cenários externos para esse estágio também eliminam a
recusa. Um estágio posterior com menos aberturas que o primeiro é aceito e copia as
primeiras delas.

#### Arquivo da árvore de aberturas ausente

**Quando ocorre:** `training.scenario_source.openings` é `{"source": "file"}`
e `scenarios/noise_openings.parquet` está ausente. A fase de preparação estocástica
de `novomodelo validate` é interrompida com código de saída `2`, assim como `novomodelo run`, e, com `--json`, a `phase` do erro é
`StochasticPreparationError`. A mensagem é:

{/* quoted from source: crates/novomodelo-sddp/src/setup/stochastic_pipeline.rs:86-96 at novomodelo v0.20.0 */}

```text
openings source is 'file' but the conventional scenarios/noise_openings.parquet is absent
```

**Exemplo:** `novomodelo validate` imprime a mensagem dentro de uma linha de erro de E/S. O
rótulo `scenarios/` e a expressão `I/O error:` são a forma como esta fase reporta um
arquivo ausente, e `<case>` representa o caminho do diretório do seu caso:

{/* capture: novomodelo validate nofile 2>&1 | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nofile; config.json re-written with 2-space indentation, simulation.enabled false, training.scenario_source gains openings with source file, and no scenarios/noise_openings.parquet; run with NO_COLOR=1, exit code 2; the Validation summary line, which carries the temporary path, is not quoted; the fixture directory name nofile in the error lines is replaced by <case>) */}

```text
error: scenarios/: I/O error: I/O error reading <case>/scenarios/noise_openings.parquet: openings source is 'file' but the conventional scenarios/noise_openings.parquet is absent
error: I/O error in <case>/scenarios/noise_openings.parquet: openings source is 'file' but the conventional scenarios/noise_openings.parquet is absent
  -> check that the path exists and you have read/write permissions
```

**Solução:** Forneça `scenarios/noise_openings.parquet` ou declare `openings`
como `{"source": "generated"}`. [Configuração](/pt-br/running/configuration/#training)
descreve a chave `openings`.

### `GenericConstraintValidationError`

**Severidade:** Erro

**Quando ocorre:** Uma falha durante a preparação das restrições genéricas, incluindo
a expansão de expressões, a resolução de parâmetros e a montagem das folgas. Rótulo de arquivo:
`constraints/`.

Um **escalar `@parameter` não resolvido** — um parâmetro de restrição genérica
declarado em `constraints/generic_parameters.json` que não tem valor para um
período sazonal, estágio ou patamar de que o estudo precisa — falha aqui, durante `novomodelo validate`.
Um `@name` que nenhum arquivo declara é reportado na carga; veja
[Expressão de restrição genérica rejeitada](#expressao-de-restricao-generica-rejeitada).
O parâmetro é recusado com uma das mensagens:

{/* quoted from source: ResolvedParametersError and PerStageBlockCoverageIssue in crates/novomodelo-sddp/src/policy/resolved_parameters.rs at novomodelo v0.20.0 */}

```text
parameter '<name>': no seasonal value for season_id=<season> (needed by stage <t>)
parameter '<name>': PerStageBlock cell (stage=<s>, block=<b>) is not covered by any triple
parameter '<name>': PerStageBlock cell (stage=<s>, block=<b>) lies outside the study's (stage, block) grid
parameter '<name>': no specific productivity (`ρ_esp`) available for hydro_id=EntityId(<id>)
```

`<t>` e `<s>` são posições de estágios do estudo a partir de 0, e `<b>` é um índice de patamar
a partir de 0. Um parâmetro `seasonal` precisa de um valor para o período sazonal de cada estágio
do estudo, e um parâmetro `per_stage_block`, de um valor para cada patamar de cada estágio
do estudo. Um parâmetro `computed` com a tag `specific_productivity` precisa de um
`specific_productivity_mw_per_m3s_per_m` para sua hidrelétrica em cada estágio do estudo,
proveniente de `system/hydro_energy_productivity.parquet` ou de `system/hydros.json`.

Um **valor resolvido não finito** também falha aqui. Um coeficiente, um limite ou um
parâmetro `expression` que depende de parâmetros escalares é avaliado em cada
estágio e patamar em que está ativo, e um cujo valor não seja finito ali (uma
divisão por um parâmetro nulo naquele estágio, por exemplo) é recusado
com uma das mensagens:

```text
generic constraint <id> '<name>': the coefficient of <variable> resolves to the non-finite value <value> at stage <s>, block <b>
generic constraint <id> '<name>': the upper bound resolves to the non-finite value <value> at stage <s>, block <b>
parameter '<name>': expression resolves to the non-finite value <value> at stage <s>, block <b>
```

A mensagem de limite nomeia o limite inferior ou o superior; um parâmetro `expression`
é verificado mesmo que nenhuma restrição o leia. Uma constante formada apenas por
números que divide por zero é, em vez disso, recusada na carga; veja
[Expressão de restrição genérica rejeitada](#expressao-de-restricao-generica-rejeitada).

**Exemplo:** Um parâmetro `seasonal` cujo único valor é para o período sazonal `5`, em um caso
sem definições de períodos sazonais:

{/* capture: novomodelo validate sea | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sea; constraints/generic_parameters.json added holding one seasonal parameter, id 1, name sea, values [[5, 1.0]]; constraints/generic_constraints.json added holding one constraint, id 0, name cap, expression @sea * hydro_storage(0), slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 0, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
constraints/: configuration validation error: parameter 'sea': no seasonal value for season_id=0 (needed by stage 0)
```

Esta fase também reporta falhas de **conversão de energia** de uma usina hidrelétrica calculadas
na mesma etapa — uma tabela de montante (VHA) em `system/hydro_geometry.parquet` que
não pode ser construída, ou uma queda equivalente média da faixa útil não positiva — para qualquer
usina com geometria VHA e produtibilidade específica, independentemente de seu
modelo de geração e de o caso declarar ou não restrições genéricas (veja
[Modelos de função de produção hidrelétrica §4.3](/pt-br/math/hydro-production-models#43-produtibilidade-media-na-faixa-util)).
Um valor de `equivalent_productivity_mw_per_m3s` em
`system/hydro_energy_productivity.parquet` define apenas a produtibilidade no ponto de
referência e não evita a verificação da queda média; um valor de
`integrated_equivalent_productivity_mw_per_m3s` para o estágio a evita, e
a mensagem nomeia essa coluna.

### `BoundaryReconciliationError`

**Severidade:** Erro

**Quando ocorre:** Uma falha ao reconciliar uma política de fronteira injetada com
o estudo atual. Rótulo de arquivo: `policy.boundary`.

**Exemplo:** Um checkpoint de fronteira gravado por outro software ou outra versão reporta a mensagem de
[`PolicySoftwareMismatch`](#policysoftwaremismatch) prefixada com o rótulo de arquivo:

{/* quoted from source: crates/novomodelo-cli/src/commands/validate.rs:170-176, crates/novomodelo-sddp/src/validate_phases.rs:444-453, crates/novomodelo-sddp/src/error.rs:105-110 and 129-136 and crates/novomodelo-io/src/output/software.rs:13-18 at novomodelo v0.20.0 — not capturable (needs a checkpoint written by another software or version) */}

## Erros de carga da política

Uma carga da política recusa um checkpoint que não se ajusta ao estudo que o carrega. Duas
cargas geram esses erros: uma **carga da FCF completa** do checkpoint em `policy.path`
(execuções com partida a quente (warm-start), retomada e somente simulação) e uma **carga de fronteira** do
checkpoint em `policy.boundary.path`. `novomodelo run` e os pontos de entrada Python
os geram antes do início do treinamento (training) ou da simulação. `novomodelo validate` executa ambas as cargas que a execução aplicaria, lendo o checkpoint da FCF completa de `<output dir>/<policy.path>` (`--output`, padrão `<CASE_DIR>/output/`), e encerra com código `1` em toda recusa que `novomodelo run` faria. Esses erros não são
variantes de `LoadError`, e a carga do caso não os retorna.

Uma carga da FCF completa executa suas verificações na ordem indicada em
[Ordem das verificações](/pt-br/running/policy-management/#ordem-de-verificacao). As verificações de uma carga
de fronteira estão listadas em
[Requisitos de compatibilidade](/pt-br/running/policy-management/#requisitos-de-compatibilidade).
Um `manifest.bin` cujo `format_version` não seja `4` falha antes dessas verificações:
`failed to read policy checkpoint: serialization error for entity checkpoint_manifest: unsupported checkpoint manifest format_version {n}; expected 4; re-run the program that produced it with novomodelo {running}; for a converted boundary policy, convert it again`, código de saída `1`.

### `PolicySoftwareMismatch`

**Severidade:** Erro

**Quando ocorre:** Uma carga da FCF completa ou uma carga de fronteira lê um checkpoint cujo
`manifest.bin` registra outro software ou outra versão que não a do build em execução: os campos
`software` e `software_version` são comparados de forma exata, de modo que um build de patch ou
pré-lançamento diferente também é recusado. Um checkpoint cujo `format_version` não seja
`4` é recusado antes desta verificação
([Como uma falha de carga da política chega até você](#como-uma-falha-de-carga-da-politica-chega-ate-voce)).
[Filtro de versão](/pt-br/running/policy-management/#verificacao-de-versao) enuncia a regra.

**Mensagem:**

{/* quoted from source: crates/novomodelo-sddp/src/error.rs:105-110 and 129-136 and crates/novomodelo-io/src/output/software.rs:13-18 at novomodelo v0.20.0 — not capturable (needs a checkpoint written by another software or version) */}

```text
policy was written by {writer}, but this is novomodelo {running}; a policy loads only in the software and version that wrote it: re-run the program that produced it with novomodelo {running}; for a converted boundary policy, convert it again
```

`{writer}` é `<software> <version>`, `<software>, which recorded no version`,

### Recusas de retomada

**Quando ocorre:** Uma carga com `policy.mode = "resume"` constata que o checkpoint não pode dar continuidade à execução interrompida
de forma idêntica. As cinco verificações são executadas após as verificações estruturais, na ordem de
[Recusas de retomada](/pt-br/running/policy-management/#recusas-da-retomada), e a primeira que falha interrompe a execução com
a fase `ResumeIncompatible`. Uma carga `warm_start` do mesmo checkpoint não faz nenhuma dessas verificações.

**Mensagens:**

{/* quoted from source: crates/novomodelo-sddp/src/policy/full_fcf_load.rs:244-327 at novomodelo v0.20.0 */}

```text
resume needs the forward-pass count the checkpoint was written with: training.selection.forward_passes is {run} here and {stored} in the checkpoint; set it to {stored} or continue with policy.mode = warm_start
resume needs the trial-state history of training.cut_selection.selection.method = level1; the checkpoint holds none (it was written by a run without level1 or exports.states); continue with policy.mode = warm_start or retrain
resume needs every trial state of the run under training.cut_selection.selection.method = level1 without lookback_iterations; the checkpoint holds those of the last {stored} iterations only; set lookback_iterations to at most {stored} or continue with policy.mode = warm_start
resume needs the trial states of the last {window} iterations (training.cut_selection.selection.lookback_iterations = {window}); the checkpoint holds those of the last {stored} iterations only; set lookback_iterations to at most {stored} or continue with policy.mode = warm_start
resume needs the binding counters read by {reader}; the checkpoint holds none (it was written by a run without max_active_per_stage or the dynamic method); continue with policy.mode = warm_start or retrain
resume needs a whole checkpoint; the checkpoint's per-scenario bases are not whole (it was written when a run failed); resume from the last whole checkpoint or continue with policy.mode = warm_start
```

`{reader}` é `training.cut_selection.max_active_per_stage` quando o limite está definido, e
`training.cut_selection.selection.method = dynamic` caso contrário. A retomada de uma execução que declarou `policy.boundary`
também é recusada quando as linhas de fronteira diferem das do checkpoint; a mensagem é citada em
[Retomada com fronteira](/pt-br/running/policy-management/#retomada-com-fronteira).

`novomodelo validate` rotula cada mensagem com `<output dir>/<policy.path>: configuration validation error: `. Por exemplo,
a retomada, com `training.selection.forward_passes` igual a `2`, de um checkpoint gravado com `1` reporta:

{/* capture: novomodelo validate rs | novomodelo   v0.20.0 | binary: novomodelo-cli sha256 ae88209f | case: 1dtoy (novomodelo init --template 1dtoy) trained with iteration_limit 3 and simulation disabled, then training.selection.forward_passes 2 and policy.mode resume; run with NO_COLOR=1, exit code 1; the Validation summary line and the error: prefix are not quoted */}

```text
rs/output/./policy: configuration validation error: resume needs the forward-pass count the checkpoint was written with: training.selection.forward_passes is 2 here and 1 in the checkpoint; set it to 1 or continue with policy.mode = warm_start
```

**Classe Python:** `PolicyIncompatibleError`, com o prefixo de mensagem `policy validation error: `.

**Solução:** Siga a alternativa indicada na mensagem ou continue com `policy.mode = "warm_start"`.

**Quando ocorre:** Uma execução com o método `dynamic` que simula com `simulation.cut_set = "all"` carrega uma

## Validação do perfil do solver

As sobrescritas de perfil do solver por fase (`training.solver.backward`,
`training.solver.forward`, `simulation.solver`) são validadas em relação à
matriz de suporte do backend compilado na montagem do estudo, antes que qualquer PL de estágio seja
construído, em todos os processos MPI; cada rejeição abaixo é um erro de configuração com
mensagem própria.

`novomodelo validate` executa essas verificações em todos os casos: reporta uma rejeição com a fase
[`StudySetupError`](#studysetuperror) (`config.json: configuration validation error: …`), ou
[`BoundaryReconciliationError`](#boundaryreconciliationerror) com `policy.boundary` configurado.
`novomodelo run` recusa o caso antes do treinamento. Ambos encerram com código `1`.

### Backend CLP: toda sobrescrita é rejeitada

**Quando ocorre:** Um binário compilado com o backend CLP (veja
[Instalação — Build com CLP](/pt-br/getting-started/installation#compilacao-com-clp))
rejeita de imediato qualquer campo de sobrescrita do perfil do solver — as opções próprias
do CLP não foram avaliadas em relação a esses campos, de modo que o novomodelo se recusa a
aplicar silenciosamente a ele um valor pensado para o HiGHS. Um bloco `"solver": {}` vazio e
a ausência do bloco `solver` são ambos válidos; apenas um campo efetivamente *definido*
dispara o erro. Quando um perfil define mais de um campo, apenas o primeiro
campo na ordem de declaração é nomeado, de modo que corrigir um campo por vez revela
um erro por ciclo de correção, em vez de um relatório combinado.

**Exemplo:**

```
solver profile field "dual_edge_weight" for phase "backward" is unsupported on backend "clp": rejected until CLP is re-measured
```

Para `primal_feasibility_tolerance`, o token do campo traz também o
valor definido:

```
solver profile field "primal_feasibility_tolerance" (1e-7) for phase "forward" is unsupported on backend "clp": rejected until CLP is re-measured
```

`"<phase>"` é `forward`, `backward` ou `simulation`.

**Solução:** Remova o campo de sobrescrita de `config.json` em um binário compilado com CLP
ou passe para o backend padrão HiGHS, se a sobrescrita for necessária.

### Backend HiGHS: seis verificações de intervalo por campo

O backend padrão (`highs`) aceita todos os campos do perfil do solver. Os enums
fechados (`dual_edge_weight`, `scale`, `price`, `presolve`) e `use_warm_start`
são sempre válidos — toda variante é verificada na leitura de `config.json`,
de modo que não há verificação de intervalo separada em tempo de execução para eles. Os
seis campos numéricos restantes têm o intervalo verificado na montagem do estudo; cada falha nomeia o
campo, o valor rejeitado e a fase (`forward` / `backward` /
`simulation`) cujo perfil o definiu.

| Campo | Regra | Mensagem |
| --- | --- | --- |
| `primal_feasibility_tolerance` | deve ser finito | `unsupported primal_feasibility_tolerance {value} for backend "highs" in phase "{phase}": value must be finite` |
| `dual_feasibility_tolerance` | deve ser finito e `>= 0.0000000001` | `unsupported dual_feasibility_tolerance {value} for backend "highs" in phase "{phase}": value must be finite and >= 0.0000000001` |
| `simplex_update_limit` | deve ser `<= 2147483647` | `unsupported simplex_update_limit {value} for backend "highs" in phase "{phase}": value must be <= 2147483647` |
| `cost_perturbation` | deve ser finito e `>= 0` | `unsupported cost_perturbation {value} for backend "highs" in phase "{phase}": value must be finite and >= 0` |
| `factor_pivot_threshold` | deve estar em `[0.0008, 0.5]` | `unsupported factor_pivot_threshold {value} for backend "highs" in phase "{phase}": value must be in [0.0008, 0.5]` |
| `steepest_edge_devex_fallback_threshold` | deve ser finito e `>= 1.0` | `unsupported steepest_edge_devex_fallback_threshold {value} for backend "highs" in phase "{phase}": value must be finite and >= 1.0` |

`0.0000000001` é 1e-10 escrito por extenso; `2147483647` é o maior inteiro
de 32 bits com sinal; `[0.0008, 0.5]` é o próprio intervalo de limiar de pivoteamento aceito pelo HiGHS.

**Solução:** Ajuste o campo problemático para que atenda à regra da tabela.
`{phase}` na mensagem identifica qual de `training.solver.backward`,
`training.solver.forward` ou `simulation.solver` definiu o valor inválido.

## Erros de execução

{/* quoted from source: crates/novomodelo-cli/src/error.rs:121-140, 164-176 and 203-226 and crates/novomodelo-cli/src/commands/run/mod.rs:149-177 and 309-317 at novomodelo v0.20.0 */}

Uma falha durante `novomodelo run` imprime `error: {message}` no stderr, seguido de linhas de dica que dependem do código de saída:

- Código `1`, uma recusa encontrada durante a execução (por exemplo, uma divergência de `--threads`), acrescenta ``-> run `novomodelo validate <CASE_DIR>` for a full diagnostic report``.
- Código `2`, cuja mensagem é `I/O error in {context}: {source}`, acrescenta `-> check that the path exists and you have read/write permissions`.
- Código `3` acrescenta `-> check constraint bounds (hydros may have conflicting min/max storage)` e ``-> run `novomodelo validate <CASE_DIR>` for a full diagnostic report``.
- Código `4` acrescenta `-> this may indicate a software or environment problem` e `-> report this at https://github.com/ons-ccee-epe/novomodelo/issues`.

Com dois ou mais processos MPI, cada processo que falha (um rank MPI) imprime primeiro `rank {rank}:` em uma linha própria e depois as mesmas linhas, e o job é encerrado com o código de saída desse processo. Quando o rank 0 não consegue gravar as saídas da execução, todos os ranks encerram com o código do rank 0, e os demais imprimem `rank 0 failed to write the run outputs; failing on every rank in lockstep`. Um checkpoint que não se ajusta ao estudo é recusado antes do início do treinamento ou da simulação; veja [Erros de carga da política](#erros-de-carga-da-politica).

Um panic, uma falha interna, imprime sua mensagem no stderr e encerra com código `101`. Com dois ou mais processos MPI, o processo que entra em panic imprime em seguida `rank {rank}: panicked; aborting the MPI job` e aborta o job inteiro com código de saída `101`.

### Falhas do solver

Uma falha dentro de uma iteração de treinamento encerra o treinamento e sai com o código do seu erro: `3` para uma falha de PL ou do solver, `4` para uma falha de comunicação, `1` para uma recusa. Uma execução sem `--quiet` imprime antes `Training failed after {n} iterations. Partial outputs written to {dir}; the partial policy is in {policy}.` no stderr, em que `{policy}` é o diretório da política acrescido de `.partial`: uma execução que falha grava sua política parcial ao lado de `policy.path` e nunca substitui um checkpoint em `policy.path`. A execução também registra `ERROR training failed after {n} iterations: {error}` no stderr, inclusive com `--quiet`. Sob MPI, um processo que falha primeiro pode abortar o job antes que o processo raiz imprima essas linhas. As mesmas falhas de PL na simulação encerram com código `3`; veja [Falhas da simulação](#falhas-da-simulacao).

### Soluções que violam um limite de linha

Quando alguma solução de PL da execução devolveu uma solução primal ótima que viola um
limite de linha, `novomodelo run` imprime uma linha no stderr ao final da execução
(apenas no rank 0; `--quiet` não a suprime). A execução continua bem-sucedida e o código
de saída não muda:

```text
warning: LP solves returned a primal solution that misses a row bound by more than the primal feasibility tolerance plus 1e-11 of the row's magnitude: {n} of {m} (forward {f}, backward {b}, lower bound {l}, simulation {s}); per-stage counts are in the lp_row_violations column of solver/iterations.parquet
```

Uma linha é contada quando sua violação excede a tolerância de viabilidade primal do
solver mais `1e-11` vezes a magnitude da linha: a soma dos valores absolutos de seus
termos na solução devolvida, tomada como no mínimo 1. O `novomodelo.run` do Python
imprime o mesmo texto com o prefixo `novomodelo-python: `. Uma contagem acima de zero
significa que as saídas recalculadas a partir dessa solução (balanços, duais, cortes)
podem não fechar; reporte-a com o caso.
