Case loading reports errors in two groups: [validation report kinds](#validation-report-kinds)
(diagnostic categories collected while the case is validated) and
[load-failure kinds](#load-failure-kinds) (returned when a case fails to load). The page also
lists the policy-load errors a checkpoint refusal raises and the
[runtime errors](#runtime-errors) of a running `novomodelo run`.

## How these errors reach you

Novomodelo surfaces errors through four user-facing channels:

- **`novomodelo validate` human report** — errors print as `error:` prefixed lines; warnings (after a successful validation) print as `warning:` prefixed lines.
- **`novomodelo validate --json`** — on success, one JSON object on stdout: `{ configured, boundary_date, report }`, plus `policy_load: { mode, unused_stored_bases }` when the run would load a policy (`mode` `warm_start`, `resume` or `simulation_only`), with no `error` key; `configured` is `true` when `policy.boundary` is configured and the run applies it, which only a run that trains does, and `false` otherwise. On failure, those three keys are `null` and an `error` key holds `{ phase, message }`. The **`phase`** field is the name of the failing [`LoadError` variant](#load-failure-kinds), one of the six [preparation-phase kinds](#preparation-phase-kinds), or a policy-load kind (`WarmStartIncompatible`, `ResumeIncompatible`, `SimulationPolicyIncompatible`, or `IoError` for a checkpoint the OS refuses to read); it names a `LoadError` variant, a preparation kind or a policy-load kind, never the `ErrorKind` of a collected diagnostic. A case-load failure reports [`ConstraintError`](#constrainterror) in almost every case, because every per-file read, parse and schema failure and every validation rule is collected into one report; its `message` holds one `[<ErrorKind>] <file>[ (<entity>)]: <message>` line per collected error, joined by newlines (the `[ (<entity>)]` part appears only when the error names an entity). Warnings are not in the JSON. Only a missing case directory prints no JSON object; it reports on stderr and exits `2`.

  A case with no `policy.boundary` succeeds with:

  {/* capture: novomodelo validate --json case | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy case (novomodelo init --template 1dtoy case; unmodified; run with NO_COLOR=1, exit code 0) */}

  ```json
  {
    "configured": false,
    "boundary_date": null,
    "report": null
  }
  ```

  A hydro unit group that names a bus that does not exist fails with:

  {/* capture: novomodelo validate --json badref | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; system/hydros.json: hydro 0 unit group 0 bus_id changed from 0 to 99; run with NO_COLOR=1, exit code 1) */}

  ```json
  {
    "configured": null,
    "boundary_date": null,
    "report": null,
    "error": {
      "phase": "ConstraintError",
      "message": "[InvalidReference] system/hydros.json (Hydro 0 unit group 0): Hydro 0 unit group 0 references non-existent Bus 99 via field 'bus_id'"
    }
  }
  ```

- **`novomodelo.io.validate(...)` (Python)** — returns `{ valid, errors: [{ kind, message }], warnings: [{ kind, message, file, entity }] }`. `errors` holds at most one entry: none when `valid` is true, one on failure. Its `kind` is the same string as the CLI `phase`, and its `message` is the error's full text, which for a case-load failure starts `constraint violation: `. For a missing case directory, where the CLI prints no JSON object, Python still returns an `IoError` entry. Each warning's `kind` is the `ErrorKind` name.
- **`novomodelo.errors` Python exception classes** — case loading raises `ValidationError` or `CaseIoError`; a policy-load refusal raises the class of its error: `PolicyIncompatibleError` for a refused checkpoint or one that is missing or cannot be decoded, `CaseIoError` for a checkpoint read the operating system refuses, and `ValidationError` for a missing policy directory or a refused boundary reconciliation (see [Policy-load errors](#policy-load-errors)). See [`novomodelo.errors`](/en/reference/python-api/#novomodeloerrors) for the full hierarchy and [Python Quickstart — Error Handling](/en/getting-started/python-quickstart/#error-handling) for catching these classes.

Policy-load failures use different exit codes and exception classes; see [How a policy-load failure reaches you](#how-a-policy-load-failure-reaches-you). For the cause and fix of the failures a study commonly meets, see [Troubleshooting](/en/running/troubleshooting/).

## Validation report kinds

Each error a case load collects prints as one report line, `[<Kind>] <file> (<entity>): <message>`. The
`(<entity>)` part appears only when the error names an entity, and `<Kind>` is one of the values below.

`novomodelo validate` prints each error as `error: ` followed by its report line, and exits `1` when any error is
present. `novomodelo run` prints `error: constraint violation: ` followed by the same lines. After a successful
validation, `novomodelo validate` prints each warning as a `warning:` line of the form `<file> (<entity>): <message>`
after the `Valid case: ...` line, without the bracketed kind, and `novomodelo.io.validate` (Python) returns the
warnings, each with its kind, in its `warnings` array.
A warning of the policy load the run would apply prints after them as
`warning: <output dir>/<policy.path>: <message>`, names no entity, and counts in the `Validation:` line.

The three warning kinds (`UnusedEntity`, `ModelQuality`,
`SemanticAmbiguity`) never stop a run, and neither does a `BusinessRuleViolation` that `novomodelo validate` prints as a `warning:` line; every other report line is an error that must be resolved
before the case loads.

`WarmStartIncompatible`, `ResumeIncompatible` and `SimulationPolicyIncompatible` are not report-line kinds:
each names a refused policy load, as the `phase` value, and that load's warnings: `WarmStartIncompatible` for a
`policy.mode = "warm_start"` load in a run that trains, `ResumeIncompatible` for a `policy.mode = "resume"`
load in a run that trains, and `SimulationPolicyIncompatible` for the load of a simulation-only run, whatever its
`policy.mode`; see their entries below.

### `FileNotFound`

**Severity:** Error

**When it occurs:** A file that is required by the case structure is missing
from the case directory. Emitted when the required files are checked, once for
each of them that is not found on disk.

**Example:** A case directory without `system/hydros.json`:

{/* capture: novomodelo validate fnf1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy fnf1; system/hydros.json deleted; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted, the error: prefix is not quoted and only the first of the two [FileNotFound] lines is quoted) */}

```text
[FileNotFound] system/hydros.json: required file 'system/hydros.json' not found in case directory
```

A case directory without `system/buses.json` gives two
`[FileNotFound]` lines: the first reports the missing required file, the second
the failed read of it:

{/* capture: novomodelo validate nobus | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nobus; system/buses.json deleted; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[FileNotFound] system/buses.json: required file 'system/buses.json' not found in case directory
[FileNotFound] system/buses.json: No such file or directory (os error 2)
```

A case directory with neither `boundary_conditions.json` nor the
deprecated `initial_conditions.json` gives one `[FileNotFound]` line for the pair:

{/* quoted from source: resolve_boundary_source in crates/novomodelo-io/src/validation/structural.rs at novomodelo commit 95318d3ba90a */}

```text
[FileNotFound] boundary_conditions.json: required file 'boundary_conditions.json' (or the deprecated 'initial_conditions.json') not found in case directory
```

**Resolution:** Create the missing file in the correct subdirectory. The required files are: `config.json`, `penalties.json`, `stages.json`,
`boundary_conditions.json` (or the deprecated `initial_conditions.json`), `system/buses.json`, and `system/hydros.json`.
To create `boundary_conditions.json`, see the
[boundary conditions page](/en/reference/case-format/boundary-conditions/#boundary_conditionsjson).

### `ParseError`

**Severity:** Error

**When it occurs:** A file exists and was read but could not be parsed —
invalid JSON syntax, an unreadable Parquet header, a missing required field, or
an unknown enum variant in a tagged JSON union. Emitted when a file is parsed and the
parse fails. `config.json` and
`system/hydros.json` report a missing field or an unknown variant as a
[`SchemaViolation`](#schemaviolation) instead, and
`system/hydro_production_models.json` does so for an unknown variant.
A `training.stopping_rules` entry that carries a field that belongs to a *different* rule `type` — for example,
`seconds` (a `time_limit` field) on a `bound_stalling` rule — is also rejected
as a `ParseError` with an `unknown field` message.
An unknown key in `boundary_conditions.json`, or in an entry of a `post_study_*` list in `stages.json`, is also a `ParseError`; see the
[boundary conditions page](/en/reference/case-format/boundary-conditions/#boundary_conditionsjson) and the
[post-study calendars](/en/reference/case-format/stages/#post-study-calendars).

**Display format:**

```
parse error in {path}: {message}
```

This format reaches you only for a parse error raised after the validation report is complete (see [Load-failure kinds](#load-failure-kinds)); a parse failure in the report prints as the `[ParseError]` line shown in the examples below.

**Fields:**

| Field     | Description                                     |
| --------- | ----------------------------------------------- |
| `path`    | Path to the file that failed to parse           |
| `message` | Human-readable description of the parse failure |

**Example:**

{/* capture: novomodelo validate trunc | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy trunc; stages.json cut off after the opening bracket of the stages array, leaving one line that ends in a newline; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] stages.json: parse error: EOF while parsing a list at line 2 column 0
```

A missing required field, here a constraint entry without `slack`:

{/* capture: novomodelo validate gcnoslack | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy gcnoslack; constraints/generic_constraints.json added as a single line holding a constraints array with one constraint, id 0, name cap, expression hydro_storage(0), and no slack object; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] constraints/generic_constraints.json: parse error: missing field `slack` at line 1 column 69
```

A `bound_stalling` rule that carries `seconds`, a `time_limit` field:

{/* capture: novomodelo validate secs | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy secs; config.json re-written with 2-space indentation, training.stopping_rules gains a bound_stalling rule with iterations 5, tolerance 0.01 and seconds 3; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] config.json: parse error: unknown field `seconds`, expected `iterations` or `tolerance` at line 19 column 5
```

**Resolution:** Fix the syntax error in the indicated file. Use a JSON linter
or Parquet viewer to find the exact location. For JSON files, common causes are
trailing commas, missing quotation marks, or mismatched braces. For a
`missing field` message, add the field it names. For an `unknown
field` message inside a `stopping_rules` entry, remove the field that does not
belong to that entry's `type`, or move it to an entry whose `type` declares it.

**See also:** an `anticipated_config` object in `system/thermals.json` that matches neither accepted
lead shape is collected under this kind — see
[Invalid anticipated-thermal lead](#invalid-anticipated-thermal-lead).

#### Unknown field in a generic-constraint entry

**When it occurs:** Each generic-constraint object accepts exactly five fields
(`id`, `name`, `description`, `expression`, `slack`); any other key is rejected
as a `ParseError` with an `unknown field` message.

**Fields:**

| Field     | Description                                                                             |
| --------- | ---------------------------------------------------------------------------------------- |
| `path`    | Always `constraints/generic_constraints.json`                                            |
| `message` | An "unknown field" message, naming the offending key and the five accepted field names |

**Example:** A constraint object with an extra `type` key:

{/* capture: novomodelo validate gcunk | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy gcunk; constraints/generic_constraints.json added, written with 2-space indentation, holding a constraints array with one constraint, id 0, name cap, expression hydro_storage(0), slack enabled false, plus the extra key type set to upper; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[ParseError] constraints/generic_constraints.json: parse error: unknown field `type`, expected one of `id`, `name`, `description`, `expression`, `slack` at line 10 column 12
```

**Resolution:** Remove the unknown field, leaving
only the five accepted keys. See [Generic Constraints](/en/reference/generic-constraints/) for the grammar.

### `SchemaViolation`

**Severity:** Error

**When it occurs:** A file parses successfully but a field fails a schema
constraint: a required field is missing from `config.json` or `system/hydros.json`, or a required Parquet column is missing (a missing field in any other JSON file is a [`ParseError`](#parseerror)), a Parquet file carries a column its table does not list, a value is outside its valid range
(e.g., negative capacity, non-positive penalty cost, a reservoir whose
`min_storage_hm3` exceeds `max_storage_hm3`, or a stage whose `num_openings` is
0), a field contains an unexpected type, or an entity `id` appears twice in a
registry file such as `system/buses.json`. Emitted when the fields of a parsed
file are checked. A `post_study_*` calendar in `stages.json` with an unparsable date, an `end_date` not after its `start_date`, a repeated `start_date`, or an `id` that breaks the calendar's id rules is also a `SchemaViolation`; see the
[post-study calendars](/en/reference/case-format/stages/#post-study-calendars) and the
[boundary conditions page](/en/reference/case-format/boundary-conditions/#boundary_conditionsjson).

**Example:**

A negative penalty cost:

{/* capture: novomodelo validate negdef | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy negdef; system/buses.json: deficit segment 0 cost changed from 7500.0 to -100.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/buses.json: field buses[0].deficit_segments[0].cost: penalty value must be > 0.0, got -100
```

A reservoir whose minimum storage exceeds its maximum:

{/* capture: novomodelo validate resv | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy resv; system/hydros.json: hydro 0 reservoir min_storage_hm3 changed from 0.0 to 800.0 and max_storage_hm3 from 1000.0 to 500.0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/hydros.json: field hydros[0].reservoir: min_storage_hm3 (800) must be <= max_storage_hm3 (500)
```

A stage with no openings:

{/* capture: novomodelo validate nop | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nop; stages.json: stage 0 num_openings changed from 10 to 0; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] stages.json: field stages[0].num_openings: num_openings must be > 0
```

A `config.json` without `training.selection`:

{/* capture: novomodelo validate nosel | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nosel; config.json re-written with 2-space indentation, training.selection removed; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] config.json: field training.selection: a forward-pass count is required via training.selection
```

Two buses that share an `id` in `system/buses.json`:

{/* capture: novomodelo validate dupbus | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy dupbus; system/buses.json: bus 0 duplicated as a second entry; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] system/buses.json: field buses[1].id: duplicate id 0 in buses array
```

**Resolution:** Correct the value in the indicated field. Field paths use
dot-notation and zero-based array indices. Consult the
[Case Format](/en/reference/case-format/) page for valid ranges and required fields.
For storage bounds, ensure `min <= max`. For opening counts, ensure `num_openings >= 1`.
For `config.json`, `training.selection` (for example
`{ "method": "sampled", "forward_passes": 192 }`) and `training.stopping_rules`
are mandatory keys with no default when absent. An absent `training.selection` is
reported with the message `a forward-pass count is required via training.selection`; add the key to `config.json`.

**See also:** a `constraints/hydro_bounds.parquet` spillage-band inversion or
non-negativity rejection is collected under this kind during a full case
load — see
[Spillage-band inversion](#spillage-band-inversion).
Two of the four failures of
[Invalid anticipated-thermal lead](#invalid-anticipated-thermal-lead) print `[SchemaViolation]` lines; the
other two print `[ParseError]` and `[BusinessRuleViolation]` lines. A case load prints every schema failure
as a `[SchemaViolation]` line; the `schema error in <path>, field <field>: <message>` form is the display
format of [`SchemaError`](#schemaerror), which reaches you only for a load error raised after the report is
complete.

A generic constraint's `slack` object is checked under this kind too, on the
field `constraints[<i>].slack.penalty` or `constraints[<i>].slack.penalty_basis`:
an enabled slack needs a positive `penalty` and a `penalty_basis`, and a
disabled slack carries neither. The missing-basis message names the choice:

{/* quoted from source: resolve_slack in crates/novomodelo-io/src/constraints/generic.rs at novomodelo v0.22.0 */}

```text
slack.enabled is true but slack.penalty_basis is absent: use "per_hour" for a row in MW or m³/s, "per_unit" for a row in MWh or hm³
```

The other slack messages:

```text
slack.enabled is true but slack.penalty is absent
slack.penalty must be > 0.0 when enabled, got {value}
slack.penalty is set but slack.enabled is false
slack.penalty_basis is set but slack.enabled is false
```

A `penalty_basis` other than `per_hour` or `per_unit` is a [`ParseError`](#parseerror)
(`unknown variant`). See
[Generic Constraints — Penalty basis](/en/reference/generic-constraints/#penalty-basis).

A computed FPHA's fit range in `system/hydro_production_models.json` is checked
under this kind too: an `fpha_config.spillage_fit_max_m3s` or
`fpha_config.turbined_fit_max_m3s` that is not a finite number above `0` is
refused on the field
`production_models[<i>].stage_ranges[<j>].fpha_config.<name>` (or
`production_models[<i>].seasons[<j>].fpha_config.<name>`):

{/* quoted from source: validate_fit_maxima in crates/novomodelo-io/src/extensions/production_models.rs at novomodelo v0.22.0 */}

```text
<name> must be finite and > 0.0, got <value> for hydro_id <id>
```

#### Configuration load rules

`config.json` loading refuses these values; each prints a `[SchemaViolation] config.json: field <field>: <message>` line, and both commands exit `1`.

{/* quoted from source: crates/novomodelo-io/src/config/mod.rs:187-196 and 424-451, crates/novomodelo-io/src/config/policy.rs:124-133 and 248-257 at novomodelo v0.22.0 */}

| Rule                                                           | Field                                      | Message                                                                                                                                              |
| -------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| No `iteration_limit` rule                                      | `training.stopping_rules`                  | `must contain an iteration_limit rule`                                                                                                               |
| `interval_iterations` absent or below 1, checkpointing enabled | `policy.checkpointing.interval_iterations` | `must be at least 1 when policy.checkpointing.enabled is true; got {found}`                                                                          |
| `policy.path` naming no subdirectory (`""`, `.`, `..`)         | `policy.path`                              | `"{value}" names the output directory or one of its ancestors, which a checkpoint write would replace; choose another directory, such as "./policy"` |

`{found}` is `no value` when the key is absent and `0` otherwise. `{value}` is the configured `policy.path`.

#### Refused policy.path

**When it occurs:** `policy.path` is resolved against `--output`, and a link is checked where it sits and where it points. The path is refused when it names the output directory or one of its ancestors, or names, contains or lies inside a directory a run rewrites or removes. [Configuration — `policy`](/en/running/configuration/#policy) states the rule. In a case that trains, the path is refused too when it (for a link, its target) or its `.staging` or `.previous` sibling is not a directory or holds an entry no checkpoint writer leaves there; the message is `refusing to write a checkpoint: …`, quoted under [Policy Management — Checkpoint Directory Contents](/en/running/policy-management/#checkpoint-directory-contents).

{/* quoted from source: crates/novomodelo-io/src/config/policy.rs:248-289 at novomodelo v0.22.0 */}

```text
"{value}" names the output directory or one of its ancestors, which a checkpoint write would replace; choose another directory, such as "./policy"
"{value}" {relation} {dir}, which a run removes whole before writing its outputs; choose a directory that neither contains nor lies inside it, such as "./policy"
"{value}" {relation} {dir}, which holds files a run writes and a checkpoint write would replace; choose a directory that neither names nor contains it, such as "./policy"
```

#### Named-expression inlining term budget exceeded

**When it occurs:** Inlining substitutes every `@name` reference with its
referenced expression and folds the result into one coefficient per variable.
An acyclic but exponentially-expanding declaration is caught once the
expansion would exceed 100,000 coefficient operations, far above any
legitimately authored expression, aborting the blow-up before it
materializes. A doubling chain whose links are scaled by a scalar
parameter, `@e_k = @a * @e_{k-1} + @e_{k-1}`, hits the cap; a chain of plain
self-additions, `@e_k = @e_{k-1} + @e_{k-1}`, folds to one term per variable
and stays under it. The cap applies only when a constraint (or another
expression) actually references the runaway declaration — declaring it
without referencing it is a cheap existence check, not an expansion.

**Fields:**

| Field     | Description                                                                     |
| --------- | --------------------------------------------------------------------------------|
| `path`    | Always `constraints/generic_constraints.json`                                   |
| `field`   | `constraints[i].expression` (or the referencing expression's own field)          |
| `message` | `` `@<name>`: named-expression reference "@<name>" expands to more than 100000 coefficient operations; this indicates an exponential reference pattern (e.g. a doubling chain "@e = @prev + @prev")`` when the expansion runs inside a referenced named expression, or `` `<fragment>`: expression expands to more than 100000 coefficient operations`` when it runs in the referencing expression's own text, for example `@e15 + @e15` |

**Example:**

{/* capture: novomodelo validate nbudget | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nbudget; constraints/generic_parameters.json added, written with 2-space indentation, holding one constant scalar parameter, id 1, name a, value 0.5; constraints/generic_constraints.json added, written with 2-space indentation, holding one constraint, id 0, name c0, expression @e60, slack disabled, and 61 named expressions, e0 = hydro_storage(0) and e<k> = @a * @e<k-1> + @e<k-1> for k 1 to 60; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 0, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
[SchemaViolation] constraints/generic_constraints.json: field constraints[0].expression: `@e60`: named-expression reference "@e60" expands to more than 100000 coefficient operations; this indicates an exponential reference pattern (e.g. a doubling chain "@e = @prev + @prev")
```

**Resolution:** Rewrite the named-expression chain to grow linearly rather
than by repeated self-addition — e.g. accumulate into one running expression
instead of doubling a reference at each step. See
[Generic Constraints](/en/reference/generic-constraints/) for the `@name`
composition rules.

#### Generic-constraint expression rejected

**When it occurs:** An expression in `constraints/generic_constraints.json`
(`constraints[i].expression`, or `expressions[i].expression` for a named
expression's own definition) that the grammar or its linearity rule refuses.
Every message starts with the offending fragment in backticks, as in
`` `@zz`: unknown name … ``; a problem at the very end of the text ends in
`(at the end of the expression)` instead.

| Mistake                                                            | Message after the quoted fragment                                                                                                              |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| An `@name` declared neither as a scalar parameter nor as a named expression | `unknown name "@<name>": no scalar parameter or named expression with this name was declared`                                      |
| A product of two terms that both hold LP variables                 | `product of LP variables is not linear`; when a factor is a named expression, followed by `("@<name>" is the named expression at expressions[<i>], which contains LP variables)` |
| A division by a term that holds an LP variable                     | `division by an expression containing LP variables`                                                                                             |
| A constant built from numbers that divides by zero                 | `division by zero`                                                                                                                              |
| A numeric literal too large to represent                           | `numeric literal <text> is not finite`                                                                                                          |
| A constant part in an expression with no relational operator       | `an expression without a relational operator cannot have a constant part; put the bound in generic_constraint_bounds.parquet or use <=, >= or ==` |
| Two relational operators                                           | `a generic constraint expression carries at most one relational operator (<=, >=, ==); an inline double-relational range is not supported — split into two constraints` |
| A relational operator inside parentheses                           | `a relational operator is only allowed at the top level`                                                                                        |
| A bare `<` or `>`                                                  | `bare '<' at position <n> is not a valid operator; use '<=' for a relational bound`                                                              |
| Parentheses and unary signs nested deeper than 256 levels          | `expression nests deeper than 256 levels`                                                                                                       |
| A named-expression body with a relational operator                 | `a named expression cannot contain a relational operator`                                                                                       |
| A named-expression body that reads no LP variable                  | `"<name>" contains no LP variable; declare it in generic_parameters.json as a kind "expression" parameter`                                       |

**Fields:**

| Field     | Description                                                          |
| --------- | -----------------------------------------------------------------------|
| `path`    | Always `constraints/generic_constraints.json`                        |
| `field`   | `constraints[i].expression` or `expressions[i].expression`            |
| `message` | The quoted fragment followed by one of the messages in the table above |

**Example:** A product of two LP variables:

```text
[SchemaViolation] constraints/generic_constraints.json: field constraints[0].expression: `hydro_generation(0) * thermal_generation(0)`: product of LP variables is not linear
```

**Resolution:** Keep every term linear: scale an LP variable only by a
number, a scalar parameter or an expression built from them, and divide only
by such a constant. Check that each `@name` matches a parameter declared in
`constraints/generic_parameters.json` or an entry of this file's own
`expressions` array; move a body that reads no LP variable into
`constraints/generic_parameters.json` as an `expression` parameter. See
[Generic Constraints — Expression grammar](/en/reference/generic-constraints/#expression-grammar)
for the full grammar.

**When it occurs:** An entry of `constraints/generic_parameters.json` whose

refused. The formula messages start with the offending fragment in backticks,

`{total_horizon_hours}` is the length of the whole study horizon in hours. In
the `SchemaViolation` lines, the index in `thermals[0]` is the entry's position in the `thermals` array, counting from 0; the horizon message names the thermal `id`
instead, as in `thermals[id=0]`.

**Resolution:** Keep one of the two keys: give `lead_stages` an integer of at
least 1, or `lead_time_hours` a number above 0. For a lead longer than the study
horizon, shorten the lead, or declare a post-study stage that the lead reaches in the
`post_study_thermal_stages` list of `stages.json` (see the
[post-study calendars](/en/reference/case-format/stages/#post-study-calendars)). See
[System Element Modeling Overview §4](/en/math/system-elements#anticipated-thermal-plants) for the
anticipated-thermal model and
[`system/thermals.json`](/en/reference/case-format/system/#systemthermalsjson)
for the file's fields.

**When it occurs:** A hydro's `diversion.max_flow_m3s` in `system/hydros.json`
is negative. The channel capacity bounds the diverted flow from above, and the
flow is bounded below by `0`, so a negative capacity is rejected at load. A
channel without a capacity limit leaves `max_flow_m3s` out or sets it to
`null`.

**Fields:**

| Field         | Description |
| ------------- | ----------- |
| `description` | Contains a `[SchemaViolation] system/hydros.json: field hydros[<i>].diversion.max_flow_m3s: max_flow_m3s must be >= 0, got <value>` line, where `<i>` is the hydro's zero-based position in the file |

**Example:**

```text
[SchemaViolation] system/hydros.json: field hydros[0].diversion.max_flow_m3s: max_flow_m3s must be >= 0, got -5
```

**Resolution:** Set `max_flow_m3s` to the channel's capacity, `0` or more, or
leave it out for a channel without a capacity limit. A per-stage or per-block

#### Generic-constraint bound reference with no activation rows

**When it occurs:** `constraints/generic_constraint_bounds.parquet` is the
**activation grid** for generic constraints — a constraint applies at
`(stage, block)` if and only if a row exists for it there, independent of
whether the row supplies a numeric endpoint or the endpoint comes entirely
from the constraint's own inline affine remainder (an inline `<= @demanda`,
say). A constraint whose only endpoints come from that affine remainder, but
which has zero rows in the bounds parquet, is collected as `InvalidReference`
— the reference would otherwise apply to nothing and be silently inert.

**Fields:**

| Field         | Description                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------------------|
| `description` | Contains a `[InvalidReference] constraints/generic_constraints.json (GenericConstraint <id>): GenericConstraint <id> declares a bound reference but has no activation rows in generic_constraint_bounds.parquet: the reference would apply to nothing` line |

**Example:**

```
constraint violation: [InvalidReference] constraints/generic_constraints.json (GenericConstraint 3): GenericConstraint 3 declares a bound reference but has no activation rows in generic_constraint_bounds.parquet: the reference would apply to nothing
```

**Resolution:** Add at least one row for the constraint's `id` to
`generic_constraint_bounds.parquet` at every `(stage, block)` where it should
apply — the row may leave both `bound_lower`/`bound_upper` null as long as the
constraint's own affine remainder supplies the value; the row's job is then
only to activate the cell. See
[Generic Constraints — the activation grid](/en/reference/generic-constraints/)
for the full model.

**Severity:** Error

**When it occurs:** An id or key is declared twice where it must be unique.

#### Generic-constraint bounds row with neither endpoint and no affine remainder

**When it occurs:** A `generic_constraint_bounds.parquet` row with
`bound_lower = null` and `bound_upper = null` is legal only when the
constraint's own `bound_lower_affine`/`bound_upper_affine` supplies at least
one endpoint (the row then only activates the cell, per above). A both-null
row on a constraint with **no** affine remainder on either side has no
endpoint at all and is collected as `InvalidValue`.

**Fields:**

| Field         | Description                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------|
| `description` | Contains a `[InvalidValue] constraints/generic_constraint_bounds.parquet (GenericConstraintBoundsRow[<i>]): GenericConstraintBoundsRow[<i>] on constraint <id> has neither bound_lower nor bound_upper: at least one endpoint is required` line |

**Example:**

```
constraint violation: [InvalidValue] constraints/generic_constraint_bounds.parquet (GenericConstraintBoundsRow[4]): GenericConstraintBoundsRow[4] on constraint 3 has neither bound_lower nor bound_upper: at least one endpoint is required
```

**Resolution:** Either supply `bound_lower` and/or `bound_upper` on the row,
or add an inline relational operator (`<=`, `>=`, `==`) to the constraint's
`expression` so an affine remainder fills the missing endpoint. See
[Generic Constraints — the activation grid](/en/reference/generic-constraints/).

When the hydro declares no `diversion` channel, its diversion flow is fixed at

#### Stage storage bounds refused at load

**When it occurs:** `constraints/hydro_bounds.parquet` sets a storage bound
outside the reservoir's range, or leaves a study stage whose minimum storage
exceeds its maximum:

- A row's `max_storage_hm3` lies above the reservoir's `max_storage_hm3` in
  `system/hydros.json`, or its `min_storage_hm3` lies below the reservoir's
  `min_storage_hm3` (the dead volume), beyond a relative tolerance of `1e-9`
  (an absolute one below 1 hm³). Each column out of range is one finding, so a
  row out of range on both sides gives two. A row on a `hydro_id` the case does
  not declare is reported as [`InvalidReference`](#invalidreference) instead.
- On a study stage, the storage minimum in force exceeds the maximum in force.
  Each bound in force is the value on the stage's row, else the reservoir's
  own, so two rows can set the minimum and the maximum separately, and one
  override can cross the reservoir's opposite bound. Equal bounds are accepted.
  One finding lists every (hydro, stage) pair. A reservoir whose own
  `min_storage_hm3` exceeds its `max_storage_hm3` is refused first, as a
  [`SchemaViolation`](#schemaviolation) of `system/hydros.json`.

reservoir's range, so a stage's storage bounds must lie within it.

#### Initial storage refused at load

**When it occurs:** A hydro's `storage_hm3` in `boundary_conditions.json` seeds
its storage outside its range:

- A `hydros[].storage_hm3` of a hydro without a `filling` configuration lies
  outside that hydro's own `[min_storage_hm3, max_storage_hm3]` from
  `system/hydros.json`, beyond a relative tolerance of `1e-9` (an absolute one
  below 1 hm³). A hydro that enters service after the first stage is checked
  too. The value is refused, never clamped. A hydro whose `min_storage_hm3`
  exceeds its `max_storage_hm3` reports that [`SchemaViolation`](#schemaviolation)
  instead.
- In the deprecated `initial_conditions.json`, a hydro with a `filling` configuration listed under `storage`, or one without it listed under `filling_storage`, is refused with an `[InvalidValue]` message naming the array the seed belongs in; the current format routes each seed by `filling`, so this rule does not apply to it. To convert a deprecated case, see [Case conversion](/en/running/case-conversion/).

The stage `min_storage_hm3` and `max_storage_hm3` of
`constraints/hydro_bounds.parquet` bound the end of their stage, not the initial
storage; a seed outside the bounds of the hydro's first operating stage is the
[`ModelQuality`](#modelquality) warning, not an error.

### `CycleDetected`

**Severity:** Error

#### Post-study boundary unanchored or malformed

**When it occurs:** The business-rule check validates the post-study boundary — the
`post_study_thermal_stages` calendar in `stages.json`, and the `post_study_bounds`
and `commitments` of `boundary_conditions.json` — and the anticipated-thermal
deliveries that resolve onto it. Several distinct failures are collected under
this one check.
(A plant whose lead is longer than the whole study horizon and reaches **no**
declared post-study stage is caught earlier, at anticipated-thermal validation,
with a
`system/thermals.json … the plant can never deliver within the study horizon`
message (see
[Invalid anticipated-thermal lead](#invalid-anticipated-thermal-lead)); to clear
it, shorten the lead or declare a post-study stage the lead reaches — see
[System Element Modeling Overview §4](/en/math/system-elements#anticipated-thermal-plants).)
The post-study failures:

- A calendar failure reported on `stages.json` as a `BusinessRuleViolation`: the
  first post-study stage does not start exactly at the study horizon end, or the
  post-study stages are not date-contiguous (a gap or overlap between consecutive
  stages).
- A calendar failure reported on `stages.json` as a [`SchemaViolation`](#schemaviolation),
  because the load refuses the file before the business-rule check runs: an
  unparsable date, an `end_date` not after its `start_date`, a repeated
  `start_date`, an `id` that collides with another stage `id`, or a thermal-calendar
  `id` that does not continue the largest study stage `id` in `start_date` order.
- **Rule 1** — a plant's lead reaches a post-study stage with no
  `post_study_bounds` row for that stage's `stage_id`.
- **V2** — a plant's commitments decided before the study and delivered past the
  horizon do not tile the post-study stages they cover at coverage `1.0`.
- **V3** — a commitment window covers a post-study stage the study itself
  decides (`carried`), or one past the plant's decision reach.
- **V5** — a non-zero fixed commitment covers a post-study stage outside the
  plant's commissioning window.

The reached-stage rules (Rule 1, V2, V3, V5) are reported on `boundary_conditions.json`
as `BusinessRuleViolation`. The deprecated `post_study_stages.json` reports its calendar and these rules on that file, and also refuses a stage whose `duration_hours` rounds to a non-positive whole-day span.

#### Uncovered or over-covered commitment window

**When it occurs:** An anticipated thermal's `commitments`
windows in `boundary_conditions.json` must tile exactly the **in-study** delivery stages the plant decided
before the study — every such stage covered at fraction `1.0` — and never a
stage the study itself decides. The business-rule check reports a gap (an
uncovered leading stage), an over-reach (a window covering a study-decided
stage), and a horizon-straddle (a single window crossing the horizon end) as
separate diagnostics; each can fire independently. A window may legitimately
extend **past** the horizon (a commitment decided before the study and delivered
past the horizon; for the equivalent term in other planning tools, see the
[Glossary](/en/reference/glossary)) — that post-study coverage is validated
separately, under
[Post-study boundary](#post-study-boundary-unanchored-or-malformed) above.

**Fields:**

| Field         | Description |
| ------------- | ----------- |
| `description` | Contains a `[BusinessRuleViolation] boundary_conditions.json (thermals[id=<id>].anticipated_config): <message>` line — see the messages below |

**Example:**

{/* quoted from source: check_commitment_coverage in crates/novomodelo-io/src/validation/semantic/thermal.rs at novomodelo commit 95318d3ba90a — thermal 7 with two leading delivery stages and no window over stage 0 */}

```text
[BusinessRuleViolation] boundary_conditions.json (thermals[id=7].anticipated_config): thermal 7: commitments do not tile the leading 2 delivery stage(s) at coverage 1.0; study stage id(s) [0] are not covered exactly once. Write a commitment window (a committed 0 MW is explicit) for every leading delivery stage.
```

{/* quoted from source: check_commitment_coverage in crates/novomodelo-io/src/validation/semantic/thermal.rs at novomodelo commit 95318d3ba90a — thermal 7 with a window over study stage 3 */}

```text
[BusinessRuleViolation] boundary_conditions.json (thermals[id=7].anticipated_config): thermal 7: commitments cover study stage id(s) [3] beyond the leading 2 calendar-derived delivery stage(s); a commitment window may not cover a study stage the study itself decides. Shorten the plant's anticipated_config lead so its window stays within the leading 2 delivery stage(s).
```

{/* quoted from source: check_no_straddling_commitment_window in crates/novomodelo-io/src/validation/semantic/thermal.rs at novomodelo commit 95318d3ba90a — thermal 7 with one window crossing a study horizon that ends 2026-09-01 */}

```text
[BusinessRuleViolation] boundary_conditions.json (thermals[id=7].anticipated_config): thermal 7: commitments window [2026-08-15, 2026-09-15) straddles the study horizon end (2026-09-01); a single window may not cover both in-study and post-study delivery. Declare two windows split at the horizon instead: one ending at 2026-09-01 for the in-study coverage, one starting at 2026-09-01 for the post-study coverage.
```

**Resolution:** Write a commitment window for every in-study delivery stage the
plant decided before the study (a committed `0` MW is a legitimate, explicit
window — not an omission), never covering a stage the study itself decides (end the window earlier, or
lengthen the plant's `anticipated_config` lead if that stage is in fact decided
before the study), and split any window at the horizon end rather than
straddling it. Those are the in-study delivery stages whose decision falls
before the first study stage: the first `lead_stages` stages, or, for
`lead_time_hours`, every stage whose decision instant — one lead before the
stage's end — is at or before the study start. See
[System Element Modeling Overview §4](/en/math/system-elements).

#### Per-block generic-constraint references

**When it occurs:** A generic-constraint term names a block that its stage
cannot expose. The check runs only for a (constraint, stage) pair that has a row
in `constraints/generic_constraint_bounds.parquet`. An evaporation reference is a
`hydro_evaporation` term; a storage reference is a `hydro_storage_initial`,
`hydro_storage_final`, `hydro_useful_volume_initial`, or
`hydro_useful_volume_final` term. With `K` the number of blocks the stage
declares, the check rejects four conditions:

- A block index of `K` or more in an evaporation or storage reference, on any
  stage.
- An evaporation reference to a block from 1 to `K - 1` on a
  [parallel stage](/en/reference/case-format/stages/#stagesjson) with `K > 1`.
- An evaporation reference with no block on a chronological stage with `K > 1`.
- A storage reference to an interior block boundary, a boundary between two
  blocks, on a parallel stage with `K > 1`.

The rules are stated under
[`hydro_evaporation` block references](/en/reference/generic-constraints/#hydro_evaporation-block-references).

**Kind, file, entity:** `BusinessRuleViolation`,
`constraints/generic_constraints.json`, and the entity `constraint[id=N]`, where
`N` is the constraint's `id`.

**Messages:** `novomodelo validate` prints one `error:` line per rejection. The five
lines below show one message per template, in this order:

1. An evaporation block of `K` or more.
2. An evaporation block from 1 to `K - 1` on a parallel stage.
3. An interior storage boundary on a parallel stage.
4. A storage block of `K` or more.
5. An evaporation reference with no block on a chronological stage.

{/* capture: novomodelo validate case 2>&1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; stages.json: stages 0 and 1 carry two blocks PEAK and OFFPEAK with hours h // 2 and h - h // 2 of the single block's hours h, stage 0 block_mode parallel, stage 1 block_mode chronological; constraints/generic_constraints.json added with five constraints on hydro 0, slack disabled: id 0 evap_out_of_range hydro_evaporation(0, 5), id 1 evap_parallel_block hydro_evaporation(0, 1), id 2 storage_interior hydro_storage_final(0, 0), id 3 storage_out_of_range hydro_storage_initial(0, 5), id 4 evap_chronological_bare hydro_evaporation(0); constraints/generic_constraint_bounds.parquet added with compression zstd and one row per activation, constraints 0-3 at stage 0 and constraint 4 at stage 1, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1; the Validation summary line, which carries the temporary path, is not quoted) */}

**When it occurs:** A generic constraint with a `hydro_outflow_volume`,

its storage bounds, or move the initial storage inside them; for the rising-floor warning, lower the rising floor, raise the previous stage's floor, or use the `penalty` inflow method (see [the complete-recourse precondition](/en/math/penalty-system#complete-recourse-precondition)); for the precomputed-plane warning, raise the flagged plane's `gamma_0` or `gamma_v` until `kappa`·`gamma_0` + `gamma_v`·v_min is at least 0 at the storage v_min the message prints, or fit the planes from geometry with `source: "computed"`; for the tailrace-flow warning, select FPHA for the hydro in `extensions/production_models.json` or remove `tailrace_flow` from the hydro; for a `lognormal_3p` warning, check the flagged seasonal means, or set an [`inflow_non_negativity`](/en/running/configuration/#modelinginflow_non_negativity) method other than `none`.
Warnings of this type do not prevent the solver from running.

#### Deprecated boundary files in use

**When it occurs:** The case directory holds the deprecated `initial_conditions.json`, with or

on the deprecated `initial_conditions.json`; `novomodelo validate` prints it as a `warning:`
line and exits `0`, and the case still runs.

**Resolution:** Convert the case with
`python3 scripts/migrate/boundary_conditions.py <case>`; see
[Case conversion](/en/running/case-conversion/) and the
[boundary conditions page](/en/reference/case-format/boundary-conditions/#boundary_conditionsjson).

### `SemanticAmbiguity`

**Severity:** Warning (does not block execution)

**When it occurs:** A valid construct whose semantics are ambiguous or
stage-dependent in a way that is likely to surprise the user. Two constructs
trigger it, both emitted by the business-rule check in
`constraints/generic_constraints.json`:

1. **`thermal_generation(N)` on an anticipated thermal.** Using
   `thermal_generation(N)` in a generic constraint when thermal `N` is an
   anticipated thermal. `thermal_generation` refers to the per-block generation
   measured at the _delivery_ stage (when the commitment matures), not the
   commitment decision made at the current stage. Users who intend to constrain
   the commitment itself should use `anticipated_decision(N)` instead.

   **Example:** A generic constraint `thermal_generation(0)` on an anticipated thermal:

   {/* capture: novomodelo validate sa1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sa1; system/thermals.json: thermal 0 given anticipated_config with lead_stages 1; initial_conditions.json: past_anticipated_commitments gains one window for thermal 0, 2024-01-01 to 2024-02-01, value_mw 0.0; constraints/generic_constraints.json added holding one constraint, id 0, name peak_cap, expression thermal_generation(0), slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 1, block_id and bound_lower null, bound_upper 10.0; run with NO_COLOR=1, exit code 0; the Valid case and Validation summary lines and the first warning line, which concerns the thermal's stage-cadence transition, are not quoted) */}

   ```text
   warning: constraints/generic_constraints.json (constraint[id=0]): Constraint "peak_cap": thermal_generation(0) references an anticipated thermal. thermal_generation refers to the per-block generation at the delivery stage, not the forward commitment. If you intend to constrain the commitment itself, use anticipated_decision(0) instead.
   ```

   **Resolution:** Review the constraint expression. If you want to bound the
   generation dispatched at the delivery stage, `thermal_generation(N)` is correct
   and the warning can be ignored. If you want to bound the advance commitment
   decision itself, replace `thermal_generation(N)` with `anticipated_decision(N)`.

2. **Stored-energy tags that would not cancel.** One constraint references
   computed tags — in its expression coefficients, in its bounds (an `@emax` on
   the right-hand side counts) or through an `expression` parameter that reads
   them — in one of two forms:
   - a `max_stored_energy(h)` ceiling beside a productivity tag for the same
     hydro other than `integrated_accumulated_productivity(h)` (or a
     `max_stored_energy_mwh(h)` ceiling beside an MWh productivity tag other
     than `integrated_accumulated_productivity_mwh_per_hm3(h)`). The tags differ
     in scope (one plant or its downstream cascade) or in evaluator (the plant's
     reference point or the useful-range mean), so a stored-energy comparison
     built from them does not cancel. One warning is emitted per such pair.
   - MWh tags (the `_mwh` and `_mwh_per_hm3` family) mixed with raw tags. The
     two families differ by a factor of $10^6/3600$; the warning reads
     `Constraint "<name>": mixes MWh tags (<tags>) with raw productivity tags (<tags>); the two units differ by a factor of 10^6/3600. Use one family throughout.`

   The case still validates.

   **Example:** A constraint that pairs the two tags for hydro 0:

   {/* capture: novomodelo validate sa2 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sa2; constraints/generic_parameters.json added holding two computed parameters for hydro 0, id 1 name rho tag accumulated_productivity and id 2 name emax tag max_stored_energy; constraints/generic_constraints.json added holding one constraint, id 0, name sec_mismatch, expression @rho * hydro_useful_volume_final(0) >= 0.3 * @emax, slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 1, block_id, bound_lower and bound_upper null; run with NO_COLOR=1, exit code 0; the Valid case and Validation summary lines are not quoted) */}

   ```text
   warning: constraints/generic_constraints.json (sec_mismatch): Constraint "sec_mismatch": pairs max_stored_energy(0) with accumulated_productivity(0) for hydro 0; the two differ in scope or evaluator and would not cancel. The coefficient matching max_stored_energy is integrated_accumulated_productivity.
   ```

   **Resolution:** Use `integrated_accumulated_productivity` as the coefficient
   that matches `max_stored_energy`, or
   `integrated_accumulated_productivity_mwh_per_hm3` with
   `max_stored_energy_mwh`, and keep one constraint in one family; see
   [the security-curve example](/en/reference/generic-constraints/#worked-example-a-security-curve).

The warning is printed by `novomodelo validate` in its human-readable output; the
`--json` success output does not carry warnings.

## Load-failure kinds

The `phase` value of `novomodelo validate --json` and the `kind` of an entry in the `errors` array of
`novomodelo.io.validate` (Python) name the failure that stopped the load. Almost every case-load failure reports
[`ConstraintError`](#constrainterror), because the load collects its problems into one report. The kinds are
listed below in the order of the load steps in which they typically occur: reading a file, parsing it,
checking its fields, then validating the whole case.

During a case load, a read, parse or schema failure in one file is collected
into the validation report rather than returned on its own. It reaches you as a
line of a [`ConstraintError`](#constrainterror): `[FileNotFound]` for a read
failure, `[ParseError] <file>: parse error: <message>` for a parse failure, and
`[SchemaViolation] <file>: field <field>: <message>` for a schema failure. The
display formats below reach you only for a load error raised after that report
is complete, such as a `policy.path` refusal raised once the case has loaded; see [Exit Codes](/en/reference/cli-reference/#exit-codes).

### `IoError`

**Severity:** Error

**When it occurs:** A required file exists in the file manifest but cannot be
read from disk — file not found, permission denied, or other OS-level I/O
failure. Occurs when a JSON or Parquet file is read for parsing and the read
returns an error. It is also returned when a `policy.path` cannot be inspected (exit `2`).

**Display format:**

```
I/O error reading {path}: {source}
```

**Fields:**

| Field    | Description                             |
| -------- | --------------------------------------- |
| `path`   | Path to the file that could not be read |
| `source` | Underlying OS I/O error                 |

**Resolution:** Verify the file exists in the case directory. Check that the
process has read permissions for the directory and file. For a full case load, the
case root must contain all required files (see [Case Format](/en/reference/case-format/)).
A problem collected during a case load prints as a report line; see [Validation report kinds](#validation-report-kinds).

---

`ParseError` — see [`ParseError`](#parseerror); a parse failure collected in the report prints as a
`[ParseError]` line.

---

### `SchemaError`

**Severity:** Error

**When it occurs:** A file parses successfully but a field violates a schema
constraint: a required field is missing, a value is outside its valid range, or
an enum discriminator names an unknown variant. Occurs when the fields of a parsed
file are checked. Also returned when `training.selection`
(which carries the forward-pass count) or `training.stopping_rules` is absent
and the config is parsed or merged outside a case load (for example, Python
config overrides); a case load reports the same absence as a
[`SchemaViolation`](#schemaviolation) line. It is also returned for a `policy.path` that the run refuses after the case loads (exit `1`; see
[Configuration — `policy`](/en/running/configuration/#policy)).

**Display format:**

```
schema error in {path}, field {field}: {message}
```

**Fields:**

| Field     | Description                                                            |
| --------- | ---------------------------------------------------------------------- |
| `path`    | Path to the file containing the invalid entry                          |
| `field`   | Dot-separated path to the offending field (e.g., `"hydros[3].bus_id"`) |
| `message` | Human-readable description of the violation                            |

**Resolution:** The `field` value identifies the exact location of the problem.
Check that required fields are present and that values fall within documented
ranges. A problem collected during a case load prints as a report line; see [Validation report kinds](#validation-report-kinds).

---

### `ConstraintError`

**Severity:** Error

**When it occurs:** A catch-all for all validation diagnostics collected
across any validation step, for system assembly rejections, and for guards
raised directly by loaders after assembly (for example, a non-finite
closure-derived innovation scale is rejected here naming the hydro and
season). The `description` field contains
every collected error message joined by newlines, each prefixed with its
`[<Kind>]`, source file, optional entity identifier, and message text.

**Display format:**

```
constraint violation: {description}
```

**Fields:**

| Field         | Description                           |
| ------------- | ------------------------------------- |
| `description` | All error messages joined by newlines |

**Example:** The `--json` failure capture under
[How these errors reach you](#how-these-errors-reach-you) reports `ConstraintError` as its
`phase`, with the collected report line in `message`.

**Resolution:** Read every line in `description` — each line is a separate
problem. Address them all and re-run. The `[<Kind>]` prefix identifies the
category of each problem, and each kind section gives its resolution. A problem collected during a case load prints as a report line; see [Validation report kinds](#validation-report-kinds).

## Preparation-phase kinds

The six `phase` values below appear only in `novomodelo validate`'s pre-solver
validation checks and are **not** `LoadError` kinds. They surface in
`novomodelo validate --json`'s error `phase` field when a prep-phase check fails
before the solver is initialized.

### `ConfigValidationError`

**When it occurs:** A `config.json` validation failure in the study-setup

config.json: configuration validation error: gap stopping rule requires at least one of tolerance / relative_tolerance to be present

### `StochasticPreparationError`

**Severity:** Error

**When it occurs:** A failure during stochastic model preparation — scenario
generation, inflow-model setup, or external scenario validation. File label:
`scenarios/inflow_history.parquet` for a stochastic-model error (after the label,
its message begins `stochastic error:`) and `scenarios/` for every other failure
in this phase, such as a load error (after the label, its message begins
`I/O error:`). The label depends on how the error is classified, not on the file
it traces to.

**Example:** A historical library that holds no complete window, a
non-stationary inflow model (non-finite innovation scale), an
autoregressive stage whose standard deviation is zero, a stage with more
openings than the first stage of its noise group, or a declared
opening-tree file that is absent.
[Historical-library refusals](#historical-library-refusals),
[Inflow-model refusals](#inflow-model-refusals),
[Noise-group opening count](#noise-group-opening-count) and
[Opening-tree file missing](#opening-tree-file-missing) quote the messages.

#### Historical-library refusals

**When it occurs:** Three refusals of the historical window pool are reachable
from a case. The pool serves the forward `historical` scheme and the stages that
use the `historical_residuals` sampling method (see
[Historical Window Pool](/en/math/scenario-generation/#historical-window-pool) and
[Historical-Residual Openings](/en/math/scenario-generation/#25-historical-residual-openings)).
Each message is `insufficient data: ` followed by the text below:

- No year is admissible, so the pool is empty:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/window.rs:136-141 at novomodelo v0.22.0 */}
  ```text
  no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
  ```
- A study stage has no season:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/historical.rs:258-271 at novomodelo v0.22.0 — reproduced with the binary of record at inflow-model order 1, so not quoted as a capture */}
  ```text
  V2.1: stage {stage_id} (index {index}) has season_id: None; all study stages must have a season_id assigned
  ```
- A residual of the pool is not finite:
  {/* quoted from source: crates/novomodelo-stochastic/src/sampling/historical.rs:579-596 at novomodelo v0.22.0 */}
  ```text
  V2.3: historical library contains non-finite eta {value} at window year {year}, stage id {stage_id}, hydro id {hydro_id}
  ```

V2.1 names the stage id, then the stage's 0-based index. A stage has no season
when it declares none and the case either has no season definitions or has a
`custom` season map that leaves the stage's start date uncovered. For example,
with an inflow model of order 1 and a `custom` season map that covers the first
stage and its lag season but leaves one later stage's start date uncovered,
`novomodelo validate` reports V2.1.

V2.3 names the value, the window's year, the stage id and the hydro id.

**Rendering under `novomodelo validate`:** the phase is `StochasticPreparationError`
and the exit code is `1`. The `error:` line carries the file label and the
`stochastic error:` prefix. This excerpt omits the `Validation:` summary line,
which carries the case path.

{/* capture: novomodelo validate case 2>&1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy; stages.json: season_definitions added with cycle_type monthly and twelve seasons, season_id 0 to 3 on the four stages, sampling_method historical_residuals on every stage; scenarios/inflow_history.parquet added with compression zstd, hydro 0, three monthly windows 2020-01-01 to 2020-04-01, values 41, 42 and 43; scenarios/inflow_ar_coefficients.parquet added with compression zstd and zero rows; run with NO_COLOR=1; the Validation summary line, which carries the temporary path, is not quoted) */}

```text
error: scenarios/inflow_history.parquet: stochastic error: insufficient data: no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
```

`novomodelo run` on the same case exits `1`. The line has no file label, and the
validate hint follows it. This excerpt omits the banner, the `Execution` block and the
`Loading case:` line.

{/* capture: novomodelo run case 2>&1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: the same temporary 1dtoy derivative as the novomodelo validate capture above; run with NO_COLOR=1; the banner, the Execution block and the Loading case line, which carry the hostname and the temporary path, are not quoted */}

```text
error: stochastic error: insufficient data: no valid historical windows found: ensure that inflow history covers the required seasons for at least one starting year
  -> run `novomodelo validate <CASE_DIR>` for a full diagnostic report
```

`novomodelo validate` builds the study as `novomodelo run` does, so it reports a refusal
of the forward `historical` scheme's library too: as
[`StudySetupError`](#studysetuperror) (`scenarios/: stochastic error: …`) without

[`BoundaryReconciliationError`](#boundaryreconciliationerror)

`policy.boundary`.

#### Inflow-model refusals

**When it occurs:** The inflow model, declared by the case's autoregressive and
statistics files or fitted from `inflow_history.parquet`, cannot support the
study. Two refusals carry a fixed message:

- An autoregressive stage has a standard deviation of zero. The message names
  the hydro id and the stage id, and `ar_order` is the stage's autoregressive
  order:
  {/* quoted from source: crates/novomodelo-stochastic/src/par/validation.rs:54-70 at novomodelo v0.22.0 */}
  ```text
  invalid PAR parameters for hydro {hydro_id} at stage {stage_id}: zero standard deviation with ar_order={ar_order}: AR model requires nonzero variance to normalize coefficients
  ```
  This is a stochastic-model error. `novomodelo validate` prints it after the
  `scenarios/inflow_history.parquet: stochastic error: ` prefix and exits `1`.
  `novomodelo run` prints it as `error: stochastic error: invalid PAR parameters …`
  with the validate hint, and exits `1`.
- The model's coefficients imply a non-stationary process, so a derived
  residual standard-deviation ratio is not finite. A model fitted from the
  history does not reach this refusal: the fit lowers the order of a season whose
  model implies a negative residual variance, and
  [`fitting_report.json`](/en/reference/output/stochastic/#stochasticfitting_reportjson)
  lists it as `negative_residual_variance`. The message names the hydro id and
  the season id:
  {/* quoted from source: crates/novomodelo-io/src/scenarios/residual_derivation.rs:144-152, crates/novomodelo-io/src/error.rs:60 and crates/novomodelo-sddp/src/error.rs:45-46 at novomodelo v0.22.0 */}
  ```text
  I/O error: constraint violation: derived residual_std_ratio is non-finite for hydro_id={hydro_id} season={season}: the coefficients imply a non-stationary process (implied residual variance 1 - sum(psi*rho) is negative)
  ```
  This is a [`ConstraintError`](#constrainterror) raised while the model is
  assembled, so it reaches the command as a load error. `novomodelo validate` prints it
  with the `scenarios/` file label and exits `1`. `novomodelo run` prints it without
  the `I/O error: ` prefix, followed by a hint to run `novomodelo validate`, and also
  exits `1`.

#### Noise-group opening count

**When it occurs:** A study stage has more openings than the first stage of its
noise group, the run of adjacent study stages with the same `season_id` whose
start dates fall in one calendar year
([Scenario Generation §2.3](/en/math/scenario-generation/#23-opening-tree)). The
counts compared are the ones the opening tree uses: `num_openings` after the
clamps by a historical window pool and by an external scenario library (the
clamp warnings of the Implementation notes tab of
[Scenario Generation](/en/math/scenario-generation/#implementation-in-novomodelo)),
so a clamp on the first stage alone can bring it about. The check runs before
any noise is drawn. The message names both stages:

{/* quoted from source: crates/novomodelo-stochastic/src/tree/generate.rs:156-183 and crates/novomodelo-stochastic/src/error.rs:28 at novomodelo v0.22.0 */}

```text
insufficient data: stage {dst_id} has {k_dst} openings but shares a noise group with stage {src_id}, which has {k_src}; a stage cannot have more openings than the first stage of its noise group: lower num_openings of stage {dst_id} in stages.json to {k_src}
```

This is a stochastic-model error. `novomodelo validate` prints it after the
`scenarios/inflow_history.parquet: stochastic error: ` prefix and exits `1`.
`novomodelo run` prints it as `error: stochastic error: insufficient data: stage …`
with the validate hint, and exits `1`.

**Resolution:** Lower `num_openings` of the named stage in `stages.json` to the
count the message gives. When a clamp lowered the first stage's count, more
historical windows or external scenarios for that stage also clear the refusal.
A later stage with fewer openings than the first stage is accepted and copies
the first of them.

#### Opening-tree file missing

**When it occurs:** `training.scenario_source.openings` is `{"source": "file"}`
and `scenarios/noise_openings.parquet` is absent. The stochastic preparation
phase of `novomodelo validate` stops with exit `2`, as `novomodelo run` does, and under `--json` the error's `phase` is
`StochasticPreparationError`. The message is:

{/* quoted from source: crates/novomodelo-sddp/src/setup/stochastic_pipeline.rs:85-95 at novomodelo v0.22.0 */}

```text
openings source is 'file' but the conventional scenarios/noise_openings.parquet is absent
```

**Example:** `novomodelo validate` prints the message inside an I/O error line. The
`scenarios/` label and the `I/O error:` wording are how this phase reports a
missing file, and `<case>` stands for the path of your case directory:

{/* capture: novomodelo validate nofile 2>&1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy nofile; config.json re-written with 2-space indentation, simulation.enabled false, training.scenario_source gains openings with source file, and no scenarios/noise_openings.parquet; run with NO_COLOR=1, exit code 2; the Validation summary line, which carries the temporary path, is not quoted; the fixture directory name nofile in the error lines is replaced by <case>) */}

**Resolution:** Supply `scenarios/noise_openings.parquet`, or declare `openings`

### `StudySetupError`

### `GenericConstraintValidationError`

**Severity:** Error

**When it occurs:** A failure during generic-constraint preparation, including
expression inlining, parameter resolution, and slack setup. File label:
`constraints/`.

An **unresolved `@parameter` scalar** — a generic-constraint parameter
declared in `constraints/generic_parameters.json` that has no value for a
season, stage or block the study needs — fails here at `novomodelo validate` time.
An `@name` that no file declares is reported at load time; see
[Generic-constraint expression rejected](#generic-constraint-expression-rejected).
The parameter is refused with one of:

{/* quoted from source: ResolvedParametersError and PerStageBlockCoverageIssue in crates/novomodelo-sddp/src/policy/resolved_parameters.rs at novomodelo v0.22.0 */}

```text
parameter '<name>': no seasonal value for season_id=<season> (needed by stage <t>)
parameter '<name>': PerStageBlock cell (stage=<s>, block=<b>) is not covered by any triple
parameter '<name>': PerStageBlock cell (stage=<s>, block=<b>) lies outside the study's (stage, block) grid
parameter '<name>': no specific productivity (`ρ_esp`) available for hydro_id=EntityId(<id>)
```

`<t>` and `<s>` are 0-based study stage positions and `<b>` a 0-based block
index. A `seasonal` parameter needs a value for the season of every study
stage, and a `per_stage_block` parameter a value for every block of every study
stage. A `computed` parameter with the `specific_productivity` tag needs a
`specific_productivity_mw_per_m3s_per_m` for its hydro at every study stage,
from `system/hydro_energy_productivity.parquet` or from `system/hydros.json`.

A **non-finite resolved value** fails here too. A coefficient, a bound or an
`expression` parameter that depends on scalar parameters is evaluated at every
stage and block it is active in, and one whose value is not finite there (a
division by a parameter that is zero at that stage, for instance) is refused
with one of:

```text
generic constraint <id> '<name>': the coefficient of <variable> resolves to the non-finite value <value> at stage <s>, block <b>
generic constraint <id> '<name>': the upper bound resolves to the non-finite value <value> at stage <s>, block <b>
parameter '<name>': expression resolves to the non-finite value <value> at stage <s>, block <b>
```

The bound message names the lower or the upper bound; an `expression`
parameter is checked whether or not a constraint reads it. A constant built from
numbers alone that divides by zero is refused at load instead; see
[Generic-constraint expression rejected](#generic-constraint-expression-rejected).

**Example:** A `seasonal` parameter whose only value is for season `5`, in a case with
no season definitions:

{/* capture: novomodelo validate sea | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy sea; constraints/generic_parameters.json added holding one seasonal parameter, id 1, name sea, values [[5, 1.0]]; constraints/generic_constraints.json added holding one constraint, id 0, name cap, expression @sea * hydro_storage(0), slack enabled false; constraints/generic_constraint_bounds.parquet added with compression zstd and one row, constraint 0, stage 0, block_id and bound_lower null, bound_upper 1e9; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
constraints/: configuration validation error: parameter 'sea': no seasonal value for season_id=0 (needed by stage 0)
```

This phase also reports **energy-conversion** failures of a hydro plant computed
at the same step — a forebay (VHA) table in `system/hydro_geometry.parquet` that
fails to build, or a non-positive useful-range mean equivalent head — for any
plant with VHA geometry and a specific productivity, independent of its
generation model and of whether the case declares generic constraints (see
[Hydro Production Function Models §4.3](/en/math/hydro-production-models#43-useful-range-mean-productivity)).
An `equivalent_productivity_mw_per_m3s` value in
`system/hydro_energy_productivity.parquet` sets only the reference-point
productivity and does not avoid the mean-head check; an
`integrated_equivalent_productivity_mw_per_m3s` value for the stage does, and
the message names that column.

A plant whose geometry and losses leave a negative head:

{/* capture: novomodelo validate e1 | novomodelo   v0.22.0 | binary: novomodelo-cli sha256 235ff225 | case: temporary 1dtoy derivative (novomodelo init --template 1dtoy e1; system/hydros.json: hydro 0 given specific_productivity_mw_per_m3s_per_m 0.009 and hydraulic_losses of type constant with value_m 450.0; system/hydro_geometry.parquet added with compression zstd, hydro 0, two rows at volume_hm3 0.0 and 1000.0, height_m 400.0 and area_km2 10.0 in both; run with NO_COLOR=1, exit code 1; the Validation summary line, which carries the temporary path, is not quoted and the error: prefix is not quoted) */}

```text
constraints/: configuration validation error: hydro EntityId(0) has non-positive useful-range mean equivalent head h_mean=-50; fix its geometry/tailrace or supply integrated_equivalent_productivity_mw_per_m3s in system/hydro_energy_productivity.parquet
```

:::note
These hydro energy-conversion failures are reported under the generic-constraint
phase with file label `constraints/`, although no constraint file is involved;
the message names the plant in the form `EntityId(N)`.
:::

## Policy-load errors

A policy load refuses a checkpoint that does not fit the study loading it. Two
loads raise these errors: a **full-FCF load** of the checkpoint at `policy.path`
(warm-start, resume, and simulation-only runs) and a **boundary load** of the
checkpoint at `policy.boundary.path`. `novomodelo run` and the Python entry points
raise them before training or simulation starts. `novomodelo validate` runs both loads the run would apply, reading the full-FCF checkpoint from `<output dir>/<policy.path>` (`--output`, default `<CASE_DIR>/output/`), and exits `1` on every refusal `novomodelo run` makes. These errors are not
`LoadError` variants, and case loading does not return them.

A full-FCF load runs its checks in the order given under
[Check order](/en/running/policy-management/#check-order). The checks of a boundary
load are listed under
[Compatibility requirements](/en/running/policy-management/#compatibility-requirements).
A `manifest.bin` whose `format_version` is not `4` fails before these checks:
`failed to read policy checkpoint: serialization error for entity checkpoint_manifest: unsupported checkpoint manifest format_version {n}; expected 4; re-run the program that produced it with novomodelo {running}; for a converted boundary policy, convert it again`, exit `1`.

### How a policy-load failure reaches you

Exit 2 for a checkpoint the OS refuses to read: `error: I/O error in {path}: {source}` and the permissions hint. |
| `novomodelo validate`, full-FCF load | Exit 1. `Validation: 1 errors, 0 warnings in <case>` and `error: <output dir>/<policy.path>: {message}`; `--json` phase `WarmStartIncompatible`, `ResumeIncompatible` or `SimulationPolicyIncompatible`. | Exit 1 (phase as for a refusal), or exit 2 with phase `IoError` for a checkpoint the OS refuses to read. |
| `novomodelo run` and `novomodelo validate`, boundary load | Exit 1. `novomodelo run` prints `error: {message}` and a hint line. `novomodelo validate` labels the message `policy.boundary: `; under `--json` it reports phase `BoundaryReconciliationError`. | Exit 1. `error: failed to read boundary policy checkpoint at {path}: {e}` and a hint line on stderr. Under `novomodelo validate --json`, phase `BoundaryReconciliationError`. |

### `PolicySoftwareMismatch`

**Severity:** Error

`manifest.bin` records another software or version than the running build: the
`software` and `software_version` compare exactly, so a different patch or
pre-release build is refused as well. A checkpoint whose `format_version` is not
`4` is refused before this check
([How a policy-load failure reaches you](#how-a-policy-load-failure-reaches-you)).
[Version gate](/en/running/policy-management/#version-gate) states the rule.

**Message:**

{/* quoted from source: crates/novomodelo-sddp/src/error.rs:105-110 and 129-136 and crates/novomodelo-io/src/output/software.rs:13-18 at novomodelo v0.22.0 — not capturable (needs a checkpoint written by another software or version) */}

```text
policy was written by {writer}, but this is novomodelo {running}; a policy loads only in the software and version that wrote it: re-run the program that produced it with novomodelo {running}; for a converted boundary policy, convert it again
```

`{writer}` is `<software> <version>`, `<software>, which recorded no version`,

**Resolution:** Re-run the program that produced the checkpoint with the running novomodelo version; for a converted

**When it occurs:** A `policy.mode = "resume"` load finds that the checkpoint cannot continue the interrupted

phase `ResumeIncompatible`. A `warm_start` load of the same checkpoint makes none of these checks.

**Messages:**

{/* quoted from source: crates/novomodelo-sddp/src/policy/full_fcf_load.rs:244-327 at novomodelo v0.22.0 */}

**When it occurs:** A boundary load (`policy.boundary`) finds an inflow-lag slot of the current study that the boundary checkpoint cannot supply. [Compatibility requirements](/en/running/policy-management/#compatibility-requirements) gives the order of the boundary checks.

**Messages:**

No coefficient for a hydro at a lag depth; `{names}` lists every missing pair as `hydro {id} at lag depth {depth}`, separated by commas:

{/* quoted from source: crates/novomodelo-sddp/src/policy/policy_load.rs:1109-1112 at novomodelo v0.22.0 */}

```text

```

A coefficient that references a different past; the two dates print as `YYYY-MM-DD`:

{/* quoted from source: crates/novomodelo-sddp/src/policy/reconcile.rs:395-404 at novomodelo v0.22.0 */}

## Solver profile validation

Per-phase solver-profile overrides (`training.solver.backward`,
`training.solver.forward`, `simulation.solver`) are validated against the
compiled backend's support matrix at study setup, before any stage LP is
built, on every MPI process; every rejection below is a configuration error with its
own message.

`novomodelo validate` runs these checks on every case: it reports a rejection with phase
[`StudySetupError`](#studysetuperror) (`config.json: configuration validation error: …`), or
[`BoundaryReconciliationError`](#boundaryreconciliationerror) with `policy.boundary` configured.
`novomodelo run` refuses the case before training. Both exit `1`.

### CLP backend: every override is rejected

**When it occurs:** A binary built with the CLP backend (see
[Installation — CLP build](/en/getting-started/installation#clp-build))
rejects every solver-profile override field outright — CLP's own option
surface has not been measured against these fields, so novomodelo refuses to
silently apply a HiGHS-flavored value to it. An empty `"solver": {}` block and
an absent `solver` block are both legal; only a field that is actually *set*
triggers the error. When a profile sets more than one field, only the first
field in declaration order is named, so fixing one field at a time surfaces
one error per fix cycle rather than a combined report.

**Example:**

```
solver profile field "dual_edge_weight" for phase "backward" is unsupported on backend "clp": rejected until CLP is re-measured
```

For `primal_feasibility_tolerance`, the field token additionally carries the
value that was set:

```
solver profile field "primal_feasibility_tolerance" (1e-7) for phase "forward" is unsupported on backend "clp": rejected until CLP is re-measured
```

`"<phase>"` is one of `forward`, `backward`, or `simulation`.

**Resolution:** Remove the override field from `config.json` on a CLP-built
binary, or switch to the default HiGHS backend if the override is required.

### HiGHS backend: six per-field range checks

The default (`highs`) backend accepts every solver-profile field. The closed
enums (`dual_edge_weight`, `scale`, `price`, `presolve`) and `use_warm_start`
are unconditionally valid — every variant is checked when `config.json` is
read, so there is no separate runtime range check for them. The remaining
six numeric fields are range-checked at study setup; each failure names the
field, the rejected value, and the phase (`forward` / `backward` /
`simulation`) whose profile set it.

| Field | Rule | Message |
| --- | --- | --- |
| `primal_feasibility_tolerance` | must be finite | `unsupported primal_feasibility_tolerance {value} for backend "highs" in phase "{phase}": value must be finite` |
| `dual_feasibility_tolerance` | must be finite and `>= 0.0000000001` | `unsupported dual_feasibility_tolerance {value} for backend "highs" in phase "{phase}": value must be finite and >= 0.0000000001` |
| `simplex_update_limit` | must be `<= 2147483647` | `unsupported simplex_update_limit {value} for backend "highs" in phase "{phase}": value must be <= 2147483647` |
| `cost_perturbation` | must be finite and `>= 0` | `unsupported cost_perturbation {value} for backend "highs" in phase "{phase}": value must be finite and >= 0` |
| `factor_pivot_threshold` | must be in `[0.0008, 0.5]` | `unsupported factor_pivot_threshold {value} for backend "highs" in phase "{phase}": value must be in [0.0008, 0.5]` |
| `steepest_edge_devex_fallback_threshold` | must be finite and `>= 1.0` | `unsupported steepest_edge_devex_fallback_threshold {value} for backend "highs" in phase "{phase}": value must be finite and >= 1.0` |

`0.0000000001` is 1e-10 printed in full; `2147483647` is the largest 32-bit
signed integer; `[0.0008, 0.5]` is HiGHS's own accepted pivot-threshold range.

**Resolution:** Adjust the offending field to satisfy the rule in the table.
`{phase}` in the message identifies which of `training.solver.backward`,
`training.solver.forward`, or `simulation.solver` set the invalid value.

A failure during `novomodelo run` prints `error: {message}` on stderr, followed by hint lines that depend on the exit code:

- Exit `1`, a refusal met during the run (for example a `--threads` mismatch), adds ``-> run `novomodelo validate <CASE_DIR>` for a full diagnostic report``.

- Exit `3` adds `-> check constraint bounds (hydros may have conflicting min/max storage)` and ``-> run `novomodelo validate <CASE_DIR>` for a full diagnostic report``.
- Exit `4` adds `-> this may indicate a software or environment problem` and `-> report this at https://github.com/ons-ccee-epe/novomodelo/issues`.

On two or more MPI processes, each failing process (an MPI rank) first prints `rank {rank}:` on its own line and then the same lines, and the job stops with that process's exit code. When rank 0 fails to write the run outputs, every rank exits with rank 0's code, and the others print `rank 0 failed to write the run outputs; failing on every rank in lockstep`. A checkpoint that does not fit the study is refused before training or simulation starts; see [Policy-load errors](#policy-load-errors).

A panic, an internal fault, prints its message on stderr and exits `101`. On two or more MPI processes, the process that panics then prints `rank {rank}: panicked; aborting the MPI job` and aborts the whole job with exit code `101`.
