Non-normative software behavior for LP warm-start — what Novomodelo does at runtime,
beyond the methodology of [LP Warm-Start](/math/lp-warm-start). This tab
references the methodology body for the hand-off and the reconstruction rather
than restating them.

### Which solves start from a stored basis

Every phase captures its solves' bases into the basis store, but whether a
solve starts from the basis it is offered depends on the solver backend. The
HiGHS backend's phase profiles set `use_warm_start` to `false` for the forward
pass and simulation and to `true` for the backward pass, so by default forward
and simulation solves start cold and backward solves warm-start. Under
`use_warm_start: false` HiGHS ignores the offered basis: it is not installed,
not validated and not counted in `basis_offered`. A cold HiGHS solve does not
continue from the basis the previous solve left in the solver either, so every
solve of a cold phase starts from scratch. The retry levels 5–11, which
restore HiGHS's default settings before applying their own, keep the phase's
`use_warm_start`. The CLP backend has no such setting and starts a solve from
the offered basis in every phase. Where the sections below say a forward or
simulation solve starts from a stored basis, that applies under CLP, or under
HiGHS when that phase's profile sets `use_warm_start: true` (see
[Turning warm-start off](#turning-warm-start-off)).

A cold solve can stop at a different optimal vertex from a warm one, with the
same optimal value
([Determinism & Provenance §3](/math/determinism-guarantees#3-methodology-mechanisms)),
so a run's trial points, its cuts, its final lower bound and its simulated duals
can differ between the two settings.

### Backward work units

This section describes the backward pass when the dynamic method of cut
selection is inactive; the next section covers the active case. A backward work unit solves a chain of
openings in sequence for one trial point at one node. Before the chain, the
worker resets the solver's retained basis and factorization, reloads the node's
frozen LP template, and appends the cuts that the node's cut pool has gained
since the template was built. When the backward phase warm-starts, the chain's
first-solved opening starts from the trial point's slot in the basis store and
the remaining openings continue from the retained factorization; that
opening's basis is the only one the chain stores back into the slot, whatever
the phase setting. On a branching graph, each successor node's openings form a chain
of their own, because each successor loads its own LP.

The default `by_scenario` scheduler solves a trial point's openings at a
successor node as one chain. The `by_node` scheduler
(`training.parallelism.backward_scheduler`; see
[By-Node Scheduling](/running/performance/#by-node-scheduling)) splits them into
opening blocks and solves each block as a chain of its own. Each block's
first-solved opening reads the basis that the forward pass captured in the slot
(the forward capture). Under `by_node` the backward pass stores nothing, so the
slot keeps the forward capture, which is the basis the next iteration's forward
solve is offered.

However, under an enumerated forward pass
([`training.selection`](/running/configuration/#trainingselection)), the forward
pass solves each node once per iteration and stores that solve's basis in one
slot for the node, which the next iteration's forward solve at the node is
offered.
The backward pass reads no stored basis and stores none: each chain's
first-solved opening starts without a stored basis, and the rest continue from
the retained factorization.
Under the default HiGHS profiles an enumerated run therefore starts no solve
from the store.

### When a stored basis is reused

A stored basis seeds a solve only when the solve's phase warm-starts and the
basis was captured at the node being solved: each basis carries the node it was
captured at, and a basis tagged with another node, or an empty slot, leaves the
solve to start cold. A slot is empty until its first capture, so in a fresh run
the first iteration's forward solves start cold whatever the phase setting. An
infeasible forward solve clears its slot.

While the dynamic method of cut selection
([Cut Management §8](/math/cut-management#8-the-dynamic-method)) is active, no
solve reads or writes the store. The forward pass leaves its slot untouched,
and every solve's initial LP starts without a stored basis; in a warm-starting
phase the later openings of a backward chain, and each re-solve after the
dynamic method adds violated cuts, continue from the retained basis, while in a
cold phase they start cold as well. The store therefore keeps the bases
captured in the iterations before the dynamic method started, and those are the
bases the end-of-training checkpoint carries.

### Warm-start, resume and simulation-only runs

The end-of-training checkpoint carries one basis per trial point at each node:
the basis held in that trial point's slot when training ends, recorded with its
scenario and the pool slot of each cut row. A warm-start or resume run seeds
each trial point's slot from the checkpoint before its first iteration. A
resume run seeds a trial point from its own basis and leaves a trial point
without one to start cold; a warm-start run seeds a trial point without its own
basis from the node's lowest-scenario basis, since the run that wrote the
checkpoint may have run fewer forward passes. A slot left empty starts its first
solve cold and then reuses its own captures. Outside the dynamic method, a
warm-starting forward phase starts the first iteration's seeded solves through
the reconstruction of
[§4](/math/lp-warm-start#4-cut-aware-basis-reconstruction-by-slot-identity); a
fresh run has nothing to seed. Under the default HiGHS forward profile the
forward solves start cold and their captures replace the seeded bases before
the backward pass reads the slots, so the checkpoint bases seed no training
solve unless `training.solver.forward` sets `"use_warm_start": true`.

When the simulation phase warm-starts, and outside the dynamic method,
simulation starts each visited node's solve from that node's basis, taken from
the preceding training run or, in a simulation-only run, from the node's
lowest-scenario checkpoint basis for every scenario (a node with none is solved
without its own stored basis); under the dynamic method simulation solves start
without a stored basis. Under the default HiGHS simulation profile every
simulation solve starts cold, so a simulation-only run reads its checkpoint
bases only when `simulation.solver` sets `"use_warm_start": true`.


A checkpoint basis is used only when its column count equals the node's
current stage LP's, its row count equals the LP's template rows plus its
recorded cut rows, its basic count equals its row count, and every cut-row slot
it records holds a loaded cut. A basis that fails is left out, and the load
reports how many were left out and why the first failed (see
[Stored-basis gate](/running/policy-management/#stored-basis-gate)). An
admitted basis keeps the statuses of its recorded cut rows, matched to the
loaded pool by slot; a current cut row it does not record starts BASIC. Either
way only the basis the warm start begins from changes, never the optimal value
of the stage LP.

### What persists across solves

Warm-starting does not rest on a resident solver that holds each node's LP for
the lifetime of the run. Each backward work unit resets the solver's retained
state and reloads the node's frozen LP template before solving, so what carries
information from one solve to the next is not a live solver but two persistent
data structures:

- The **basis store**, keyed by `(scenario, node)`, which a chain's first-solved
  opening reads and a capture refreshes.
- The **per-iteration frozen templates**, one per cut pool (one per stage on a
  stage chain), each baking in the currently active cut set. A template is built
  once per iteration and loaded into the solver afresh for every trial point it
  serves; within a chain only the realization's bounds then change.

Because the template is reloaded rather than mutated in place, LP structural
state does not accrue silently inside a long-lived solver. The frozen templates
grow over a run, because each iteration's template bakes in more cuts than
the last, and each stored basis grows with them, carrying one status per row.
For a study with many nodes and a large state-variable count, the combined
footprint of the templates and the basis store can be significant.

When the backward phase warm-starts, as it does by default, a backward-pass
solve after the first iteration costs mainly the dual simplex
work that restores optimality from the reused basis, once that basis is
reconciled to the current cut set
([§4](/math/lp-warm-start#4-cut-aware-basis-reconstruction-by-slot-identity)),
rather than Phase-I feasibility work from a cold start.

### Turning warm-start off

Each phase's solver profile — `training.solver.backward`,
`training.solver.forward` and `simulation.solver` — accepts `use_warm_start`,
which overrides the phase default (`false` for forward and simulation, `true`
for backward). Setting it to `false` forces every solve in that phase cold, and
setting it to `true` lets forward or simulation solves start from the store;
outside the dynamic method, captures fill the basis store either way. The
backward setting is diagnostic, not a production option: comparing a cold
backward pass with a warm one isolates the warm-start contribution to
training-run performance. Per-phase profile overrides are HiGHS-only; the CLP
backend rejects a set field at setup; see
[`training.solver`](/running/configuration/#trainingsolver).
