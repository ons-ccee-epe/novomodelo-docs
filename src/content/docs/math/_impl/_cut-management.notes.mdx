Non-normative software behavior for cut management — what Novomodelo does at
runtime, beyond the equations above. This tab references the methodology body
for the derivations rather than restating them.

### Reduced-cost unscaling divides by the column scale

Methodology §2 derives each cut coefficient from the reduced cost of a pinned
incoming-state column, unscaled by that column's prescaler factor. In code
terms the unscaling step is a **division**:
`coefficient = reduced_cost / col_scale[col]` (empty `col_scale` ⇒ the raw
reduced cost, unscaled).

### Storage-only cut projection

With the inflow lags projected out of the cuts on a stage under a PAR model
with lag terms, $\underline{z}^k$ is not guaranteed to be a lower bound on the optimal
value of the model as trained, and the gap is not a certificate
([condition 4](/math/cut-management#4-cut-validity)). Projecting the cuts onto
the inflow lags as well, with storage kept, on every stage satisfies
condition 4; the remaining hypotheses are those of
[Tier 1](/math/cut-management#tier-1-valid-lower-bound). The projection is
chosen per stage: the key and its default are in
[`stages[].state_variables`](#stagesstate_variables--cut-projection) of the
Configure tab, and the components each selection projects onto are in
[State Augmentation §7](/math/state-augmentation#7-cut-state-projection).

### Checkpoints store cuts in the writing study's scaled units

A checkpoint stores every cut's intercept and coefficients as the pool holds
them, in the writing study's scaled cost space, and each pool's file records the
cost-scale factor of that space. A load uses a pool unchanged when its factor
equals the loading study's bit for bit, so a same-factor round trip, a resume
included, reproduces the pool exactly. At another factor every value becomes
`(value * source) / loading`, the multiplication first. This is **orthogonal** to
the `col_scale` reduced-cost unscaling above: `col_scale` is a per-column LP
prescaler applied inside a single solve, while the cost-scale factor is the
global objective scaling of a study. See [Policy Management — Cost-Scale
Canonicalization](/running/policy-management/#cost-scale-canonicalization)
for the load-time rule.

### Append-only pool, deterministic slots

Every cut ever generated is retained for the lifetime of the run at a stable
slot index — a fixed function of the iteration and forward-pass index that
generated it (methodology §5). The pool is never compacted, and nothing is
ever deleted from it; "deactivation" always means something narrower than
removal (below).

### Deactivation excludes a cut from the template; the LB LP is append-only

Novomodelo's row-management pipeline touches two different LPs, and "deactivating"
a cut means something slightly different in each:

- In the **per-iteration forward/backward stage LP** — rebuilt from the stage
  template at the start of each solve — a deactivated cut is simply omitted
  from that iteration's template rebake. Only active cuts are encoded as LP
  rows on each forward/backward solve; there is no row to toggle because the
  row was never emitted.
- In the **persistent lower-bound LP** the pool is **append-only**: only
  active cuts are ever appended, and a cut already present is not re-appended;
  appended rows are **never removed**, so the training
  lower bound stays monotone and every appended row keeps constraining.
  Deactivation touches no row here; it only changes which cuts the
  forward/backward template rebake encodes. The only $+\infty$ on a cut row is
  the ordinary upper bound of the one-sided `≥` cut, present on every
  active row — not a deactivation sentinel.

Both routes preserve the slot index, which is what makes reactivation exact:
a cut that a later selection pass restores is re-baked into the template, at
the same slot, with the same coefficients it was generated with.

### Selection pass and budget pass

The row-management pipeline runs after each iteration's backward pass and cut
synchronization, in two passes over the **interior** pools — those strictly
between the root and the terminal pool:

1. **Selection pass** (`level1`) — runs at iterations that are a multiple of
   `check_frequency`. It drops the trial states older than the
   `lookback_iterations` window, records each stored state's owner, and sets
   every scored cut's flag from that record, the current iteration's cuts
   included. The root pool is never selected, and the backward pass adds no cut
   to the terminal pool. Within a pool, trial points are evaluated in parallel
   blocks. `dynamic` never runs this pass and never deactivates a pool cut.
2. **Budget pass** (`max_active_per_stage`) — runs **every** iteration after
   the selection pass. It counts and evicts only the cuts this run generated: a
   loaded cut neither counts nor is evicted, and a cut of the current iteration
   counts but is never evicted, so a pool's active count can exceed the cap by
   its loaded cuts. Under `level1` an evicted cut that still owns a state is
   reactivated by the next selection pass, and the cap is applied again in that
   iteration. The cap is refused at load with `dynamic`, whose candidates are
   the active cuts, so an evicted cut would never be a candidate again, and
   with an enumerated forward pass, whose backward records no binding, so
   eviction would follow generation order alone.
   [Stage 2: Budget Enforcement](/running/performance/#stage-2-budget-enforcement)
   gives the eviction order.

### The dynamic method is lazy, not a deactivation pass

The dynamic method (methodology §8) never deactivates a pool cut. Each stage
solve instead starts from a small resident subset — the active cuts that bound
within the last `seed_window` iterations plus every cut generated this
iteration — and grows it by scoring the omitted candidates and adding the
most-violated ones. After 50 rounds (not user-configurable) the per-round limit
is lifted and every violated candidate is added in each round until none is
left, so a solve always returns the optimum over the candidates up to the
violation tolerance and needs no closing solve. Each solve that reaches the 50th
round with a candidate still violated is counted in the `lazy_round_cap_hits`
column of [`training/convergence.parquet`](/reference/output/training/#trainingconvergenceparquet).
The simulation seeds every active cut, so its lazy solve adds none.

The dynamic method is refused at setup under an enumerated forward pass
(methodology §8): the enumerated backward records no binding activity, so the
seed window's activity clock never advances past each cut's generating
iteration.

A cut loaded into the pool by `policy.mode = "warm_start"` or `"resume"`
(Inputs & Outputs tab) keeps the iteration that generated it in its source run.
Under a finite `candidate_recency` window a loaded cut is always a candidate,
like a boundary cut. Under `resume` a reloaded cut counts as loaded only when
the run that wrote the checkpoint loaded it; the cuts that run generated are
windowed as they were in it.
